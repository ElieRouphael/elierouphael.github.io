## A workshop you can experiment on {#why}

You run the workshop of chapter [[a03]]: five machines, two carts, orders of four families arriving all day, changeovers, breakdowns. Does "most urgent first" beat "shortest setup first"? Trying each rule for a few weeks is impossible: the orders of week one are not those of week two, and the losing rule costs real late deliveries.

A **simulation** replaces the workshop by a program that follows the same causes and effects: orders appear, wait, are carried, set up, processed, delayed by breakdowns and leave. On it you can replay the same day under every rule, so that the method is the only difference between two runs (chapter [[d02#crn]]). One simulated day under a rule, without breakdowns, takes a median of 5.8 ms for about 1,348 simulated minutes, 22.5 hours: a speed-up of $1.4 \times 10^7$ over real time. The optimiser runs take far longer, because planning, not simulating, costs time (chapter [[c03]]).

::: define What is a discrete-event simulation?
**In plain words:** a program that keeps a list of what is going to happen next (an order arrives at 10:42, machine 3 finishes at 10:47), jumps straight to the soonest item, updates the shop, writes the new consequences onto the list, and repeats.

**More precisely:** the state of the model changes only at a countable set of instants, the **events**; between two events nothing changes and nothing is computed. The simulator keeps a **simulation clock** $t$ and an **event list** of pending events keyed by their time. One iteration removes the earliest event, sets $t$ to its time and runs its **event routine**, which changes the state and may schedule or cancel future events.

- State :: what determines the future given the future random inputs: queues, what each machine does and how much work it has left, which machines are down, where the carts are.
- Event :: an instant at which the state changes: an arrival, the end of a changeover or of an operation, a failure, a repair, a cart reaching a station.
- Random inputs :: arrival times, families, due dates and breakdowns, drawn with a seed so that a run can be replayed exactly.
:::

Everything here is synthetic: the workshop and its distributions were invented, not measured on a plant. The simulation is a fair test bench for decision methods, not a forecast of a real factory.

## Time steps or events {#events}

**Time-stepped.** Choose a step $\Delta$, say one minute, and loop: $t \leftarrow t + \Delta$, then ask every machine, cart and order whether anything happened. Simple, and natural for a differential equation; but most steps are empty, events are rounded to the grid, and two events in one step are ordered arbitrarily.

**Event-driven.** Keep the list of future events and jump from one event time to the next: no empty steps, no rounding. The price is bookkeeping: every routine must write the consequences it causes onto the list, and strike off those that will no longer happen.

::: define What is the event list?
**In plain words:** the simulator's diary of the future, sorted by time. Its top line says what happens next and when.

**More precisely:** a priority queue of records (time, tie-breaker, event), with two operations, *insert* and *remove the minimum*. A binary heap, a tree that keeps the soonest event on top, does each in about $\log_2 n$ comparisons for $n$ pending events. SimPy keeps exactly this: a heap of (time, priority, sequence number, event), where the sequence number breaks ties in scheduling order, so that a run is deterministic.

- Clock :: the time of the event being executed; it never moves backwards, and it jumps rather than ticks.
- Scheduling :: inserting a future event: "B's changeover will be done at minute 30".
- Cancelling :: striking off an event that will not happen: a breakdown at minute 25 cancels the end of changeover planned for 30.
:::

**The paint machine, traced by hand.** Take the four orders of chapter [[a02]], blue A (20 min), red B (10), blue C (15) and red D (25), but let them arrive at minutes 0, 5, 12 and 40. The machine is set up for blue, a colour change takes 10 minutes, the rule is first come, first served (FIFO), and the machine is down from minute 25 to 33. An interrupted operation keeps the work done and resumes after the repair, changeovers included. Only the *next* arrival is on the list: each arrival, when it happens, schedules the one after it. The hero replays this trace with **Next event**.

Given the same orders, one machine and carts that take no time, the repository's simulator produces the same log, B's changeover in two pieces (20 to 25, 33 to 38), as the numbers script checks.

**The honest count for the real workshop.** On test day 0 under "most urgent first" (EDD), without breakdowns, SimPy executes 1,680 events, its own bookkeeping included (process starts and ends, interrupts, stale timeouts), on only 613 of the 1,384 minutes: a one-minute loop would find nothing to do in 56 % of its steps, while several events often share a minute, ordered by the tie-breaker. With breakdowns, 1,965 events fall on 712 of 1,493 minutes, 52 % empty. With times in seconds, a time-stepped loop would need 60 times more steps; the event list would hold the same events.

## Random arrivals: the Poisson process {#poisson}

In plain words, the repository's arrival model says: at every instant an order is as likely to arrive in the next minute as at any other instant, whatever happened before. That sentence pins down the distribution of the gaps.

::: define What is a Poisson process?
**In plain words:** arrivals at a constant average rate but without rhythm: clumps and droughts happen by chance, and when the last order came tells you nothing about when the next comes.

**More precisely:** a counting process $R(t)$, the number of arrivals (releases) in $[0, t]$, with $R(0) = 0$, is a Poisson process of rate $\lambda > 0$ when its increments over disjoint intervals are independent, and an interval of length $h$ gains one arrival with probability $\lambda h + o(h)$ and two or more with probability $o(h)$, where $o(h)$ is a term that vanishes faster than $h$ as $h \to 0$. Equivalently, the gaps $X_1, X_2, \dots$ are independent exponentials of rate $\lambda$; the equivalence is a standard theorem, which we only cite [[ref:3]].

- Exponential distribution :: $P(X > x) = e^{-\lambda x}$ for $x \ge 0$, density $\lambda e^{-\lambda x}$.
- Count in a window :: $R(t+u) - R(t)$ is Poisson with mean $\lambda u$: $P(k \text{ arrivals}) = e^{-\lambda u} (\lambda u)^k / k!$.
- In the workshop :: $1/\lambda = 20.83$ min, $\lambda = 0.0480$ orders per minute, 2.88 per hour.
:::

**Mean and variance, derived.** Integrate by parts against the density $\lambda e^{-\lambda x}$, whose antiderivative is $-e^{-\lambda x}$; the boundary terms vanish at 0 and at infinity, because $x^k e^{-\lambda x} \to 0$:

$$\begin{aligned} E[X] &= \int_0^\infty x\, \lambda e^{-\lambda x}\, dx = \Big[-x e^{-\lambda x}\Big]_0^\infty + \int_0^\infty e^{-\lambda x}\, dx = \frac1\lambda, \\ E[X^2] &= \int_0^\infty x^2 \lambda e^{-\lambda x}\, dx = \Big[-x^2 e^{-\lambda x}\Big]_0^\infty + \frac2\lambda \int_0^\infty x\, \lambda e^{-\lambda x}\, dx = \frac2\lambda E[X] = \frac2{\lambda^2}, \\ \operatorname{Var} X &= E[X^2] - E[X]^2 = \frac2{\lambda^2} - \frac1{\lambda^2} = \frac1{\lambda^2}. \end{aligned}$$
%narrow \begin{aligned} E[X] &= \int_0^\infty x \lambda e^{-\lambda x} dx \\ &= 0 + \int_0^\infty e^{-\lambda x} dx = \tfrac1\lambda \\ E[X^2] &= \int_0^\infty x^2 \lambda e^{-\lambda x} dx \\ &= 0 + \tfrac2\lambda \int_0^\infty x \lambda e^{-\lambda x} dx \\ &= \tfrac2\lambda E[X] = \tfrac2{\lambda^2} \\ \operatorname{Var} X &= E[X^2] - E[X]^2 = \tfrac1{\lambda^2} \end{aligned}

The standard deviation equals the mean, 20.83 minutes for the workshop (a variance of 434 min²): the coefficient of variation, standard deviation over mean, is exactly 1, where a timetable has 0. That is "no rhythm" in numbers.

**The memoryless property, proved.** For $s, t \ge 0$,

$$P(X > s + t \mid X > s) = \frac{P(X > s + t)}{P(X > s)} = \frac{e^{-\lambda (s+t)}}{e^{-\lambda s}} = e^{-\lambda t} = P(X > t).$$
%narrow \begin{aligned} P(X > s+t \mid X > s) &= \tfrac{P(X > s+t)}{P(X > s)} \\ &= \tfrac{e^{-\lambda(s+t)}}{e^{-\lambda s}} \\ &= e^{-\lambda t} = P(X > t) \end{aligned}

After $s$ minutes without an order, the remaining wait has the distribution of a fresh gap. The exponential is the only continuous distribution with this property (exercise 2), which is why "a constant chance per minute" and "exponential gaps" are the same model. In the widget, the leftover part of an exponential gap looks exactly like a whole gap; with uniform gaps of the same mean, waiting makes the next arrival come sooner.

**The real stream.** `make_scenario` draws 60 exponential gaps of mean 20.83 per test day and floors the cumulative sums to integer minutes. On the 20 test days the 1,200 gaps have mean 20.14 and standard deviation 20.77 min. The standard error of a mean of 1,200 draws is $20.83/\sqrt{1200} = 0.60$, so 20.14 is 1.14 standard errors from 20.83: ordinary chance. The 392 full hours hold 2.93 arrivals on average with variance 3.12, against a Poisson mean and variance of 2.88; an hour without any order happens 6.6 % of the time against $e^{-2.88} = 0.056$. The memoryless check: of the 442 gaps longer than 20 min, a share of 0.344 also lasts beyond 40, where theory predicts $e^{-20/20.83} = 0.383$, the share of fresh gaps beyond 20. Its standard error is about $\sqrt{0.38 \times 0.62 / 442} = 0.023$, so 0.344 is 1.7 standard errors off: within chance.

**Merging (superposition).** For independent Poisson streams of rates $\lambda_1$ and $\lambda_2$, the time to the next event of either is $\min(X_1, X_2)$, and

$$P(\min(X_1, X_2) > t) = P(X_1 > t)\, P(X_2 > t) = e^{-(\lambda_1 + \lambda_2) t}:$$
%narrow \begin{aligned} P(\min(X_1, X_2) > t) &= P(X_1 > t) P(X_2 > t) \\ &= e^{-(\lambda_1 + \lambda_2) t} \end{aligned}

the first gap is exponential with rate $\lambda_1 + \lambda_2$. The whole merged stream is Poisson by the definition: the sum of two independent processes with independent increments has independent increments, and in an interval of length $h$ it gains one event with probability $(\lambda_1 + \lambda_2) h + o(h)$ and two or more with probability $o(h)$, since both streams firing has probability $\lambda_1 \lambda_2 h^2 + o(h^2)$. While all five machines are up, each fails at rate $1/120$ per minute, so the next failure *somewhere in the shop* comes after an exponential time of mean $120/5 = 24$ minutes.

**Splitting (thinning).** If each arrival of a Poisson stream of rate $\lambda$ is independently labelled family $f$ with probability $p$, the family-$f$ arrivals form a Poisson process of rate $p\lambda$. The proof counts. Start at time 0. No family-$f$ order comes in the first $t$ minutes exactly when each of the $k$ arrivals in that window, $k$ Poisson with mean $\lambda t$, is labelled not-$f$, which happens with probability $(1-p)^k$. So the wait $S$ for the first family-$f$ order has

$$P(S > t) = \sum_{k \ge 0} e^{-\lambda t} \frac{(\lambda t)^k}{k!} (1-p)^k = e^{-\lambda t}\, e^{(1-p)\lambda t} = e^{-p\lambda t},$$
%narrow \begin{aligned} P(S > t) &= \sum_{k \ge 0} e^{-\lambda t} \tfrac{(\lambda t)^k}{k!} (1-p)^k \\ &= e^{-\lambda t} e^{(1-p)\lambda t} = e^{-p\lambda t} \end{aligned}

an exponential of rate $p\lambda$ (the sum is the series of $e^x$ at $x = (1-p)\lambda t$). Each later family-$f$ gap is built like this first one from its own disjoint block of the independent gaps $X_i$ and labels, so all of them are independent copies of $S$: a renewal process with exponential gaps, that is, a Poisson process. That the families are also independent of one another needs a further argument, which Ross gives [[ref:3]]. The workshop draws families uniformly, $p = 1/4$, so each family arrives with mean gap $4 \times 20.83 = 83.33$ min. The 1,120 family gaps of the test days average only 77.2 min: counted inside a day, long gaps that would run past the last order are never seen, which pulls the expected measured mean down to 78.9 (a simulation of the same measurement), within one standard error, 2.4, of 77.2.

## Load, by hand, and what it leaves out {#load}

In plain words, the **load** asks: of all the machine time the shop has, what share is needed just to do the work that comes in? Five machines offer five machine-minutes every minute; orders bring (orders per minute) × (minutes of work per order).

::: define What is the load ρ?
**In plain words:** how busy the machines would have to be, on average, to keep up with the orders, counting only processing on the fastest routes.

**More precisely:** with arrival rate $\lambda$, expected work per job $E[w]$ and $m$ machines, $\rho = \lambda\, E[w] / m$. If $\rho \ge 1$, work arrives faster than the machines could process it even on their fastest routes, and the queue grows without bound; a fortiori once changeovers are counted. $\rho < 1$ is necessary but not sufficient: a single machine can still be overloaded, since some operations can run on one machine only. Only when $w$ is the work actually done (processing on the chosen machines plus changeovers) does $\lambda E[w]/m$ equal the long-run busy fraction, averaged over the machines; with fastest-route $w$ it is a lower bound on that fraction.

- Fastest-route work :: the repository's choice of $w$: each operation on its quickest eligible machine, $W_f$ in [[a03#workshop]].
:::

**By hand, for the workshop.** The fastest routes of the four families take 46, 61, 70 and 73 minutes; families are equally likely, so

$$E[w] = \frac{46 + 61 + 70 + 73}{4} = 62.5 \text{ min}, \qquad \frac1\lambda = \frac{E[w]}{\rho\, m} = \frac{62.5}{0.60 \times 5} = 20.83 \text{ min}.$$
%narrow \begin{aligned} E[w] &= \tfrac{46+61+70+73}{4} = 62.5 \text{ min} \\ \tfrac1\lambda &= \tfrac{E[w]}{\rho m} = \tfrac{62.5}{0.60 \times 5} = 20.83 \text{ min} \end{aligned}

The repository fixes $\rho = 0.60$ and derives the gap, which is what `mean_interarrival` computes; read backwards, $\rho = 62.5 / (20.83 \times 5) = 0.60$.

**What $\rho$ ignores**, each item computed from the workshop data:

- *Non-fastest routes.* Routing picks the machine with the earliest expected finish, which may be a slower one with a shorter queue. If every operation took the average time of its eligible machines, $E[w]$ would be 68.00 min and $\rho = 0.65$.
- *Changeovers.* The mean changeover between two different families is 6.95 min (from 3 to 10). In random order the family would change with probability $3/4$ (a rough estimate: each machine sees only some families), adding about 5.21 min per operation, 20.9 min per job: $\rho = 0.80$. Changeovers depend on the order of the jobs, which is the decision being studied; that is why the load leaves them out.
- *Breakdowns.* A machine is available a fraction $A = 0.857$ of the time (Part 5), so the fastest-route work per *available* machine is $0.60 / 0.857 = 0.70$.
- *Transport.* A job on a cart, 2 or 3 minutes per move, is in the shop but not being processed.

**Measured.** Over the 20 test days without breakdowns, first come, first served (FIFO) spends 67.3 min of processing and 18.1 min of changeover per job: a load of 0.82 with both counted. Shortest setup first (SST) cuts the changeovers to 15.3 min per job (load 0.79) and optimiser re-planning (CP-SAT) to 10.6 (load 0.74). The shop is much busier than 0.60 says, and how much depends on the decisions (chapter [[c03]]).

## Breakdowns and availability {#breakdowns}

In plain words, each machine lives a cycle: it works, fails, is repaired, works again. The repository draws the working stretch from an exponential of mean MTBF = 120 min, in calendar time from a repair to the next failure whether or not the machine is busy, and the repair from a uniform distribution on $[0.5, 1.5] \times \text{MTTR} = [10, 30]$ min, mean 20 and standard deviation $20/\sqrt{12} = 5.77$; both are rounded to whole minutes, at least 1.

::: define What is an alternating renewal process?
**In plain words:** a machine that alternates between "up" and "down", every up-and-down cycle a fresh, independent copy of the same random pair.

**More precisely:** up times $U_1, U_2, \dots$ and down times $D_1, D_2, \dots$, the pairs $(U_i, D_i)$ independent and identically distributed; cycle $i$ lasts $C_i = U_i + D_i$ minutes.

- MTBF :: here $E[U]$, the mean time from a repair to the next failure, 120 min. Some texts mean the time between successive failures, $E[U] + E[D]$; check which.
- MTTR :: $E[D]$, the mean repair time, 20 min.
- Availability :: $A$, the long-run fraction of time a machine is up.
:::

**Availability from expected cycle lengths.** Over the first $n$ cycles the machine is up $\sum_{i \le n} U_i$ out of $\sum_{i \le n} (U_i + D_i)$. Divide both by $n$ and apply the strong law of large numbers to each:

$$\frac{\sum_{i=1}^n U_i}{\sum_{i=1}^n (U_i + D_i)} = \frac{\frac1n \sum_{i=1}^n U_i}{\frac1n \sum_{i=1}^n (U_i + D_i)} \;\xrightarrow[n \to \infty]{}\; \frac{E[U]}{E[U] + E[D]} = A,$$
%narrow \begin{aligned} \frac{\sum_{i \le n} U_i}{\sum_{i \le n} (U_i + D_i)} &= \frac{\frac1n \sum_{i \le n} U_i}{\frac1n \sum_{i \le n} (U_i + D_i)} \\ &\to \frac{E[U]}{E[U] + E[D]} = A \end{aligned}

that is, $A = \text{MTBF}/(\text{MTBF} + \text{MTTR})$. This is the simplest case of the renewal-reward theorem: long-run reward per unit time equals expected reward per cycle over expected cycle length [[ref:3]]. To pass from $n$ cycles to a time $T$, let $B(T)$ be the number of cycles started by $T$; $T$ lies between the ends of cycles $B(T)-1$ and $B(T)$, both of which grow like $B(T)\, E[C]$, so $T/B(T) \to E[C]$. The up time in $[0, T]$ lies between $\sum_{i < B(T)} U_i$ and $\sum_{i \le B(T)} U_i$; divided by $T = B(T) \cdot (T/B(T))$, both bounds tend to $E[U]/E[C]$, so the up fraction of $[0, T]$ tends to $A$ too. For the workshop,

$$A = \frac{120}{120 + 20} = \frac{120}{140} = 0.857, \qquad 1 - A = 0.1429:$$
%narrow \begin{aligned} A &= \tfrac{120}{120 + 20} = \tfrac{120}{140} = 0.857 \\ 1 - A &= 0.1429 \end{aligned}

each machine is down about 14.3 % of the time. Only the means enter $A$, not the distributions.

**Breakdowns per machine per day.** By the same argument a machine has one breakdown per $E[C] = 140$ minutes in the long run: over $T = 1{,}400$ minutes, about a simulated day with breakdowns, $1400/140 = 10.0$ per machine and 50 for the five. The count $B(T)$ is random; exercise 4 computes its variance.

**On the test days.** The 7,130 cycles `make_scenario` generates for the 20 test days and 5 machines have mean up time 119.9 min and mean repair 19.98 min: availability 0.857. Over the first 1,400 minutes of the 100 machine-days, the machines are down 13.9 % of the time and break down 9.78 times on average; single machine-days range from 2.9 % to 23.9 % and from 2 to 16 breakdowns. One day is a noisy sample, which is why the course compares methods on twenty.

**What a breakdown does to an operation.** A failure suspends the operation in progress, changeover or processing; the work done is kept and the rest resumes after the repair on the same machine, the "preempt-resume" assumption of the scheduling literature [[ref:2]]. The controller learns of the failure and the MTTR, never the actual repair time. Breakdowns lengthen the day: the rules' makespan grows from 1,348 to 1,423 minutes on average.

## Little's law {#little}

In plain words: if orders come in at 3 an hour and each stays 2 hours, about 6 orders are inside on average. That is all Little's law says, and it holds for any rule, any routing and any breakdowns.

::: define What is Little's law?
**In plain words:** the average number of jobs inside equals the rate at which they come in times the average time each spends inside.

**More precisely:** observe a system on $[0, T]$; let $N(t)$ be the number of jobs inside, $L_T = \frac1T \int_0^T N(t)\, dt$ its time average, $n$ the number of arrivals, $\lambda_T = n/T$ and $W_T$ their mean time inside. If the system is empty at $0$ and at $T$, then $L_T = \lambda_T W_T$ exactly. In the long run $L = \lambda W$: Little proved it in 1961 for stationary systems [[ref:4]]; on a single path it holds whenever the limits $\lambda = \lim n/T$ and $W$ exist and are finite (Stidham, 1974 [[ref:6]]; see also Ross [[ref:3]]).

- Flow time :: $F_j = C_j - r_j$, the time job $j$ spends in the shop ([[a01]]); $W$ is the mean flow time $\bar F$, not the fastest-route work $W_f$ of Part 4.
- Work in progress :: $L$, the average number of jobs in the shop.
:::

**The proof is an area counted twice.** Draw for each job a horizontal bar from its arrival $r_j$ to its completion $C_j$. At any instant, $N(t)$ is the number of bars crossing $t$, so the area under $N$ is the total length of the bars:

$$\int_0^T N(t)\, dt = \sum_{j=1}^{n} (C_j - r_j) = n\, W_T \quad\Longrightarrow\quad \frac1T \int_0^T N(t)\, dt = \frac nT \cdot W_T .$$
%narrow \begin{aligned} \int_0^T N(t) dt &= \sum_{j=1}^{n} (C_j - r_j) = n W_T \\ \Longrightarrow \tfrac1T \int_0^T N(t) dt &= \tfrac nT \cdot W_T \end{aligned}

If jobs are still inside at $T$, their bars are cut and the two sides differ by the cut-off parts; divided by $T$, the difference tends to 0 whenever $\lambda$ and $W$ exist and are finite, which is the sample-path form of Little's theorem [[ref:6]].

**On the worked example.** $N(t)$ is 1 on $[0, 5)$, 2 on $[5, 12)$, 3 on $[12, 20)$, 2 on $[20, 40)$, 3 on $[40, 48)$, 2 on $[48, 73)$ and 1 on $[73, 108)$: an area of $5 + 14 + 24 + 40 + 24 + 50 + 35 = 192$ job-minutes, and the flow times 20, 43, 61 and 68 sum to 192 too. So $L = 192/108 = 1.778 = (4/108) \times 48 = \lambda_T W_T$. The hero shows this equality at the end of any run, and why it fails in the middle of one.

**On the workshop.** A simulated day starts empty at 0 and ends empty at the makespan $C_{\max}$, so the proof applies exactly. Re-running the four rules on the 20 test days (flow times identical to `runs.csv`) and counting $N(t)$ from the executed log, FIFO without breakdowns has a day-average $L$ of 7.146 jobs and $\lambda_T W_T = 7.146$, to every digit. The nominal rate gives a larger $\lambda W = 157.4/20.83 = 7.56$: a steady-state reading, the work in progress of a shop whose day never ended, while a real day drains out after its last arrival and $\lambda_T$ is about $1/22.3$ per minute. EDD: 6.581 against 6.99; FIFO with breakdowns: 9.670 against 10.90.

**What it buys.** The area under $N$ is $nW$, the job-minutes spent in the shop, so the day average is $L = nW / C_{\max}$, which the mean flow times and makespans of `results/runs.csv` give for every method:

::: table num
| Method | No breakdowns: $W$ (min) | Day-average $L$ (jobs) | Frequent breakdowns: $W$ (min) | Day-average $L$ (jobs) |
|---|---|---|---|---|
| First come, first served (FIFO) | 157.4 | 7.15 | 227.0 | 9.67 |
| Shortest job first (SPT) | 147.2 | 6.67 | 209.0 | 8.85 |
| Most urgent first (EDD) | 145.6 | 6.58 | 202.9 | 8.61 |

The day averages divide by days of different lengths, so they differ a little less. Little's law is also the standard check of a simulator's bookkeeping.

## SimPy in a few ideas {#simpy}

An event list by hand is fine for one machine and error-prone for a workshop. SimPy [[ref:5]] lets you tell each actor's story in order and keeps the list for you.

::: define What is a SimPy process?
**In plain words:** a function that tells the life of one actor, an order stream, a machine, a cart, in the order things happen to it, saying "wait" wherever time passes.

**More precisely:** a Python generator function registered with `env.process(gen)`. Each `yield` hands an event to the `simpy.Environment` and suspends the generator until the event is triggered; `env.timeout(d)` is triggered $d$ time units later, so yielding it means "sleep $d$ simulated minutes". `env.run(until=...)` repeatedly pops the earliest event from the heap, sets `env.now` to its time and resumes the processes waiting on it.

- Event :: any `simpy.Event`; a process can wait on a timeout, on another process, or on an event someone else triggers with `succeed()`.
- Generator :: a Python function containing `yield`; each call to `next()` on it runs it up to the next `yield` and pauses it there, keeping its local variables, until it is resumed.
- Interrupt :: `proc.interrupt(cause)` throws `simpy.Interrupt` into a waiting process, whose pending timeout no longer resumes it: how a breakdown stops an operation.
:::

The arrivals of Part 2 as a process: the loop is the story, the timeouts are the gaps, and each arrival schedules the next by resuming the loop.

```python
import simpy

def arrivals(env, gaps):
    for name, g in zip("ABCD", gaps):
        yield env.timeout(g)              # sleep g simulated minutes
        print(f"t = {env.now}: order {name} arrives")

env = simpy.Environment()
env.process(arrivals(env, [0, 5, 7, 28]))
env.run()                                 # t = 0, 5, 12, 40
```

The breakdown of Part 2 as an interrupt: the machine finishes A at 20, starts B's colour change, is interrupted at 25 with 5 minutes left, waits out the 8-minute repair and finishes at 38, as in the trace.

```python
def machine(env):
    yield env.timeout(20)                 # A is processed from 0 to 20
    left = 10                             # then the colour change for B
    while left > 0:
        start = env.now
        try:
            yield env.timeout(left)
            left = 0
        except simpy.Interrupt as stop:
            left -= env.now - start       # keep the work already done
            yield env.timeout(stop.cause) # wait out the repair
    print(f"t = {env.now}: changeover done")

def breakdown(env, victim):
    yield env.timeout(25)
    victim.interrupt(8)                   # down for 8 minutes

env = simpy.Environment()
proc = env.process(machine(env))
env.process(breakdown(env, proc))
env.run()                                 # done at 38
```

The repository refines the second pattern in one way: the machine cannot know the repair time, so the breakdown process triggers an event `up_event` when the repair is over, and the interrupted operation waits on that event.

## The workshop in code {#code}

The scenario is drawn before the simulation starts, so the random inputs are the same whatever the decisions.

::: code jobshop/scenario.py:make_scenario
One generator per purpose and per seed: `default_rng([seed, 1])` for the arrivals, `default_rng([seed, 2, m])` for the breakdowns of machine `m`, so the same seed gives the same jobs with and without breakdowns ([[d02#crn]]). The gaps are `rng.exponential(mean_interarrival(ws, load))`, the $1/\lambda = 62.5/(0.60 \times 5)$ of Part 4, and `np.floor(np.cumsum(gaps))` makes integer arrival minutes. Families are uniform (the thinning of Part 3); due dates are arrival plus $k \times W_f$, $k$ uniform in $[2, 4]$. Each machine's downtime is the alternating renewal process of Part 5, `down = t + max(1, round(exponential(mtbf)))`, `up = down + max(1, round(uniform(0.5, 1.5) * mttr))`, `t = up`, repeated far beyond any run and hidden from the controllers.
:::

`Shop.run` starts one process for the arrivals and one per machine with downtime, and runs `env.run(until=self._all_done)`: until the last job is done, not until a time. `Shop._arrivals` waits for each scenario arrival time, tells the controller (`on_event(..., "arrival")`, where CP-SAT re-plans, chapter [[c03]]) and asks for a routing: one pending timeout at a time, as in the hand trace. A breakdown is handled by two cooperating processes.

::: code jobshop/shop.py:Shop._breakdowns
At `t_down` the machine is marked down, a fresh `up_event` is created for the operation to wait on, the running segment is booked into the log by `_close_segment` (the work done so far, subtracted from what remains), and the operation's process is interrupted. The controller hears of the breakdown and may reroute the queue (chapter [[b02#routing]]). At `t_up` the event succeeds, the controller hears of the repair, and `_try_start` lets an idle machine start again.
:::

::: code jobshop/shop.py:Shop._work
One operation as a loop over segments, so that a breakdown can cut it. While work remains: if the machine is down, wait for `up_event`; otherwise run the setup (`rem_setup`), then the processing (`rem_proc`), each as one timeout, and book it. An interrupt lands in the `except` and the loop waits for the repair. When nothing remains, the job is routed to its next operation or is done, and the machine asks for its next job.
:::

::: code jobshop/shop.py:Shop._try_start
The only place where a machine starts a job, and the only place the simulator asks a controller to sequence. The machine must be idle and up with a non-empty queue; `controller.sequence(shop, m)` returns a queued job, or `None` to wait (CP-SAT uses it to keep a machine for a planned job still on its way). The changeover `setup_time(m, last_family, family)` comes from the data, not from the controller.
:::

Carts follow the same pattern: `Shop._transport` is one process per mission, an empty leg if needed and the loaded leg, each a timeout logged as a `Leg`. Requests are served oldest first by the nearest idle cart, for every method: the carts are simulated, not optimised.

**The controller interface.** The simulator takes no decision. It calls `controller.route(shop, job)` when a job needs a machine for its next operation, `controller.sequence(shop, machine)` when a machine is free, and `controller.on_event(shop, kind, ...)` on every arrival, breakdown and repair, where the controller may `reroute` queued jobs. The physics of the shop is fixed. That makes the comparison fair: FIFO, the DQN agent and CP-SAT are objects with the same three methods, run on the same simulator and scenario and judged by the same checker (chapter [[d02]]). Exercise 5 writes another.

## Common pitfalls {#pitfalls}

1. **"One order every 20.83 minutes."** That is the average, not a timetable: the test gaps range from 0 to 161 minutes, and an hour without any order happens about one hour in 15 on the test days (6.6 %; one in 17.8 in theory).
2. **"A load of 0.60 means the machines are 60 % busy and nobody waits."** The 0.60 counts fastest-route processing only; with real routes and changeovers the load is between 0.74 and 0.82, depending on the method, and queues form at any load because arrivals and work are variable.
3. **"MTBF is the time between two failures."** In the repository it is the time from a repair to the next failure; the time between failures is MTBF + MTTR = 140 min. Mixing the conventions changes $A$.
4. **"One simulated day shows the long-run values."** A machine-day has between 2 and 16 breakdowns and between 2.9 % and 23.9 % downtime. $A$ and $L = \lambda W$ are long-run statements.
5. **"Little's law needs Poisson arrivals or FIFO."** It needs neither. It needs care with the window: exact on one that starts and ends empty, approximate otherwise.
6. **"Events at the same time happen at the same time."** The simulator executes them one after the other in tie-breaker order, and results can depend on it (a repair and an arrival at minute 50). SimPy's order makes runs deterministic, but it is a modelling choice.

## Check your understanding {#check}

:::: qa
Try to answer each question before opening it.

::: q 1. Why does the clock of an event-driven simulator jump rather than tick?
Because the state changes only at events: between two events there is nothing to compute, so the clock moves straight to the next event time, without rounding it to a grid.
:::
::: q 2. In the repository's shop, what can be on the event list at a given moment?
The next arrival; for each machine with breakdowns, its next failure or its repair; for each running operation, the end of its current segment; for each cart on a mission, the end of its leg; and SimPy's own bookkeeping events.
:::
::: q 3. Why is only the next arrival on the list, rather than all 60?
The arrival process schedules the next arrival when the current one happens: a single pending timeout. The run is the same and the list stays short.
:::
::: q 4. A machine has been up for 100 minutes. What is the expected time to its next failure?
120 minutes, as if just repaired: the exponential up time is memoryless. Real machines wear, and their failure rate grows with age; the model ignores that.
:::
::: q 5. What does the load ρ = 0.60 leave out?
Changeovers, which depend on the sequence; routes that are not the fastest; breakdowns (85.7 % of machine time is available); and time on the carts. Measured, FIFO loads the machines at 0.82.
:::
::: q 6. Why does availability depend only on MTBF and MTTR, not on their distributions?
The long-run up fraction is $\sum U_i / \sum (U_i + D_i)$, and by the law of large numbers each sum divided by $n$ tends to its mean. Only $E[U]$ and $E[D]$ survive the limit.
:::
::: q 7. CP-SAT has a mean flow time of 124.9 min, FIFO 157.4 min, on the same 60 orders a day. How much less work in progress does CP-SAT keep?
A day starts and ends empty, so the area under $N(t)$ is $nW$: $60 \times 124.9 = 7{,}494$ job-minutes against 9,444, 21 % fewer; as day averages $nW/C_{\max}$, 5.69 against 7.15 jobs. The nominal $\lambda W$, 6.00 against 7.56, overstates both, because each day drains out after its last arrival.
:::
::: q 8. Why does the simulator leave every decision to a controller?
So that every method runs on the same model and scenario and only the decisions differ.
:::

:::: exercise Only the exponential is memoryless
Let $X \ge 0$ be continuous with $P(X > s + t \mid X > s) = P(X > t)$ for all $s, t \ge 0$ and $P(X > t) > 0$ for all $t$. Prove that $X$ is exponential. Then compute $P(X > 30 \mid X > 10)$ for the workshop's gaps.
::: hint
With $g(t) = P(X > t)$ the property is $g(s + t) = g(s)\, g(t)$. Find $g$ on the rationals, then use that $g$ is monotone.
:::
::: solution
By induction $g(nt) = g(t)^n$, so $g(1) = g(1/q)^q$ and $g(p/q) = g(1)^{p/q}$ for integers $p, q > 0$. Write $g(1) = e^{-\lambda}$; $\lambda$ is finite since $g(1) > 0$, and positive since $g(1) = 1$ would give $g = 1$ on the rationals, $X = \infty$. So $g(r) = e^{-\lambda r}$ for every rational $r \ge 0$. A survival function is nonincreasing: for rationals $r_1 < t < r_2$, $e^{-\lambda r_2} \le g(t) \le e^{-\lambda r_1}$, and letting $r_1, r_2 \to t$ gives $g(t) = e^{-\lambda t}$.
For the workshop, $P(X > 30 \mid X > 10) = P(X > 20) = e^{-20/20.83} = 0.383$.
:::

:::: exercise The first of several clocks
Let $X_1, \dots, X_k$ be independent exponentials with rates $\lambda_1, \dots, \lambda_k$, $M = \min_i X_i$ and $\Lambda = \sum_i \lambda_i$. Prove that $M$ is exponential with rate $\Lambda$ and that $P(M = X_i) = \lambda_i / \Lambda$. Then: (a) with all five machines up, when does the next breakdown come, and on which machine? (b) If orders arrived twice as often, what would $\rho$ be?
::: hint

$P(M > t) = \prod_i e^{-\lambda_i t} = e^{-\Lambda t}$, and $P(M = X_i) = \int_0^\infty \lambda_i e^{-\lambda_i x} \prod_{j \ne i} e^{-\lambda_j x} \, dx = \lambda_i \int_0^\infty e^{-\Lambda x} dx = \lambda_i / \Lambda$.

(b) Arrivals merge just as clocks do: doubling $\lambda$ halves the mean gap to 10.42 min and gives $\rho = 62.5/(10.42 \times 5) = 1.20 > 1$. The machines cannot keep up even without changeovers or breakdowns, and the queue grows for as long as orders come; no dispatching rule fixes a load above one.

## The chapter on one page {#summary}

::: steps
- **Why simulate**: the simulated shop replays the same day under every method, in 5.8 ms under a rule.
- **Event-driven**: pop the earliest event from the list, run its routine, schedule and cancel consequences. Paint example: 13 events for 108 minutes; a real day, 1,680 events on 613 of 1,384 minutes.
- **Poisson arrivals**: exponential gaps, mean and standard deviation $1/\lambda = 20.83$ min; memoryless; merging adds rates, splitting multiplies them by the label's probability. Test days: mean gap 20.14 (standard error 0.60).
- **Load**: $\rho = \lambda E[w]/m = 62.5/(20.83 \times 5) = 0.60$ for fastest routes without changeovers, a lower bound on the busy fraction; FIFO's real load is 0.82.
- **Breakdowns**: an alternating renewal process, $A = E[U]/(E[U] + E[D]) = 120/140 = 0.857$, 10.0 breakdowns per machine in 1,400 min; measured 13.9 % downtime and 9.78 breakdowns.
- **Little's law**: $L = \lambda W$, exact on a window that starts and ends empty; a day holds 9,444 job-minutes under FIFO and 7,494 under CP-SAT, day averages of 7.15 and 5.69 jobs. The nominal $\lambda W$ (7.56 for FIFO) overstates a day that drains out.
- **SimPy and the repository**: processes are generators, timeouts waits, interrupts breakdowns; `make_scenario` draws the inputs, `Shop` plays them, the controller decides.
:::

### The vocabulary, in one table

| Word | Meaning |
|---|---|
| Discrete-event simulation | A model whose state changes only at events; the clock jumps from one to the next. |
| Event list | Priority queue of future events keyed by time, with a tie-breaker. |
| Poisson process, rate $\lambda$ | Independent exponential gaps of mean $1/\lambda$; counts in a window are Poisson. |
| Memoryless | $P(X > s+t \mid X > s) = P(X > t)$; only the exponential has it. |
| Superposition, thinning | Merging independent Poisson streams adds rates; random labels split a stream into Poisson streams. |
| Load $\rho$ | $\lambda E[w]/m$: work brought per minute over capacity per minute. |
| MTBF, MTTR, availability $A$ | Mean up time, mean repair time, long-run up fraction MTBF/(MTBF + MTTR). |
| Alternating renewal process | Independent, identically distributed up-down cycles. |
| Little's law | $L = \lambda W$: work in progress equals arrival rate times flow time. |
| Process, timeout, interrupt | SimPy's generator telling one actor's story; a fixed wait; an exception thrown into a waiting process. |
| Controller interface | `route`, `sequence`, `on_event`: the only places a decision enters the simulation. |

**Scope.** This is a *terminating* simulation: a day starts empty and ends when the 60th job leaves, so runs are compared day against day, not with a steady state. Breakdowns ignore age and workload, repairs need no resource, and every distribution was chosen, not fitted to data. Law [[ref:1]] covers what a real study would add: input modelling, warm-up and output analysis.
