Arrays and the numbers inside them

Before JAX can compile, differentiate or vectorise anything, it has to store numbers. This chapter is about that storage. It covers what a JAX array is and why it cannot be changed in place, how arrays of different shapes combine in the repository's own filter code, and what a 32-bit float, JAX's default, actually holds, bit by bit. The running example is the simplest numerical experiment there is: add 0.1 ten million times. In float32 a plain loop gets 1 087 937. By the end you can explain why, and you can predict the unscented filter's failure in chapter 02 before you get there.

Part 0

Part I in one table

The Kalman chapters that follow use JAX the way working code does: arrays updated with .at, functions compiled with jit, Jacobians from jacfwd, sigma points pushed through vmap, the whole recursion run as a scan, and a network trained with Optax. Part I teaches each of those as a computer-science idea first, with the Kalman code as the place it pays off.

JAX in one paragraph. JAX is a Python library with a NumPy-like interface, jax.numpy, whose programs can be transformed: compiled by the XLA compiler for a CPU, GPU or TPU (jit), differentiated (grad), vectorised (vmap) [1]. The transformations work by tracing your function with stand-in values and rewriting the result. That puts two demands on your code. The data must be arrays whose shapes and types are known, and the functions must be pure, with no hidden state and no in-place changes. This chapter covers the first demand; J2 covers the second.

Part 1

A JAX array

Making one. jax.numpy, imported as jnp by convention, mirrors NumPy's functions, and its arrays print like NumPy's with the type spelled out:

import jax
import jax.numpy as jnp

x = jnp.array([1.0, 2.0, 3.0])
x                                   # Array([1., 2., 3.], dtype=float32)
x.shape, x.dtype, x.ndim, x.size    # ((3,), dtype('float32'), 1, 3)
x.devices()                         # {CpuDevice(id=0)}

Three properties describe every array. The shape is a tuple of lengths, one per axis: (3,) is a vector, (2, 2) a matrix, () a single number. The dtype is the type of every element, the same for all of them. Here it is float32, although NumPy would have chosen float64 for the same line; Part 4 explains. The device is where the memory lives: a CPU here, or a GPU's or TPU's own memory. An array on an accelerator is not in the computer's main memory, and converting it to NumPy with np.asarray(x) copies it back.

You cannot change it. A NumPy array can be modified in place. A JAX array cannot:

x[0] = 10.0
TypeError: JAX arrays are immutable and do not support in-place item assignment.
Instead of x[idx] = y, use x = x.at[idx].set(y) or another .at[] method: ...

The replacement returns a new array and leaves the old one alone:

x.at[0].set(10.0)          # Array([10.,  2.,  3.], dtype=float32)
x                          # Array([1., 2., 3.], dtype=float32): unchanged
x.at[1].add(5.0)           # Array([1., 7., 3.], dtype=float32)
x.at[::2].multiply(2.0)    # Array([2., 2., 6.], dtype=float32)

The repository uses exactly this to set the centre weight of the unscented filter: Wm = Wm.at[0].set(lambda_ / scale). Reassigning the name is the idiom. The array Wm pointed to before still exists, unchanged, until nothing refers to it.

Immutability

In plain words: once an array is made, its contents never change; "changing" it means making a new one.

More precisely: JAX's transformations trace a function and record every operation on its arrays as a graph of values. An in-place write would make one name stand for two different values at different moments, and the recorded graph would no longer match the program. With immutable arrays, every value is computed once from earlier values, which is what a compiler and a differentiator need. J2 makes this concrete.

Is it slow?
Outside compiled code, .at[...].set does copy. Inside a function compiled with jit, JAX's documentation states that such updates are applied in place when the compiler can see that the old array is never used again; an array passed in as an argument is still copied unless its buffer is donated with donate_argnums [4].
Functional update
The general name for "return a modified copy". Python's tuples and strings work the same way.

Indexing out of bounds does not raise. In NumPy, np.arange(5)[10] raises IndexError: index 10 is out of bounds for axis 0 with size 5. In JAX:

jnp.arange(5)[10]               # Array(4, dtype=int32): clamped to the last element
jnp.arange(5).at[10].set(99)    # Array([0, 1, 2, 3, 4], dtype=int32): the write is dropped

This is deliberate. Compiled code on an accelerator has no way to stop and raise a Python exception halfway through, so JAX defines an answer instead. By default, out-of-bounds reads are clipped to the nearest valid index and out-of-bounds writes are dropped [4]. It is safer than C, where the program in chapter 05 read 199 cells past the end of an array and got whatever memory held. But the result is still wrong without any error, so an index computed from data must be checked by you.

Part 2

Shapes and broadcasting

Elementwise and matrix operations. +, -, *, / act element by element; @ is the matrix product; jnp.outer(a, b) is the matrix of all products a_i b_j; reductions such as jnp.sum(a, axis=0) add along one axis and remove it. A product (2, 3) @ (3, 4) has shape (2, 4), and a vector times a matrix, (3,) @ (3, 2), has shape (2,).

Broadcasting is the rule that lets an elementwise operation combine arrays of different shapes without copying data [5]. Line the two shapes up from the right. Pad the shorter one on the left with axes of length 1. Then along each axis the two lengths must be equal, or one of them must be 1, and an axis of length 1 is stretched to match the other. If neither rule holds on some axis, the operation fails. None in an index inserts a new axis of length 1, which is how you ask for stretching along a particular direction.

The unscented filter is built from these rules. Its sigma points are a (5, 2) array, five points with two coordinates each, and its weights a (5,) vector. The checker below is preloaded with the operations kalman_jax/filters.py performs. Try them, then try your own.

The failing preset is worth seeing as JAX reports it, because it is the most common shape bug in code like this:

Wm, points = jnp.ones(5), jnp.ones((5, 2))
Wm * points
ValueError: Incompatible shapes for broadcasting: shapes=[(5,), (5, 2)]

Lined up from the right, the weights' 5 meets the points' 2. Wm[:, None] turns the weights into a (5, 1) column, which stretches across the two coordinates so that weight i multiplies row i; jnp.sum(..., axis=0) then adds the five rows into the (2,) weighted mean. The covariance does the same one level up: Wc[:, None, None] is (5, 1, 1), the five outer products are (5, 2, 2), and summing over axis 0 leaves the (2, 2) covariance.

Part 3

What a float stores

Binary fractions. A computer stores numbers in base 2. A fraction has a finite binary expansion only if its denominator is a power of two: 0.75 = \tfrac12 + \tfrac14 is 0.11 in binary, exact. 0.1 = \tfrac{1}{10} is not, because 10 has a factor 5: in binary it is 0.000110011001100… with 1100 repeating forever, just as \tfrac13 never ends in decimal. A float keeps a fixed number of binary digits and rounds the rest.

The format. The IEEE 754 standard [2], which every current CPU and GPU follows, writes a number as a sign, a power of two and a significand between 1 and 2:

x = (-1)^{s} \times 1.f \times 2^{\,e - \text{bias}}, \qquad \text{float32: } 1 + 8 + 23 \text{ bits, bias } 127, \qquad \text{float64: } 1 + 11 + 52 \text{ bits, bias } 1023.

The leading 1 of the significand is not stored, since it is always 1, so a float32 has 24 significant bits and a float64 has 53. The demo at the top shows the three fields. For 0.1 in float32 the sign is 0, the exponent field is 123, meaning 2^{123-127} = 2^{-4}, and the fraction is 10011001100110011001101: the repeating pattern, cut off and rounded up in the last place. What is stored is exactly

0.100000001490116119384765625 \quad (\text{float32}), \qquad 0.1000000000000000055511151231257827\ldots \quad (\text{float64}).

Neither is 0.1. Every arithmetic result is rounded the same way, to the nearest representable number, with ties going to the one whose last bit is 0.

The gap grows with the number. Because the significand has a fixed number of bits, the spacing between neighbouring floats is a fixed fraction of their size. It doubles at every power of two:

Read the table as a precision budget. A float32 resolves about one part in 2^{23} \approx 8.4 million, about 7 decimal digits, whatever the size of the number; a float64 about 16. Two consequences follow.

Integers stop being exact. Up to 2^{24} = 16\,777\,216 every whole number is a float32. Above it, the gap is 2, and 16 777 217 is stored as 16 777 216. Type it into the demo. In float64 the same happens above 2^{53} \approx 9 \times 10^{15}.

"Equal" is fragile. 0.1 + 0.2 == 0.3 is False in float64, where the sum is 0.30000000000000004, and True in float32. Float32 is not more accurate: it happens that the two roundings land on the same float32. Compare floats with a tolerance, such as jnp.allclose, never with ==.

Machine epsilon and the unit roundoff

In plain words: the smallest relative step a format can take; every stored number and every arithmetic result is wrong by at most half of it, relatively.

More precisely: machine epsilon is the gap between 1 and the next float: \varepsilon = 2^{-23} \approx 1.19 \times 10^{-7} for float32 and 2^{-52} \approx 2.2 \times 10^{-16} for float64. Rounding to nearest gives a relative error of at most the unit roundoff u = \varepsilon/2: \mathrm{fl}(a \circ b) = (a \circ b)(1 + \delta) with |\delta| \le u, for each of +, -, \times, \div [3]. That one inequality is the model of all the error analysis in this course.

Range
float32 reaches about 3.4 \times 10^{38}; beyond, results become inf. Normal numbers go down to 1.2 \times 10^{-38}, and subnormals, which give up leading bits, down to 1.4 \times 10^{-45}. Below that, results become 0.
Special values
inf from overflow and from 1/0; nan, "not a number", from 0/0, sqrt(-1) and inf - inf. A NaN is not equal even to itself.
Part 4

JAX's dtypes and its 32-bit default

Float32 unless you ask. NumPy's default float is float64. JAX's is float32, and its default integer is int32 instead of NumPy's int64. Accelerators process 32-bit numbers faster than 64-bit ones, often much faster on GPUs, and they halve the memory. For training neural networks, 7 digits are plenty. For numerical algorithms that cancel large terms, they may not be, as chapter 02 shows. The switch is global and must be set at startup, before any array is created:

jax.config.update("jax_enable_x64", True)   # or the environment variable JAX_ENABLE_X64=1
jnp.array(1.0).dtype                         # float64 from now on

Conversions are silent. Without the switch, a float64 array from NumPy is converted to float32 with no message at all:

import numpy as np
jnp.asarray(np.array([0.1])).dtype        # dtype('float32'): 9 digits dropped, no warning
jnp.array([0.1], dtype=jnp.float64)       # float32 too, but this one warns:
UserWarning: Explicitly requested dtype float64 requested in array is not available,
and will be truncated to dtype float32. To enable more dtypes, set the jax_enable_x64
configuration option or the JAX_ENABLE_X64 shell environment variable. ...

So data you prepared carefully in float64 with NumPy or pandas becomes float32 the moment it enters JAX, unless you have turned 64-bit on.

Weak types: Python numbers do not change the dtype. When an array meets a Python scalar, the array's dtype wins. JAX calls the scalar weakly typed [6]. Two arrays of different dtypes promote to the wider one:

(jnp.ones(3, jnp.float16) + 1.0).dtype                      # float16: the Python float adapts
(jnp.ones(3, jnp.float16) + jnp.ones(3, jnp.float32)).dtype  # float32: two arrays promote
(jnp.ones(3, jnp.int32) * 2.5).dtype                         # float32: an int array times a float

This is why 2.0 * x never silently doubles the memory of a float32 array, and why the repository's jnp.eye(state_dim, dtype=P.dtype) asks for the covariance's own dtype, so that a float64 filter stays float64 throughout.

Integers wrap around. An int32 holds -2^{31} to 2^{31} - 1. Past the top it wraps to the bottom without an error. A Python integer that does not fit is refused when the array is made:

jnp.int32(2**31 - 1) + 1     # Array(-2147483648, dtype=int32)
jnp.array(2**31)             # OverflowError: Python int 2147483648 too large to convert to int32

Smaller floats. Machine learning also uses 16-bit floats: float16, with machine epsilon 9.8 \times 10^{-4} and a largest value of 65 504, and bfloat16, which keeps float32's exponent range but only 8 significant bits (epsilon 7.8 \times 10^{-3}). Neither is used in this course; both make everything in Part 5 thousands of times worse: about 8 000 times for float16 and 65 000 times for bfloat16.

Part 5

Rounding in arithmetic

Each operation's error is tiny, at most u relative. Three things make the total large.

1. Order matters. Floating-point addition is commutative but not associative. In float32, near 10^8 the gap is 8, so:

a, b, c = np.float32(1e8), np.float32(1.0), np.float32(-1e8)
(a + b) + c      # 0.0: 1e8 + 1 rounds back to 1e8
(a + c) + b      # 1.0

The same numbers added in a different order give different answers. A compiler that reorders a sum, as XLA may, can change its result.

2. Cancellation exposes old errors. Subtracting nearly equal numbers is itself exact, but the result keeps the rounding errors of its inputs, which are now large compared with what is left. In float32, (1 + 1e-7) - 1 gives 1.19 \times 10^{-7}, not 10^{-7}: a 19% error from one addition and one subtraction, because 1 + 10^{-7} had to be stored as the nearest float32, 1 + 2^{-23}.

3. Errors accumulate. A long sum rounds at every step, and the running total grows while the numbers added to it do not. Add the float32 number 0.1 to a running total, ten million times:

Relative error of the final sum against N, for four ways of adding

Why the plain loop gets 1 087 937. As long as the total is small, each addition of 0.1 is rounded by a tiny fraction of 0.1. As the total grows, so does the gap between float32s around it, and once the gap is comparable to 0.1, each addition is rounded to a whole number of gaps. Between 262 144 and 524 288 the gap is 0.03125, and 0.1 becomes 0.09375: too little. Between 524 288 and 2 097 152 the gap is 0.0625 and then 0.125, and 0.1 becomes 0.125 either way: a quarter too much on every addition. The total is wrong by 8.8% and no single operation broke a rule.

The remedies. jnp.sum does not add one number at a time: the compiled reduction combines partial sums, so totals stay comparable in size to what is added to them. It gets 1 000 000.06. Kahan's compensated summation [7] keeps a second variable for the part of each addition that rounding threw away and adds it back on the next step. In float32 it gets exactly 1 000 000, the nearest float32 to the true sum of the stored values:

def kahan_sum(values):
    total, lost = 0.0, 0.0
    for v in values:
        y = v - lost              # put back what was lost last time
        t = total + y             # big + small: the low bits of y are rounded away...
        lost = (t - total) - y    # ...and recovered exactly here
        total = t
    return total

And float64 simply has 29 more bits to lose: its plain loop ends at 999 999.99984, a relative error of 1.6 \times 10^{-10}.

Checked against JAX. The page computes the float32 loop and Kahan's loop itself, rounding after every operation with Math.fround; both match JAX's lax.fori_loop results, computed by code/j1_numbers.py and stored in interactive/j1-data.js, bit for bit at every N. The jnp.sum values are JAX's own; the page does not reimplement XLA's reduction.

Part 7

Check your understanding

1. Why does x[0] = 1.0 fail on a JAX array, and what do you write instead?

JAX arrays are immutable, so that a traced function's values each have one definition and the compiler and differentiator can treat the program as a graph of values. Write x = x.at[0].set(1.0), which returns a new array; inside jit it is performed in place, without a copy, when the old array is not used again.

2. jnp.arange(5)[10] returns 4. Why does JAX not raise an IndexError as NumPy does?

Compiled code on an accelerator cannot stop and raise in the middle of a computation, so JAX defines a result instead: out-of-bounds reads are clipped to the last valid index and out-of-bounds writes are dropped. No error is reported, so indices computed from data must be checked by the programmer.

3. Why does Wm * points fail for shapes (5,) and (5, 2) while Wm[:, None] * points works?

Broadcasting aligns shapes from the right, so the weights' 5 meets the points' 2: neither is 1, error. Wm[:, None] has shape (5, 1): now 5 meets 5 and 1 meets 2, which stretches, giving (5, 2) with weight i on row i.

4. Is float32 more accurate than float64, since 0.1 + 0.2 == 0.3 is true only in float32?

No. Neither format stores 0.1, 0.2 or 0.3 exactly. In float32 the rounded sum happens to land on the same float as the rounded 0.3; in float64 it lands one float above (0.30000000000000004). The lesson is not to compare floats with ==.

5. jnp.asarray(np.array([0.1])) has dtype float32. What happened, and why was there no warning?

With 64-bit disabled, JAX converts float64 input to float32, rounding away about nine significant digits. It warns only when float64 is requested explicitly with dtype=; converting existing data is silent. Enable jax_enable_x64 at startup if the digits matter.

6. Why does a float32 loop that adds 0.1 ten million times end at 1 087 937?

The gap between float32s grows with the running total. Once it is comparable to 0.1, every addition is rounded to a whole number of gaps: between 524 288 and 2 097 152 that is 0.125 per addition instead of 0.1. The total overshoots by 8.8%, though each operation was correctly rounded.

7. What does Kahan's second variable hold, and why does it help?

The part of each addend that was rounded away when it was added to the large total, recovered exactly as (t - total) - y. Adding it back on the next step means the lost low-order bits are not lost for good, and the error no longer grows with N.

8. How would you run the repository's filter in float64, and what does it cost?

Call jax.config.update("jax_enable_x64", True) before creating any array; the filter's code needs no change, since it builds its matrices with the input's dtype. The costs are twice the memory and bandwidth, much slower arithmetic on many GPUs, and a setting that applies to the whole program.

    Above 2^p the gap is 2, so 2^p + 1 is the first casualty: 2^{24} + 1 = 16\,777\,217 for float32 and 2^{53} + 1 = 9\,007\,199\,254\,740\,993 for float64.

  3. Kahan's loop in JAX. Write the compensated sum of 0.1, N times, in float32 with jax.lax.fori_loop, and compare it with a plain fori_loop for N = 10^7. (fori_loop(lower, upper, body, init) runs body(i, carry) for each i and returns the final carry; J5 explains why JAX wants loops written this way.)
    Hint

    The carry is the pair (total, lost). Make every constant a jnp.float32 so nothing is promoted.

    Solution

    The plain loop gives 1087937.0 and the compensated loop 1000000.0.

    from jax import lax

@jax.jit
def plain(n):
    return lax.fori_loop(0, n, lambda i, s: s + jnp.float32(0.1), jnp.float32(0.0))

@jax.jit
def kahan(n):
    def body(i, carry):
        total, lost = carry
        y = jnp.float32(0.1) - lost
        t = total + y
        return t, (t - total) - y
    return lax.fori_loop(0, n, body, (jnp.float32(0.0), jnp.float32(0.0)))[0]

print(float(plain(10_000_000)), float(kahan(10_000_000)))    # 1087937.0 1000000.0
  4. Predict chapter 02's failure. The unscented filter with \alpha = 10^{-3} computes its predicted position as -999\,999\, p_0 + 250\,000\,(p_1 + p_2 + p_3 + p_4), where the p_i are five float32 positions near 33. Estimate how wrong the result can be, from two sources: the rounding of the terms, and the rounding of the positions themselves.
    Hint

    Use the gap table. How large are the terms, and how far apart are float32s at that size? And how far apart are float32s near 33, multiplied by the weights?

    Solution

    The terms are about 3.3 \times 10^7, where float32s are 2 apart (np.spacing(np.float32(999999 * 33.0)) is 2.0), so each term is rounded by up to 1.   5. A jitter that works. _sigma_points adds 10^{-9} to the covariance's diagonal before the Cholesky factorisation. How large must a jitter be to change a float32 variance of 1? Of 0.5? Suggest a jitter that scales with the matrix.
    Hint

    An addition changes a number only if it exceeds half the gap at that number. The gap just above 1 is 2^{-23}.

    Solution

    Half the gap above 1 is 2^{-24} \approx 6 \times 10^{-8}, so 10^{-7} changes a variance of 1 and 5 \times 10^{-8} does not. Above 0.5 the gap is 2^{-24}, so the threshold is about 3 \times 10^{-8}. A jitter proportional to the matrix, for example 10^{-6} times the mean diagonal, keeps the same relative effect at every scale and in both precisions.

    np.float32(1.0) + np.float32(1e-7) == np.float32(1.0)    # False: changed
np.float32(1.0) + np.float32(5e-8) == np.float32(1.0)    # True: lost
np.float32(0.5) + np.float32(1e-9) == np.float32(0.5)    # True: the repository's jitter
Part 9

The chapter on one page

  1. A JAX array has a shape, one dtype and a device. It is immutable: x.at[i].set(v) returns a new array, and inside jit the update can be done in place when the old array is not used again. Out-of-bounds reads are clipped and writes dropped, without an error.
  2. Broadcasting: align shapes from the right, pad with 1s, and stretch length-1 axes; None adds such an axis. Wm[:, None] * points weights each row; Wm * points fails.
  3. A float is sign × 1.fraction × 2exponent: 24 significant bits in float32, 53 in float64. 0.1 is not representable. The gap between neighbours is a fixed fraction of their size: 2 near 33 million in float32.
  4. JAX defaults to float32 and int32, converts float64 input silently, lets arrays win over Python scalars (weak types), and wraps integers on overflow. jax_enable_x64 switches the whole program to 64-bit.
  5. Rounding: each operation is wrong by at most u = 2^{-24} relative in float32. Order matters, cancellation exposes earlier errors, and long sums accumulate them: adding 0.1 ten million times gives 1 087 937 in a float32 loop, 1 000 000.06 with jnp.sum, 1 000 000 with Kahan's loop.
  6. In the Kalman code: the sigma points are built by broadcasting, the weights by a functional update, the jitter of 10^{-9} vanishes in float32 for variances above 1/32, and weights of a million times positions near 33 put the mean in a range where float32 counts in steps of 2.

Part 10

Scope and further reading

Scope. This chapter covers JAX arrays, their immutability and indexing, broadcasting, the IEEE 754 binary formats, JAX's dtype defaults and promotion, and the basic mechanisms of rounding error, enough to read the array code of the Kalman chapters and to understand chapter 02's numerical failure. It does not cover sharding arrays across devices, sparse arrays, error analysis of matrix algorithms such as the Cholesky factorisation, which [3] treats in depth, or mixed-precision training.
