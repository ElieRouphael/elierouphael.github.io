Pure functions, tracing and jit

J1 was about the data; this chapter is about the code. When you wrap a function in jax.jit, JAX does not run it on your numbers. It runs it once on stand-ins that carry only a shape and a dtype, records every operation into a small program, and hands that program to a compiler. That one idea explains what surprises people about JAX: a print that fires only once, a global variable whose new value is ignored, an if that raises an error. It also explains why one predict-and-update step of the Kalman filter takes 421 µs uncompiled and 13 µs compiled. The demo below runs the trace one line at a time.

    Part 1
    
Pure functions

  

  

    
A function is pure when its result depends only on its arguments, and calling it does nothing except return that result. def f(x): return 2 * x + 1 is pure. Each of these is not:

    
def shout(x):
    print("x is", x)        # writes to the terminal
    return x

def scaled(x):
    return scale * x        # reads a global

def remember(x):
    history.append(x)       # changes a list outside
    return x

def noisy(x):
    return x + np.random.normal()   # reads and advances a hidden state

    
A pure call can be replaced by its value without changing the program: f(3) and 7 mean the same thing. This property, referential transparency, is what gives a compiler room to work. It may compute f(3) once and reuse the result, which is called memoization [7]. It may reorder independent calls, run them in parallel, fuse them, or drop a call whose result is never used. None of that is safe for shout, whose output would then appear once, twice or never.

    
JAX's transformations are all of this kind. jit compiles a function once and reuses the compiled code; grad (J3) builds a new function that computes a derivative; vmap (J4) runs a function on a batch. Each assumes that the function's arguments are its only inputs and its return value its only output. JAX does not check this. Part 4 shows what happens when it is not true: there is usually no error, only a wrong answer.

    
The repository is written this way. Every step function in kalman_jax/filters.py carries a docstring that says so, for example """Pure function for the linear Kalman-filter prediction step.""". The filter's state goes in as arguments and comes out as return values; nothing is stored between calls. Compare the object-oriented style common in other Kalman libraries, where the state lives inside an object and each step changes it:

    
# object-oriented: the state lives in the object, and predict() changes it
class KalmanFilter:
    def predict(self):
        self.x = self.F @ self.x
        self.P = self.F @ self.P @ self.F.T + self.Q

# functional, as in kalman_jax/filters.py: the state goes in and comes out
def linear_kf_predict(x, P, F, Q):
    x_pred = F @ x
    P_pred = F @ P @ F.T + Q
    return x_pred, P_pred

    
The two compute the same numbers. Only the second can be compiled, differentiated and batched by JAX, because only the second says, in its signature, everything it reads and everything it produces.

    

      
Pure function

      
In plain words: same inputs, same output, and no other effects.

      
More precisely: a function is pure if its return value is determined by its arguments alone and evaluating it has no observable side effect. A call to a pure function is referentially transparent: it can be replaced by its value anywhere in a program without changing the program's meaning [6].

      

        
Side effect
Anything a call does besides returning its value: printing, writing a file or a global variable, changing an argument in place, advancing a random number generator.

        
Why J1 mattered
JAX arrays are immutable, so a function cannot change its argument in place. Half of purity is enforced by the array type; the other half, globals and I/O, is up to you.

      

    

  







  

    Part 2
    
Tracing: running a function on stand-ins

  

  

    
What jit does on the first call. jax.jit(f) returns a new function. When you call it, it does not pass your arrays to f. It replaces each argument with a tracer, an object that carries the argument's shape and dtype but no values, and calls f on the tracers. Python then runs f's body as usual, line by line. Every jnp operation that receives a tracer does not compute anything: it records an equation, "this primitive applied to these inputs gives an output of this shape and dtype", and returns a new tracer for the output. When f returns, the recorded equations are the program. JAX calls it a jaxpr [1].

    
You can see it without compiling anything, with jax.make_jaxpr. Here is the repository's prediction step:

    
jax.make_jaxpr(linear_kf_predict)(x0, P0, F, Q)

    
{ lambda ; a:f32[2] b:f32[2,2] c:f32[2,2] d:f32[2,2]. let
    e:f32[2] = dot_general[
      dimension_numbers=(([1], [0]), ([], []))
      preferred_element_type=float32
    ] c a
    f:f32[2,2] = dot_general[
      dimension_numbers=(([1], [0]), ([], []))
      preferred_element_type=float32
    ] c b
    g:f32[2,2] = transpose[permutation=(1, 0)] c
    h:f32[2,2] = dot_general[
      dimension_numbers=(([1], [0]), ([], []))
      preferred_element_type=float32
    ] f g
    i:f32[2,2] = add h d
  in (e, i) }

    
Reading a jaxpr. The first line names the inputs and their types: a to d are x, P, F and Q, with f32[2] meaning a float32 vector of length 2. Each following line is one primitive operation, its output's name and type on the left. F @ x became e = dot_general c a, a general matrix product whose parameters say which axes are summed: axis 1 of F against axis 0 of x. F @ P @ F.T + Q became four equations, one per operator, in Python's evaluation order. The last line lists the outputs: (e, i) is (x_pred, P_pred).

    
What is missing is as instructive as what is there. The names x_pred and P_pred are gone, and so is the docstring. A helper function called from f would leave no trace either: its operations would simply appear in the list. A Python for loop would leave one copy of its body per iteration. Python numbers would appear as constants such as 2.0:f32[]. Everything that Python decided while tracing is fixed in the program; only the array operations remain.

    
The form of the program matters too. Each variable is assigned exactly once and never changed. Compilers call this static single assignment form [5], and it is the form in which they analyse and optimise code: every use of a value points to the one place it was defined. J1's immutable arrays are what let JAX produce it directly.

    

      
Tracing

      
In plain words: running a program on descriptions of values instead of values, and writing down what it does.

      
More precisely: each argument is replaced by a tracer whose abstract value is a shape and a dtype, a ShapedArray. JAX's operations are defined on tracers too: given abstract inputs, they compute the abstract output and record the operation. Evaluating a program over abstract values rather than concrete ones is known in programming-language theory as abstract interpretation [4]; JAX uses it to extract the program [2].

      

        
Tracer
The stand-in object. Printing one inside jit shows JitTracer(float32[2]): a shape and dtype, no numbers.

        
Primitive
One of the basic operations JAX knows how to compile and differentiate: add, dot_general, transpose, cholesky, and many more. Every jnp function is built from them.

        
jaxpr
The recorded program: typed inputs, a list of primitive equations in single-assignment form, and outputs.

      

    

    
The demo at the top runs this trace one line at a time. Step through linear_kf_predict and watch which line produces which equation. Then press Call it again: the function's Python body does not run a second time.

  







  

    Part 3
    
Compiling and caching

  

  

    
Three stages. The first call of a jitted function goes through three stages, and JAX lets you run them one at a time:

    
traced = jax.jit(kf_step).trace(x0, P0, z, F, H, Q, R)   # 1. trace: Python runs, a jaxpr is recorded
lowered = traced.lower()                                 # 2. lower: the jaxpr is translated to StableHLO
compiled = lowered.compile()                             # 3. compile: XLA optimises it and emits machine code
compiled(x0, P0, z, F, H, Q, R)                          # run

    
Here kf_step is one predict-and-update step of chapter 02's filter, with every matrix passed as an argument. The jaxpr is translated, or lowered, into StableHLO, a representation of array programs that compilers for different hardware share. For the prediction step it reads much like the jaxpr (the body of the module, as JAX prints it):

    
%0 = stablehlo.dot_general %arg2, %arg0, contracting_dims = [1] x [0], precision = [DEFAULT, DEFAULT] : (tensor<2x2xf32>, tensor<2xf32>) -> tensor<2xf32>
%1 = stablehlo.dot_general %arg2, %arg1, contracting_dims = [1] x [0], precision = [DEFAULT, DEFAULT] : (tensor<2x2xf32>, tensor<2x2xf32>) -> tensor<2x2xf32>
%2 = stablehlo.transpose %arg2, dims = [1, 0] : (tensor<2x2xf32>) -> tensor<2x2xf32>
%3 = stablehlo.dot_general %1, %2, contracting_dims = [1] x [0], precision = [DEFAULT, DEFAULT] : (tensor<2x2xf32>, tensor<2x2xf32>) -> tensor<2x2xf32>
%4 = stablehlo.add %3, %arg3 : tensor<2x2xf32>

    
Then the XLA compiler [3] optimises the whole program at once, which it can do because it sees all of it. In the compiled code for the prediction step, the transpose is gone (three lines of XLA's output, with layout annotations and metadata removed):

    
%dot_general.4 = f32[2,2] dot(%F.1, %P.1), lhs_contracting_dims={1}, rhs_contracting_dims={0}
%dot_general.5 = f32[2,2] dot(%dot_general.4, %F.1), lhs_contracting_dims={1}, rhs_contracting_dims={1}
%wrapped_add   = f32[2,2] fusion(%dot_general.5, %Q.1), kind=kLoop, calls=%wrapped_add_computation

    
The second product sums over axis 1 of F instead of axis 0 of F^\top, which computes (FP)F^\top without ever building F^\top. The addition of Q has become a fusion, a loop XLA generates itself. On a GPU, fusing a chain of elementwise operations into one kernel saves a round trip to memory per operation, and that is often most of the speed-up from jit.

    
What it costs. On the laptop CPU used for this page, compiling kf_step for the first time took 23 ms to trace, 23 ms to lower and 66 ms to compile: about 0.11 s before the first result. Each later call took 13 µs. Compilation is paid once, and the result is cached.

    
The cache key. A jitted function keeps a cache of compiled programs. The key is what JAX can see at the call: the function itself, and for each argument its shape, its dtype, whether it is weakly typed (J1, Part 4), and the structure of nested containers such as tuples. Values the body reads from elsewhere, such as globals, are not part of it (Part 4). The values in the arrays are not part of the key, because the trace never saw them. So a call with new values of the same shapes reuses the compiled program; a call with a new shape or dtype traces and compiles again. The demo below is the jitted kf_step, with the timings measured for each stage. Make some calls and watch the cache.

The practical rule: keep shapes and dtypes stable across calls. A training loop that feeds batches of varying length, or a filter run on sequences of different lengths, compiles once per length. Padding to a few fixed sizes is the usual cure.

    
Asynchronous dispatch. A call to a compiled function returns as soon as the work has been handed to the device, before the result exists. Python can then queue more work while the device computes. The returned array is a placeholder that waits when you look at it. On the same laptop, A @ A for a 3000 × 3000 matrix returned in 5 ms, and the result was ready after 161 ms:

    
t0 = time.perf_counter(); C = A @ A; t1 = time.perf_counter()   # 5 ms: queued, not computed
C.block_until_ready(); t2 = time.perf_counter()                 # 161 ms: now it is done

    
Anything that needs the numbers waits for them: print(C), float(C), np.asarray(C). For timing, this means a benchmark must call .block_until_ready() on the result, or it measures only how long it took to place the order. It must also exclude the first call, which compiles. All timings on this page follow both rules.

  







  

    Part 4
    
Side effects run once

  

  

    
Tracing runs your Python once per signature. Every side effect therefore happens once per signature, at trace time, and never when the compiled program runs. JAX raises no error. These are the four cases you will meet.

    
print shows a tracer, once.

    
@jax.jit
def f(x):
    print("tracing f with", x)
    return 2.0 * x + 1.0

f(jnp.array([1.0, 2.0]))         # prints: tracing f with JitTracer(float32[2])
f(jnp.array([3.0, 4.0]))         # prints nothing: the cached program ran
f(jnp.array([1.0, 2.0, 3.0]))    # prints: tracing f with JitTracer(float32[3])

    
This is useful: a print inside a jitted function is a free counter of how often it recompiles. To see values at run time, use jax.debug.print("x = {x}", x=x), which records a print operation in the program itself; it prints x = [1. 2.], then x = [3. 4.], on every call.

    
A global is read once, and becomes a constant.

    
scale = 2.0

@jax.jit
def g(x):
    return scale * x

g(jnp.float32(1.0))     # 2.0
scale = 3.0
g(jnp.float32(1.0))     # 2.0: the jaxpr says  mul 2.0:f32[] a
g(jnp.ones(2))          # [3. 3.]: a new shape retraces, and this trace reads 3.0

    
The two calls with the same argument now disagree with the code as written, and whether you get the old or the new value depends on whether some earlier call happened to have the same shape. The cure is to pass anything that can change as an argument.

    
A tracer can escape. Storing a value outside the function stores a tracer, which is meaningless once the trace is over:

    
seen = []

@jax.jit
def h(x):
    seen.append(x)
    return x + 1

h(jnp.float32(1.0))
seen              # [JitTracer(float32[])]
seen[0] + 1

    
UnexpectedTracerError: Encountered an unexpected tracer. A function transformed by JAX had a side
effect, allowing for a reference to an intermediate value with type float32[] wrapped in a
DynamicJaxprTracer to escape the scope of the transformation. ...

    
NumPy randomness is drawn once. np.random.normal() is not a JAX operation; it runs during tracing and returns a Python number, which becomes a constant:

    
np.random.seed(0)

@jax.jit
def noisy(x):
    return x + np.random.normal()

noisy(0.0), noisy(0.0), noisy(0.0)    # 1.7640524 three times

    
JAX's own random numbers avoid this by making the generator's state an explicit argument, a key, which J6 covers. The repository's data generator takes one: generate_linear_synthetic_data(key, ...).

    Part 5
    
Control flow on values

  

  

    
The error. Python's if needs True or False now. During tracing, x > 0 is a tracer of type bool[] with no value, so the question cannot be answered:

    
@jax.jit
def relu(x):
    if x > 0:
        return x
    return 0.0 * x

relu(2.0)

    
TracerBoolConversionError: Attempted boolean conversion of traced array with shape bool[].
The error occurred while tracing the function relu at ... for jit. This concrete value was not
available in Python because it depends on the value of the argument x.

    
The program a compiler receives must be the same for every input of a given signature, so a branch that depends on a value has to be inside the program, as an operation, rather than decided by Python before the program exists. There are three ways to put it there.

    
1. Compute both and select: jnp.where. jnp.where(x > 0, x, 0.0) evaluates both alternatives for every element and keeps one, through the primitive select_n. It works on arrays of any shape and is the usual choice when both branches are cheap. Step through it in the demo at the top: the comparison and the selection are recorded, and nothing fails.

    
2. Run one branch: lax.cond. lax.cond(x > 0, lambda v: v, lambda v: jnp.zeros_like(v), x) traces both branches into the program and decides at run time which one to execute:

    
{ lambda ; a:f32[]. let
    b:bool[] = gt a 0.0:f32[]
    c:i32[] = convert_element_type[new_dtype=int32 weak_type=False] b
    d:f32[] = cond[
      branches=(
        { lambda ; e:f32[]. let  in (0.0:f32[],) }
        { lambda ; f:f32[]. let  in (f,) }
      )
    ] c a
  in (d,) }

    
The predicate must be a single boolean, and both branches must return the same shapes and dtypes, because the program's output type cannot depend on which branch runs. (The first branch's zeros_like has already been simplified to the constant 0.0.) Use it when a branch is expensive.

    
3. Make the value static: static_argnums. If the value is a configuration choice rather than data, tell jit to treat it as part of the cache key. Python then sees the real value and may branch or loop on it:

    
@partial(jax.jit, static_argnums=1)
def power(x, n):
    y = x
    for _ in range(n - 1):
        y = y * x
    return y

power(2.0, 3)    # traces with n = 3; the jaxpr is two multiplications: mul a a; mul b a
power(2.0, 3)    # cache hit
power(2.0, 5)    # traces again with n = 5

    
Every new value of n compiles a new program, so static arguments should take few distinct values. Without static_argnums, range(n - 1) fails with TracerIntegerConversionError, the integer version of the same problem.

    

      
Static and traced

      
In plain words: static things are known while the program is being written down; traced things are known only when it runs.

      
More precisely: static values are those available during tracing: Python numbers and objects the function reads or builds (literals, globals, closed-over values), the shapes and dtypes of arguments, and arguments marked with static_argnums or static_argnames. Only the shapes, dtypes and marked arguments are part of the cache key: a global is not, which is Part 4's bug, and a Python number passed as an ordinary argument is traced, as a weakly typed scalar. Traced values are the contents of array arguments and everything computed from them. Python's control flow, if, for, while, range, may depend on static values only.

      

        
Shapes are static
if x.ndim == 1: is fine inside jit, and so is jnp.eye(P.shape[0]): the repository's Joseph update builds its identity matrix that way.

        
Shapes cannot depend on values
x[x > 0] has a length that depends on the data, so it fails with NonConcreteBooleanIndexError: Array boolean indices must be concrete; got bool[3]. Keep the shape fixed and mask instead: jnp.sum(jnp.where(x > 0, x, 0.0)) gives 5.0 for [-1, 2, 3].

        
Functions are static
A function is not an array, so passing one as an ordinary argument fails with TypeError: Error interpreting argument to <function ...> as an abstract array. Mark it static; exercise 3 does this for the EKF.

      

    

  







  

    Part 6
    
Back to Kalman

  

  

    
Why one step is 33 times faster compiled. One predict-and-update step of chapter 02's filter, kf_step, is 31 primitive operations. Without jit, JAX runs them one at a time, and each pays a fixed cost to be dispatched from Python: about 13 µs here, against 0.37 µs for the same tiny addition in NumPy. Thirty-one dispatches come to about 400 µs; the measured step takes 421 µs. Compiled, the step is one dispatch of one program: 13 µs, nearly all of it the same fixed cost. For arrays this small the arithmetic itself is a rounding error; the overhead of calling is everything.

    
Running 1000 steps. Chapter 02 runs the filter over 1000 measurements. Here are six ways to do it, timed on the same laptop:

The fastest version is about 480 times faster than the slowest, and it gives the same estimates: after 1000 steps the eager loop and the compiled scan agree to 3 \times 10^{-6}, float32 rounding in a different order. J5 explains lax.scan, which turns the loop itself into one primitive so that all 1000 steps are a single program.

    
A function that recompiles on every call. The second row deserves a closer look. run_linear_kf is not jitted; it calls jax.lax.scan, which compiles its loop body before running it. That body is step, a function defined inside run_linear_kf:

    
def run_linear_kf(measurements, F, H, Q, R, x0, P0):
    def step(carry, measurement):          # a new Python function object on every call
        ...
    (_, _), estimated_states = jax.lax.scan(step, (x0, P0), measurements)
    return estimated_states

    
Each call creates a new step object, and the function itself is part of the cache key, so the cache never hits. JAX's compilation log confirms it: one XLA compilation on every call, and each call takes about 94 ms. Wrapping the whole function in jit moves the boundary outwards. The outer function is traced once per signature, the inner step is traced as part of that trace, and later calls find the compiled program in the cache: 1.2 ms.

    
For the repository's scripts this costs nothing that matters, since each runs the filter once. It would matter as soon as the filter ran in a loop, for example to tune Q over a grid of 100 values: 9.4 s instead of 0.24 s. The fix is one line, run_linear_kf = jax.jit(run_linear_kf), or the decorator @jax.jit on the definition.

    
The training loop. Chapters 03 and 04 train a model with this pattern from kalman_jax/forecasters.py:

    
@jax.jit
def update(current_params, current_opt_state):
    loss, grads = value_and_grad(forecasting_loss_fn)(current_params, A, B, C, Q, R, x0, P0, us, ys)
    ...
    return next_params, next_opt_state, loss

for step in range(num_steps):
    params, opt_state, loss = update(params, opt_state)
    losses.append(loss)
    if log_every is not None and step % log_every == 0:
        print(f"Step {step}, Forecast Loss: {float(loss):.6f}")

    
Everything in Parts 3 and 4 is visible here. update is pure in what it takes and returns: parameters and optimiser state go in and come out. It reads A, B, the data us and ys and the rest from the enclosing function, so those are captured at trace time as constants of the compiled program. That is correct here, because they do not change during training, and update is created afresh on each call to train_kalman_forecaster. Every iteration has the same signature, so the loop compiles once. losses.append(loss) stores a placeholder without waiting, so Python can queue the next step while the device finishes this one. Only float(loss), every log_every steps, makes Python wait for a result.

Next, J3 asks how JAX differentiates a function. It traces it, exactly as here, and then transforms the jaxpr.

  







  

    Part 7
    
Check your understanding

  

  

    
1. What makes a function pure, and why do JAX's transformations need it?
Its result depends only on its arguments, and calling it has no other effect. JAX runs the Python function once, on tracers, and from then on uses the recorded program in its place. That substitution is only correct if the function's arguments are its only inputs and its return value its only output, which is what purity means.

    
2. What happens, in order, on the first call of a jitted function?
Each argument is replaced by a tracer carrying its shape and dtype. The Python body runs once on the tracers, and each JAX operation records an equation: the result is a jaxpr. The jaxpr is lowered to StableHLO, compiled by XLA into machine code for the device, stored in the cache under the arguments' signature, and run on the actual arguments.

    
3. Why does print(x) inside a jitted function show JitTracer(float32[2]), and only on some calls?
print is plain Python, so it runs while the body runs, which is only during tracing, and at that moment x is a tracer with a shape and a dtype but no values. Later calls with the same signature run the compiled program, which contains no print. Use jax.debug.print to print values on every call.

    
4. A jitted function reads a global scale. You change scale and call the function again. Why is the result unchanged, and when would it change?
The global was read once, during tracing, and its value became a constant in the compiled program. The result changes only if the function is traced again, which happens on a call with a new signature, for example a new shape. Pass scale as an argument to make the dependence explicit.

    
5. Which of these calls to a jitted f trace again after f(jnp.ones(3)): f(jnp.zeros(3)), f(jnp.ones(4)), f(jnp.ones(3, dtype=jnp.int32)), f(np.ones(3))?
The second and third: a new shape and a new dtype. f(jnp.zeros(3)) differs only in values, and np.ones(3) is float64 but converted to float32 before the cache is consulted, so both are cache hits.

    
6. Why does if x > 0: fail inside jit while if x.ndim == 1: works?
During tracing x's values are unknown, so x > 0 is a traced boolean that Python cannot turn into True or False. Its number of dimensions is part of its abstract value, so x.ndim == 1 is an ordinary Python boolean.

    
7. What is the difference between jnp.where and lax.cond?
jnp.where computes both alternatives in full and selects element by element; it works on arrays of any shape. lax.cond takes a single boolean and runs only one branch at run time, though both are traced and compiled and must return the same shapes and dtypes. Choose where for cheap elementwise choices and cond to skip expensive work.

    
8. The 1000-step filter takes 567 ms as an eager Python loop and 1.2 ms jitted. Where did the 566 ms go?
Into overhead on the Python side: 31 000 operations, each dispatched separately. A bare dispatch costs about 13 µs, and in the loop each operation cost about 18 µs once Python's own work between them is counted. The arithmetic on 2 × 2 matrices is negligible. Compiled with lax.scan inside jit, the whole run is one program and one dispatch.

  2. Gate an outlier. A filter can reject a measurement whose innovation is implausibly large. Make this jittable, then check it on z = [5.0] and [2.0] with z_pred = [1.0] and a threshold of 3.
    
        
    def gate(z, z_pred, threshold):
    r = z - z_pred
    if jnp.abs(r) > threshold:     # an outlier: ignore it
        r = 0.0 * r

    Hint

    Under jit it fails with TracerBoolConversionError: Attempted boolean conversion of traced array with shape bool[1]. Select instead of branching; it returns [0.] for the outlier and [1.] otherwise.
    
          
    @jax.jit
def gate(z, z_pred, threshold):
    r = z - z_pred
    return jnp.where(jnp.abs(r) > threshold, 0.0, r)

  3. Jit the EKF. run_ekf(measurements, f, h, F_jacobian, H_jacobian, Q, R, x0, P0) takes four functions. Try jax.jit(run_ekf), read the error, and fix it.     Hint
    Positions 1 to 4 are the functions. A lambda expression creates a new object each time it is evaluated, even if its text is the same.

    Plain jax.jit(run_ekf) fails with TypeError: Error interpreting argument to <function run_ekf at 0x...> as an abstract array. The problematic value is of type <class 'function'> and was passed to the function at path f. Marking the functions static fixes it. Two calls with the same function objects trace once; the fresh lambda is a new key and traces again, for two traces in all. Static functions are compared by identity, so define them once and reuse them.

f, h = (lambda x: F @ x), (lambda x: H @ x)

    4. 
      
  4. A missing measurement. Sensors drop readings. Write a jitted kf_step that takes z = [nan] to mean "no measurement" and then returns the prediction unchanged. Check that a NaN gives exactly linear_kf_predict's output, and that a real measurement gives the usual step.
    
        
    Hint
    Whether a reading is missing is a value, so it must be selected, not branched on. jnp.where then discards the update's NaN result, so the value comes out right; replacing the NaN first with jnp.nan_to_num also keeps it out of gradients (J3), where 0 \times \text{NaN} is still NaN.
    
        
    Solution
    Replace the NaN before the update with jnp.nan_to_num, run the update anyway, and select. With [nan] the result equals the prediction exactly; with a real measurement it agrees with the usual step to 3 \times 10^{-8}. With no selection at all, a plain kf_step turns the state into [nan nan]. The where alone already gives the right value; the nan_to_num is what keeps the gradient finite, as J3 (Part 7) shows.
    
          
    @jax.jit
def kf_step_missing(x, P, z, F, H, Q, R):
    x_pred, P_pred = linear_kf_predict(x, P, F, Q)
    x_upd, P_upd, _, _ = linear_kf_update(x_pred, P_pred, jnp.nan_to_num(z), H, R)
    seen = ~jnp.any(jnp.isnan(z))
    return jnp.where(seen, x_upd, x_pred), jnp.where(seen, P_upd, P_pred)

  5. Benchmark it properly, and count compilations. Write a function that times another one correctly, and use it on run_linear_kf and jax.jit(run_linear_kf). Then turn on JAX's compilation log and confirm that the first recompiles on every call.
    
        
    Hint
    Two rules from Part 3: discard the first call, and block until the result is ready. Take the median of several runs. The log is enabled with jax.config.update("jax_log_compiles", True).
    
        
    Solution
    On the laptop used for this page: about 94 ms per call for run_linear_kf and 1.2 ms for the jitted version. With the log on, every call of the first prints a line beginning Finished XLA compilation of jit(scan); the jitted version prints nothing after its first call.
    
          
    import statistics, time

def benchmark(fn, *args, reps=7):
    jax.block_until_ready(fn(*args))              # the first call compiles: exclude it
    times = []
    for _ in range(reps):
        t0 = time.perf_counter()
        jax.block_until_ready(fn(*args))          # wait for the result, not just the dispatch
        times.append(time.perf_counter() - t0)
    return statistics.median(times)

print(benchmark(run_linear_kf, zs, F, H, Q, R, x0, P0))
print(benchmark(jax.jit(run_linear_kf), zs, F, H, Q, R, x0, P0))

    Part 9
    
The chapter on one page

  

  

    
    
      
  1. A pure function depends only on its arguments and has no side effects. JAX's transformations assume it and do not check. The repository's filter steps are pure: state in, state out.
    2. 
      
  2. Tracing: on the first call, jit runs the Python body once on tracers that carry only shapes and dtypes. Each JAX operation records an equation; the result is a jaxpr, a typed list of primitives in single-assignment form. jax.make_jaxpr shows it.
    3. 
      
  3. Compiling: the jaxpr is lowered to StableHLO and compiled by XLA, which optimises the whole program, folding transposes and fusing loops. For one filter step: about 0.11 s once, then 13 µs per call.
    4. 
      
  4. The cache is keyed on the function, the shapes, dtypes and weak types of the arguments, and static arguments, never on values. New shapes or dtypes compile again. Calls return before the result is ready; benchmarks must block_until_ready.
    5. 
      
  5. Side effects happen once, at trace time: print shows a tracer, globals become constants, stored tracers escape, NumPy random numbers are frozen. Pass what changes as arguments; use jax.debug.print and jax.random.
    6. 
      
  6. Control flow may depend on static values only. For values, use jnp.where (both computed), lax.cond (one runs) or static_argnums (a compile per value). Shapes cannot depend on data.
    7. 
      
  7. In the Kalman code: one step is 31 operations, 421 µs eager and 13 µs compiled; 1000 steps take 567 ms eagerly and 1.2 ms as a jitted scan. run_linear_kf without jit recompiles on every call, because its step is a new function each time.

The vocabulary, in one table

  

  

    

      
WordMeaning

      
        
Pure function, side effectA function whose result depends only on its arguments and that does nothing else; anything else a call does.

        
Referential transparencyA call can be replaced by its value without changing the program.

        
MemoizationStoring a function's results by argument so a repeated call is looked up, not recomputed.

        
Tracer, abstract valueThe stand-in for an argument during tracing; its shape, dtype and weak type, without values.

        
PrimitiveOne of JAX's basic operations, from which every jnp function is built.

        
jaxprThe program recorded by tracing: typed inputs, primitive equations, outputs.

        
Static single assignmentA program form in which every variable is assigned once; the form compilers optimise.

        
Lowering, StableHLOTranslating the jaxpr into StableHLO, a representation of array programs shared by compilers.

        
XLA, fusionThe compiler JAX uses; merging several operations into one generated loop or kernel.

        
Cache key, signatureWhat a compiled program is stored under: the function, the arguments' shapes, dtypes and weak types, and static arguments.

        
Asynchronous dispatchA call returns once the work is queued; the result is waited for only when it is needed.

        
Static, tracedKnown while tracing and part of the key; known only when the program runs.

This chapter covers purity, tracing to jaxprs, the stages of jit, its cache, asynchronous dispatch, side effects under tracing, and control flow with where, cond and static arguments, enough to read every use of jit in the Kalman chapters and to time them correctly.
