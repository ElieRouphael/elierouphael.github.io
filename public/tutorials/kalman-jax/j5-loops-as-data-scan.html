Kalman Filters with JAX · Part I, JAX · Chapter J5 of J6

Loops as data: scan, fori_loop and while_loop

A Kalman filter is a loop: one step per measurement, each step needing the last. Inside jit, a Python loop is not a loop at all. Tracing runs it, so a thousand-step filter becomes a program of 33 001 operations that took more than two minutes to compile. jax.lax.scan hands the compiler the loop itself, as one operation that holds the step function once: ready in under two tenths of a second, differentiable, batchable, and runnable backwards. This chapter is about loops expressed as data, and it ends with the Kalman smoother, which is a second scan run in reverse, and which halves the filter's error on chapter 02's data.

Part 1

A loop the compiler cannot see

Here is chapter 02's filter written the obvious way, with a Python loop, and compiled:

def filter_python_loop(zs, F, H, Q, R, x0, P0):
    x, P, outs = x0, P0, []
    for k in range(zs.shape[0]):                     # runs while tracing: once per step
        x, P = linear_kf_predict(x, P, F, Q)
        x, P, _, _ = linear_kf_update(x, P, zs[k], H, R)
        outs.append(x)
    return jnp.stack(outs)

jax.jit(filter_python_loop)(zs, F, H, Q, R, x0, P0)

It works, and it gives exactly the same estimates as the repository's run_linear_kf. But recall J2: tracing runs the Python body once, recording each operation. The for loop runs during tracing, so the recorded program has no loop in it. It has 33 operations per step, written out once per step: the loop has been unrolled. The repository's version uses jax.lax.scan instead, and its jaxpr has one equation however long the sequence is. The cost, measured on the laptop CPU used throughout:

Steps TJaxpr equations: loop / scanTrace + lower + compile: loop / scanOne run: loop / scanCompile time, log scale: loop, scan

The unrolled program grows in proportion to T, and its compile time grows faster: XLA's optimisation passes are not linear in program size. At 1000 steps the Python loop took over two minutes to compile, while scan took under two tenths of a second at every length. The unrolled program also ran slower once compiled, 15 ms against under 1 ms for the scan; a thousand copies of the step make a great deal more machine code to load and execute. A thousand measurements is a small data set; a day of NO₂ readings at one-minute resolution is 1440.

scan is a control-flow primitive: an operation whose parameters include another program. Its jaxpr for a running sum shows the shape:

{ lambda ; a:f32[5]. let
    b:f32[] c:f32[5] = scan[
      jaxpr={ lambda ; d:f32[] e:f32[]. let
          f:f32[] = convert_element_type[new_dtype=float32 weak_type=False] d
          g:f32[] = add f e
        in (g, g) }
      length=5
      reverse=False
      unroll=1
      ...
    ] 0.0:f32[] a
  in (b, c) }

(Two bookkeeping parameters are elided.) The body, add, appears once, with the loop's length as a number. The compiler sees a loop and emits a loop. This is what "loops as data" means: the loop is a value the compiler can inspect, transform and generate code for, not a Python behaviour that happened while tracing.

Part 2

scan's contract

lax.scan(f, init, xs) means exactly this Python, which the JAX documentation gives as its definition:

def scan(f, init, xs):
    carry, ys = init, []
    for x in xs:                      # one step per slice of xs along axis 0
        carry, y = f(carry, x)
        ys.append(y)
    return carry, jnp.stack(ys)

The step function takes the carry, the state passed from step to step, and one slice of the inputs xs, and returns the new carry and one output y. scan returns the final carry and all the outputs stacked along a new leading axis. In the repository's filter, the carry is (x, P), the input is one measurement, and the output is the updated state; the demo at the top colours the three. Carry, inputs and outputs can each be a tuple or any nested container of arrays (J6's pytrees), which is how the filter carries two arrays at once.

lax.scan

In plain words: a loop over the leading axis of some arrays, threading a state through and collecting one result per step.

More precisely: scan is a primitive whose parameters hold the step function as a jaxpr, traced once. It compiles to one loop. Its carry must have the same structure, shapes and dtypes on the way out of each step as on the way in, so that the loop's state has one fixed type. In functional programming the same pattern is a left fold that also returns its intermediate states, mapAccumL in Haskell [5].

length
The number of steps; inferred from xs, or given when there are no inputs, as in the data generator.
reverse=True
Run from the last slice to the first. Outputs are still stacked in the original order (Part 7).

What must stay fixed. The carry's type is a contract. Breaking it is an error at trace time, with a message that names the culprit:

lax.scan(lambda c, x: (c + 0.5, x), jnp.int32(0), xs)              # an int carry becomes a float
lax.scan(lambda c, x: (jnp.append(c, x), x), jnp.zeros(1), xs)       # a carry that grows
TypeError: scan body function carry input and carry output must have equal types, but they differ:
The input carry c has type int32[] but the corresponding output carry component has type float32[], ...

TypeError: scan body function carry input and carry output must have equal types, but they differ:
The input carry c has type float32[1] but the corresponding output carry component has type float32[2], ...

One subtlety: start the first example from the Python integer 0 instead of jnp.int32(0) and there is no error. The Python 0 is weakly typed (J1, Part 4), so scan promotes the carry to float32 and returns 1.5. A carry that should grow, such as a list of accepted measurements, has to be written as a fixed-size array and a counter. Everything else from J2 applies to the step function: it is traced once (a counter in its Python body reads 1 after a 1000-step scan), Python if on its values raises TracerBoolConversionError, and side effects happen once.

Part 3

fori_loop and while_loop

JAX has two more loops, each a convenience or a generalisation of scan:

LoopUse it whenBecomesReverse-mode gradient
lax.scan(f, init, xs)there are inputs per step or outputs to collectscanyes
lax.fori_loop(lo, hi, body, init), bounds known while tracinga fixed number of steps, nothing collectedscanyes
lax.fori_loop, bounds tracedthe count is datawhileno
lax.while_loop(cond, body, init)the number of steps is decided by the valueswhileno

The "becomes" column is read off the jaxprs. lax.fori_loop(0, 10, lambda i, c: c * x, 1.0) computes x^{10}; its jaxpr contains one scan, and jax.grad of it at x = 2 is 10 \cdot 2^9 = 5120. Pass the upper bound as an argument of a jitted function and it is traced, so the jaxpr contains a while, and the gradient fails:

ValueError: Reverse-mode differentiation does not work for lax.while_loop or lax.fori_loop with
dynamic start/stop values. Try using lax.scan, or using fori_loop with static start/stop.

J3 explained why. Reverse mode stores every step's intermediate values for the backward sweep, and a while loop's number of steps is unknown when the program is compiled, so there is nowhere to put them. Forward mode stores nothing and works through a while. The practical rule for code that will be differentiated: give loops a length the tracer can see.

Part 4

Differentiating a loop

The gradient of a scan is a scan in reverse. The forward scan computes the loss and saves, for each step, the values its backward sweep needs: the residuals. A second scan runs from the last step to the first, propagating the adjoint of the carry (J3), one step's VJP at a time. For J3's likelihood of the noise levels, the residuals are each step's covariances, gains and innovations, so memory grows in proportion to the number of steps.

jax.checkpoint, also called jax.remat, changes the bargain. Wrap the step function, lax.scan(jax.checkpoint(step), ...), and the forward scan saves only each step's input carry; the backward scan recomputes the step from it before differentiating. XLA reports the temporary memory of each compiled gradient:

Steps TMemory, plainMemory, checkpointedTime, plainTime, checkpointed

Plain, the gradient keeps 124 bytes per step; checkpointed, 24 bytes per step, five times less. Twenty-four bytes is exactly the carry: a state of 2 float32 numbers and a covariance of 4. The gradients are the same up to rounding (they differ by 3 \times 10^{-8}), and the recomputation, about one extra forward step per step, did not make the gradient consistently slower: at 100 000 steps the checkpointed version was even faster, presumably because it moves less memory. For a 2-state filter none of this matters. For a filter inside a neural network, with a large state and a long sequence, residual memory is what limits the sequence length, and checkpointing, which can be applied at any granularity, is the standard remedy [3].

Part 5

The unroll knob

Between the two extremes of Part 1, scan offers a dial: unroll=k writes k copies of the step inside each iteration of the compiled loop, so the loop runs T/k times. Fewer iterations mean less loop overhead and more room for the compiler to interleave neighbouring steps; more copies mean longer compile times. Measured on the 1000-step filter:

unrollFirst call (compile + run)Each later run

Here unrolling bought nothing: the plain loop was fastest, and every larger setting compiled more slowly. The step is a chain of small dependent matrix operations, each needing the last, so there is nothing for the compiler to interleave, and the loop overhead is already small next to the step. On a GPU, where every loop iteration launches work on the device, unrolling a small body often pays. The lesson is the general one: measure before turning a knob.

Part 6

A loop in log time

A scan is inherently sequential: step k needs the carry from step k-1. Or is it? Chapter 05's first-order filter is

y_k = z_0\, y_{k-1} + (1 - z_0)\, u_k, \qquad z_0 = e^{-0.005} = 0.99501 .

Each step is an affine map y \mapsto a y + b with a = z_0, b = (1 - z_0) u_k. Two affine maps compose into another one, (a_2, b_2) \circ (a_1, b_1) = (a_2 a_1,\ a_2 b_1 + b_2), and composition is associative: the maps of steps 1 to 8 can be combined as ((1\,2)(3\,4))((5\,6)(7\,8)) instead of left to right. The output y_k is the composition of maps 1 to k applied to y_0 = 0, and computing all those prefix compositions is a parallel prefix problem, solvable in about \log_2 T rounds of independent work [4]. The demo shows the simplest scheme for 16 steps: in round r, every element combines with the one 2^r places to its left.

Which steps each element has combined, after each round: 16 steps, rounds of independent combinations

rounds so far (sequential: 15 steps)0 combinations so far (sequential: 15)0

JAX provides this as lax.associative_scan(fn, elems), for any associative fn:

def combine(left, right):               # compose y -> a y + b: first left, then right
    a1, b1 = left
    a2, b2 = right
    return a2 * a1, a2 * b1 + b2

def lowpass_parallel(u):
    a = jnp.full_like(u, z0)
    b = (1 - z0) * u
    return lax.associative_scan(combine, (a, b))[1]

It matches the sequential scan to 1.6 \times 10^{-7} in float32 on 1000 random inputs, not exactly: J1's lesson that floating-point addition is not associative returns, since the parallel version adds in a different order. Both are within 4 \times 10^{-7} of the exact float64 result. For 1024 steps its jaxpr has 242 equations, a tree of slices, combinations and interleavings, against scan's one. JAX uses a work-efficient scheme that does about twice the sequential work in about 2\log_2 T rounds, rather than the simpler one in the demo.

On this laptop's CPU, which has few cores and runs the sequential loop very fast, the parallel version is slower at every size above a thousand:

Steps Tscanassociative_scan

The trade is work for depth: more total operations, far fewer sequential rounds. It pays on a GPU, where thousands of combinations can run at once and a sequential loop leaves the device idle. And it is not limited to first-order filters: Särkkä and García-Fernández showed that the Kalman filter and the smoother themselves can be written as associative operations on suitably defined elements, giving filters with O(\log T) depth [6].

Part 7

Back to Kalman

Every filter is a scan. run_linear_kf, run_ekf and run_ukf each define a step(carry, measurement) that returns ((x, P), x) and hand it to jax.lax.scan. Chapter 03's loss runs the same scan inside the function being differentiated, so its gradient is Part 4's backward scan. J4's batched data generator was the repository's Python loop rewritten as a scan with no inputs and length=n_steps.

The smoother is a scan in reverse. A filter's estimate at step k uses the measurements up to k. After the run, all 1000 are known, and the estimate at step k can use the later ones too. The Rauch–Tung–Striebel smoother does this with one backward pass over the filter's results [7]:

G_k = P_{k|k} F^\top P_{k+1|k}^{-1}, \qquad \hat x_{k|T} = \hat x_{k|k} + G_k (\hat x_{k+1|T} - \hat x_{k+1|k}), \qquad P_{k|T} = P_{k|k} + G_k (P_{k+1|T} - P_{k+1|k}) G_k^\top .

The smoothed estimate at k needs the smoothed estimate at k+1: a carry, flowing backwards. In JAX that is lax.scan(..., reverse=True). The repository has no smoother; here is one, added to its filter in a few lines:

def filter_and_smoother(zs):
    def fstep(carry, z):                               # the repository's filter, keeping its predictions
        x, P = carry
        xp, Pp = linear_kf_predict(x, P, F, Q)
        xu, Pu, _, _ = linear_kf_update(xp, Pp, z, H, R)
        return (xu, Pu), (xu, Pu, xp, Pp)
    _, (xf, Pf, xp, Pp) = lax.scan(fstep, (x0, P0), zs)

    def bstep(carry, inp):                             # Rauch-Tung-Striebel, one step back
        xs_next, Ps_next = carry
        x, P, xp_next, Pp_next = inp
        G = jnp.linalg.solve(Pp_next, F @ P).T          # P F^T Pp_next^-1, without an inverse
        xs = x + G @ (xs_next - xp_next)
        Ps = P + G @ (Ps_next - Pp_next) @ G.T
        return (xs, Ps), (xs, Ps)
    _, (xs, Ps) = lax.scan(bstep, (xf[-1], Pf[-1]), (xf[:-1], Pf[:-1], xp[1:], Pp[1:]), reverse=True)
    return xf, jnp.concatenate([xs, xf[-1:]])

The backward scan starts from the filter's last estimate, which is already smoothed (no later measurements exist), and its inputs pair each step's filtered result with the next step's prediction. Is it right? For a linear Gaussian model the smoothed means are the exact posterior means of all 1000 states given all 1000 measurements, which can also be found by brute force: write the joint distribution of the 1001 states as one Gaussian and solve its 2002 normal equations. In float64 the scan and the brute-force solution agree to 10^{-9}. The scan does it in O(T) work with a carry of six numbers; the dense solve took a 2002 × 2002 matrix.

On chapter 02's 1000 stepsPosition RMSEVelocity RMSE

The smoother almost halves the filter's error, in both position and velocity. The price is time: it is only available after the data has arrived, so it suits offline analysis, such as reconstructing chapter 04's NO₂ series, cleaning a log before training a model, or, in the EM algorithm, estimating the noise levels J3 found by gradient descent. Step through both scans in the demo at the top: the filter's carry flows right, the smoother's left, and the smoothed curve hugs the truth where the filter lags it.

Part 8

Check your understanding

1. Why does a Python for loop inside jit produce a program whose size grows with the number of iterations?

The loop runs while the function is traced, and tracing records every operation it performs. Each iteration's operations are recorded again, so the jaxpr holds one copy of the body per iteration: the loop is unrolled. Compile time grows faster than linearly with that size.

2. What are the carry, the inputs and the outputs of the repository's filter scan?

The carry is (x, P), the state estimate and its covariance, passed from step to step. The inputs are the measurements, one row per step. The output of each step is the updated state, and scan stacks them into an array of shape (T, 2).

3. Why must the carry keep its shape and dtype?

The compiled loop has one state of one fixed type, stored in fixed memory and read by the same machine code on every iteration. A carry that changed type would need a different program per iteration, which is what unrolling is.

4. When is fori_loop differentiable in reverse mode?

When its bounds are known while tracing, because then it is implemented as a scan of known length. With traced bounds it becomes a while_loop, whose length is unknown at compile time, so the residuals of reverse mode cannot be allocated.

5. What does jax.checkpoint on a scan's step function trade, and why did the memory fall to exactly 24 bytes per step?

It trades memory for recomputation: the forward pass keeps only each step's input carry, and the backward pass recomputes the step from it. The carry here is a float32 state of 2 numbers and a covariance of 4: 6 numbers, 24 bytes.

6. Why can chapter 05's filter be computed in logarithmic depth, and why was that slower on a laptop?

Each step is an affine map and composition of affine maps is associative, so the prefix compositions can be combined in a tree of about \log_2 T rounds of independent work. The tree does more total work than the sequential loop, and a CPU with a few cores cannot run enough of each round at once to recover it.

7. Why does the smoother need reverse=True?

The smoothed estimate at step k depends on the smoothed estimate at k+1, so the carry must flow from the last step to the first. The outputs are still stacked in time order.

8. Why is the smoother more accurate than the filter, and when can it not be used?

It conditions each estimate on all the measurements, before and after, while the filter uses only those up to the current step. It needs the whole sequence, so it cannot run in real time; it is for analysis after the fact.

Part 9

Exercises

  1. Chapter 05's filter as a scan. Write y_k = z_0 y_{k-1} + (1 - z_0) u_k with lax.scan and check it against a Python loop in float64.
    Hint

    The carry is y; the input is u_k; the output is the new y.

    Solution

    In float32 the scan is within about 2 \times 10^{-7} of the float64 loop on 1000 random inputs, for outputs about 0.1 in size.

    def lowpass_scan(u, z0=jnp.exp(-0.005)):
    def step(y, uk):
        y = z0 * y + (1 - z0) * uk
        return y, y
    return lax.scan(step, jnp.float32(0.0), u)[1]
  2. Keep the covariances. Change run_linear_kf so that it also returns every step's covariance. What are the shapes of the outputs?
    Hint

    The output of a step can be a tuple; scan stacks each element separately.

    Solution

    Return ((x_updated, P_updated), (x_updated, P_updated)) from the step. The stacked outputs are a tuple of shapes (1000, 2) and (1000, 2, 2). The smoother in Part 7 uses exactly this.

  3. Make the gradient work. This fails under jax.jit(jax.grad(power))(2.0, 10). Fix it two ways.
    def power(x, n):
    return lax.fori_loop(0, n, lambda i, c: c * x, 1.0)
    Hint

    Under jit, n is traced. Either tell jit it is static (J2), or loop over something of fixed length.

    Solution

    With jax.jit(jax.grad(power), static_argnums=1), n is known while tracing, the loop is a scan, and the gradient is 5120. Or write lax.scan(lambda c, _: (c * x, None), 1.0, None, length=n) with n static. Either way, every distinct n compiles a new program.

  4. Read the memory table. From the plain gradient's 124 bytes per step, how much memory would the gradient of a 10-million-step likelihood need, with and without checkpointing? What would checkpointing every 100 steps instead of every step change?
    Hint

    Checkpointing every step keeps one carry per step. Checkpointing blocks of 100 keeps one carry per block, plus one block's residuals during the backward pass.

    Solution

    About 1.24 GB plain and 240 MB checkpointed. Checkpointing blocks of 100 steps (a scan over blocks, each block a checkpointed scan of 100 steps) keeps 100 000 carries, 2.4 MB, plus one block's residuals, 12.4 kB, at the cost of recomputing each block once. Nesting this idea gives memory that grows like \log T [3].

  5. Check the smoother by brute force. For the first 50 measurements, build the joint Gaussian of x_0, \dots, x_{50} as one linear system and compare its solution with the scan smoother.
    Hint

    The negative log-posterior is a sum of quadratic terms: the prior on x_0, one transition term (x_k - Fx_{k-1})^\top Q^{-1}(\cdot) per step, one measurement term per step. Its minimiser solves Ax = b, where A is block-tridiagonal.

    Solution

    dense_posterior in j5_numbers.py builds exactly this system; on all 1000 steps it agrees with the reverse scan to 10^{-9} in float64. The smoother is a block-tridiagonal solver in disguise: its forward scan is the elimination, its backward scan the back-substitution.

Part 10

The chapter on one page

  1. A Python loop inside jit is unrolled: 33 001 operations for a 1000-step filter, over two minutes to compile. lax.scan is one operation holding the step once, ready in under two tenths of a second.
  2. scan(f, init, xs) threads a carry through f(carry, x) -> (carry, y) and stacks the outputs. The carry's structure, shapes and dtypes are fixed; the body is traced once.
  3. fori_loop with static bounds is a scan; with traced bounds, like while_loop, it is a while, which reverse mode cannot differentiate.
  4. The gradient of a scan is a reverse scan over saved residuals: 124 bytes per filter step. jax.checkpoint keeps only the carry, 24 bytes, and recomputes.
  5. unroll did not help this filter on a CPU; measure. associative_scan computes associative recurrences in logarithmic depth, at the cost of more work: slower here, faster where parallelism is wide.
  6. In the Kalman code: every filter is a scan; the RTS smoother is a second scan with reverse=True, exact to 10^{-9} against brute force, and it cuts chapter 02's position RMSE from 0.155 to 0.084.

Part 11

Scope and further reading

Scope. This chapter covers scan, fori_loop, while_loop and associative_scan, their costs, their differentiation and checkpointing, and the RTS smoother. Not covered: lax.map, nested checkpointing policies, the parallel Kalman filter itself, and smoothers for the extended and unscented filters.
