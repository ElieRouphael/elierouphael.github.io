A first-order filter in C

Ten chapters of Python and JAX, and then the filter has to run on a microcontroller with 32 kilobytes of memory and no NumPy. This chapter is about that step. It takes the simplest useful filter, the first-order low-pass, derives its exact discrete form, and implements it in C the way the author's coursework program TD3.c does: arrays, pointers, functions with return codes, and files read and written by hand. The program is read line by line as a C lesson; compiling and running it finds three bugs, one of which turned its output into a column of zeros; and the fixed filter runs below on the program's own recording, where one sample of delay turns out to decide how much noise it can remove.

Part 1

The first-order filter

Continuous time. The first-order low-pass filter is the simplest system with memory: an output that chases its input with a time constant \tau and a static gain K,

\tau\,\dot y(t) + y(t) = K\,u(t), \qquad H(s) = \frac{Y(s)}{U(s)} = \frac{K}{1 + \tau s}.

An RC circuit, a thermometer in a bath, a motor's speed under a voltage step: all are first-order. Its step response is K(1 - e^{-t/\tau}), 63% of the way after one time constant; its frequency response has magnitude K/\sqrt{1 + (\omega\tau)^2} and phase -\arctan(\omega\tau), so it passes frequencies well below the cutoff f_c = 1/(2\pi\tau) and attenuates those above it by a factor of ten per decade (20 dB per decade), with a lag that reaches 45° at the cutoff and 90° far above it [1].

Discrete time, exactly. A program sees the input only at the sampling instants kT_e and must produce y_k from y_{k-1} and past inputs. If the input is held constant over each sampling interval (what a digital-to-analogue converter does, the zero-order hold), the differential equation can be solved exactly over one interval: the homogeneous part decays by z_0 = e^{-T_e/\tau} and the held input contributes K(1 - z_0)u_{k-1}, so

y_k = z_0\, y_{k-1} + K(1 - z_0)\, u_{k-1}, \qquad z_0 = e^{-T_e/\tau}.

This is the recursion in the program's filtrage(). It is an infinite-impulse-response filter with one pole at z_0, and it costs one multiplication and one multiply-add per sample and one memory cell of state, which is why it runs on anything: y_k needs samples up to k-1 only, so it can be computed as soon as u_{k-1} arrives and held until it is due (Exercise 1's version keeps the previous output and the previous input instead, which is easier to read). Two things to notice: a constant input u settles where y = z_0 y + K(1 - z_0)u, that is at y = Ku; and the input enters with one sample of delay, u_{k-1}, because the sample held over the interval ending at k is the one taken at k-1. (Many implementations use u_k instead, y_k = z_0 y_{k-1} + K(1 - z_0)u_k, the exponential-smoothing form. It is neither backward Euler, whose pole is \tau/(\tau + T_e), nor the bilinear transform, which averages u_k and u_{k-1}. The two forms have the same gain and differ by one sample of delay, which the phase plot of Part 5 draws and which, Part 5 shows, decides how much noise the filter can remove from the program's recording.)

Numbers for the program's setting. With T_e = 0.01 s and \tau = 2 s, z_0 = e^{-0.005} = 0.99501 and K(1 - z_0) = 0.00499: each new sample moves the output half a percent of the way toward it, an average over about 200 samples. The cutoff is 1/(4\pi) = 0.080 Hz. The recording the program filters is a sine at 1.00 Hz, thirteen times the cutoff, which the filter passes at 8% of its amplitude. Part 4 shows what the program made of that.

Exact (zero-order-hold) discretisation

In plain words: instead of approximating the derivative by a difference, solve the differential equation exactly between two samples, assuming the input stays constant in between.

More precisely: for \dot y = -y/\tau + (K/\tau)u with u constant on [kT_e - T_e, kT_e), y_k = e^{-T_e/\tau} y_{k-1} + \int_0^{T_e} e^{-s/\tau} (K/\tau)\,u_{k-1}\,ds = z_0 y_{k-1} + K(1 - z_0) u_{k-1}. The discrete system has the continuous one's pole mapped by z_0 = e^{sT_e} with s = -1/\tau, is stable for every T_e (since 0 < z_0 < 1), and matches the continuous response exactly at the sampling instants for held inputs [2].

Forward Euler
y_k = (1 - T_e/\tau)y_{k-1} + (KT_e/\tau)u_{k-1}: the first-order Taylor approximation of the same thing, unstable for T_e > 2\tau.
Pole
z_0: the factor by which the output decays per sample when the input is zero; the closer to one, the longer the memory.
Cutoff
f_c = 1/(2\pi\tau), where the gain is K/\sqrt 2 and the lag 45°.
Part 2

The C you need

C is a small language that maps almost directly onto the machine: numbers live in typed memory cells, arrays are consecutive cells, a pointer is the address of a cell, and nothing is checked at run time. That is what makes it fast and portable to microcontrollers, and what makes the bugs of Part 4 possible. This section covers exactly the subset the program uses [3].

Compile and run. A C program is text that a compiler turns into an executable. With gcc, which the repository's editor configuration also uses:

gcc -Wall -Wextra -o td3 TD3.c -lm
./td3

-Wall -Wextra turns on the warnings; read them, they are free bug reports. -lm links the maths library, where Linux keeps exp; on Windows it does no harm, and the executable is td3.exe.

Part 3

The program, line by line

The filter. The heart of the program is six lines. The length check and the return code are the C idiom for "this can fail":

int filtrage(double *u, int taille_u, double *y, int taille_y, double K, double tau, double Te) {
    if (taille_u != taille_y) return -1;        /* the caller passed arrays of different lengths */
    double z0 = exp(-Te / tau);                 /* the pole: how much of y survives one sample   */
    y[0] = 0;                                   /* start at rest                                  */
    for (int k = 1; k < taille_u; k++)
        y[k] = z0 * y[k - 1] + K * (1 - z0) * u[k - 1];
    return 0;
}

Note what is not here: no allocation (the caller owns both arrays), no state between calls (a real-time version would keep y[k-1] and u[k-1] in variables and process one sample per call, Exercise 1), and exp computed once, outside the loop.

Reading a file of numbers. LireEntree opens the file, reads doubles one at a time with fscanf until it fails, and distinguishes "end of file" from "something else went wrong":

int LireEntree(const char *nom_fichier, double *valeurs) {
    FILE *fichier = fopen(nom_fichier, "r");
    if (fichier == NULL) return -1;
    int compteur = 0;
    while (compteur < 10000) {
        if (fscanf(fichier, "%lf", &valeurs[compteur]) != 1) {
            if (feof(fichier)) break;           /* clean end of file */
            fclose(fichier); return -1;         /* a line that is not a number */
        }
        compteur++;
    }
    fclose(fichier);
    return compteur;                            /* how many values were read */
}

The return value does double duty, count on success and −1 on failure, a common C convention. The cap of 10000 protects the caller's array, which the function cannot otherwise know the size of. EcrireSortie is the mirror image: fopen(…, "w"), a loop of fprintf(fichier, "%.2f\n", valeurs[i]), fclose. The two decimals of %.2f will matter in Part 4.

Minimum, maximum, histogram. ChercheMinMax walks the array once and writes its two results through pointers. CalculeHistogramme divides [\min, \max] into nb_bins equal bins and counts; the one subtle line is

int index = (tableau[i] - min) / largeur_bin;   /* double -> int truncates */
if (index >= nb_bins) index = nb_bins - 1;       /* the maximum lands exactly on the edge */

where the implicit conversion from double to int is the floor for non-negative values, and the clamp catches the maximum, whose index would otherwise be nb_bins.

main. Three stages. First a self-test: build a 51-sample input (0.5 s at T_e = 0.01) with a 1 at t = 0, filter it with K = 1, \tau = 2, and print the table. Second, read enregistrement-bruit.txt into valeurs and print it. Third, read it again into bruit, filter it into sortie, write sortie.txt, and print a 16-bin histogram of bruit − sortie. Each stage checks the return codes of its reading, filtering and writing calls.

Part 5

What the filter does to the signal

The recording is 250 samples of a sine at 1.00 Hz with amplitude 1.00 and additive noise of standard deviation 0.096 (a least-squares sine fit; the fitted sine is the dashed line in the hero demo). The question a filter is supposed to answer is: can we get the sine back with less noise? The response plots say how a first-order filter trades the two.

continuous filter (dashed)C program, u_{k-1}fed u_k (phase; same gain)cutoff and 1 Hz

Three settings tell the story. At the program's \tau = 2 s the sine is thirteen times above the cutoff: gain 0.08, lag 87°, the signal is gone. At \tau = 0.2 s the gain is 0.62 and the lag 53°: a smaller, later sine, further from the clean one (RMSE 0.54) than the raw recording (0.096). At \tau = 0.02 s, the corrected program's setting, chosen to pass the sine almost intact rather than to remove noise, the gain is 0.99 and the lag 9°, 2.5 samples; the output's RMSE to the clean sine is 0.120, still above the raw recording's. Sweeping \tau finely, the program's recursion beats the recording only just: its best, 0.0948 at \tau \approx 0.0083 s, less than one sample, is 1.5% below the recording's 0.0963.

The culprit is not causality but the one sample of delay. Fed the current sample instead, y_k = z_0 y_{k-1} + K(1 - z_0)u_k, the same one-pole recursion is just as causal and just as cheap, and it does remove noise: 0.082 at \tau = 0.02 s, and at best 0.069 at \tau \approx 0.012 s, 28% below the recording. The program's form computes y_k from samples up to k-1 only, so it is a forecast of the signal one sample ahead (Part 6 makes this exact), and on a sine that moves by up to 6% of its amplitude per sample the forecast costs nearly all that the averaging saves. Even the better form gains only 28%: a causal low-pass removes noise by averaging the recent past, which delays a sine, so at 100 samples per period its time constant must stay near one sample. To do better, use a filter that knows the frequency, a narrow band-pass or an oscillator model inside a Kalman filter, or, offline, a zero-phase filter run forwards and backwards. The first-order filter earns its keep where the signal is much slower than the noise, which the program's own recording is not.

Part 6

Back to Kalman

The first-order filter and the Kalman filter of chapters 01 and 02 are closer than they look. Take the scalar Kalman filter for a slowly drifting level, x_{k+1} = x_k + w_k, z_k = x_k + \nu_k, with noise variances q and r. Chapter 02's exercise 5 shows that its gain converges to a constant K_\infty, after which the update reads

\hat x_k = (1 - K_\infty)\,\hat x_{k-1} + K_\infty\, z_k, \qquad K_\infty = \frac{p_\infty}{p_\infty + r}, \quad p_\infty = \frac{q + \sqrt{q^2 + 4qr}}{2}.

That is Part 1's first-order low-pass with pole z_0 = 1 - K_\infty (the pole, not a measurement), static gain 1 and time constant \tau = -T_e / \ln(1 - K_\infty), fed the current sample: Part 5's u_k form, with \hat x_k the estimate after the update, \hat x_{k|k}. The C program's own form is the same filter one step earlier. For a random walk the prediction step copies the estimate, \hat x_{k|k-1} = \hat x_{k-1|k-1}, so the predicted level obeys

\hat x_{k|k-1} = (1 - K_\infty)\,\hat x_{k-1|k-2} + K_\infty\, z_{k-1},

which is filtrage() exactly, delayed input included (the chapter's script checks the two on the recording to 2 \times 10^{-16}). In chapter 01's terms, the C program outputs the prediction and the u_k form the update. That is why the program's filter gained so little in Part 5, 1.5% against the u_k form's 28%: it was scored as an estimate of the present while computing a forecast of it.

The Kalman filter's contribution is not the recursion, which forecasters had used as simple exponential smoothing since R. G. Brown's work of 1956 [6], four years before Kalman's paper of 1960 (the time-series course derives it), but the choice of its coefficient: the time constant is derived from how fast the level drifts (q) relative to how noisy the sensor is (r), rather than guessed (choosing the smoothing constant from data is the same question). For q \ll r, K_\infty \approx \sqrt{q/r}, and the filter averages over about \sqrt{r/q} samples. Chapter 04's forecaster had K_\infty = 0.31 with A = 0.9, so the linear part of its state decays by (1 - K_\infty)A = 0.62 an hour, a time constant of about two hours, and it lagged the series for the reason the sine lags here.

Conversely, a first-order filter whose time constant was chosen by ear is a Kalman filter for some unstated q/r, and stating it is often the quickest way to see whether the choice is reasonable: K_\infty = 1 - z_0 gives q/r = K_\infty^2/(1 - K_\infty). The repository's \tau = 2 s claims q/r = 2.5 \times 10^{-5}, a level that drifts by a two-hundredth of the noise per sample, for a sine that crosses its whole range in 50 samples; the corrected program's 0.02 s claims 0.26 (K_\infty = 0.39); the best u_k time constant on the recording, 0.012 s, about 0.7. On a microcontroller the two cost the same, a couple of multiply-adds per sample. With a time-varying gain the scalar filter needs one more double, its variance p, and per sample two additions, a multiplication and a division more (p \leftarrow p + q, K = p/(p + r), and after the update p \leftarrow rK); chapter 01's two-state filter, twenty lines of Python, needs a 2×2 matrix and about a dozen multiply-adds per sample in C, which Exercise 4 asks for.

Part 7

Check your understanding

1. Why is z_0 = e^{-T_e/\tau} rather than 1 - T_e/\tau?

Because the differential equation is solved exactly over one sampling interval for a held input; 1 - T_e/\tau is the first-order Taylor approximation (forward Euler), which is less accurate and unstable for T_e > 2\tau. For the program's values the two differ in the fifth decimal, but the exact form costs nothing more.

2. Why does the recursion use u_{k-1} and not u_k?

With a zero-order hold the sample taken at k-1 is the input applied during the interval that ends at k. Using u_k gives the exponential-smoothing form, with the same gain and one sample less delay. At the signal's 1 Hz the program's form lags the continuous filter by about 1.8°, half a sample, and the u_k form leads it by about as much, so the two are 360^\circ f T_e = 3.6^\circ apart; the phase plot of Part 5 draws all three, and Part 6 gives the two discrete forms their Kalman names.

3. Why do the program's array functions take a length argument?

A C array carries no length; a pointer parameter is just an address. A function must be told how many cells it may touch, or, like LireEntree, assume a size (its cap of 10000). A length protects only if it is right: filtrage's mismatch check passed in bug 1, because the caller gave the same wrong length, taille_bruit, for both arrays.

4. How does LireEntree return both a count and an error?

By convention: a non-negative return is the count, −1 is an error, and the caller tests < 0. C has no exceptions and one return value, so this and output pointers are the two mechanisms available.

5. Why did the original program produce all zeros without crashing?

It filtered the wrong array, a 51-sample impulse, and read 198 cells past its end. Reading past an array is undefined behaviour: here the memory past the array held zeros, so the output was the impulse response alone, at most 1 - z_0 = 0.00499, and %.2f printed it as 0.00. Nothing in C checks the index.

6. With bugs 1 and 2 fixed, the program writes values between −0.05 and 0.14. Is it still wrong?

It is correct and badly configured: with \tau = 2 s the 1 Hz signal is attenuated to 8%, and what is left is a small sine on a start-up transient. The test, a unit impulse whose largest response value, 1 - z_0 = 0.00499, prints as 0.00, could not reveal the problem. A unit step and %.4f would.

7. Why does the program's filter barely beat the raw recording, when the same filter fed the current sample does?

Because y_k is computed from samples up to k-1: the program's form forecasts the signal one sample ahead and is scored as an estimate of the present. On a sine that moves by up to 6% of its amplitude per sample, the forecast's error eats nearly all that the averaging gains, so at its best time constant, about 0.008 s, it is 1.5% closer to the clean sine than the recording. Fed u_k, the same causal recursion reaches 0.069 at about 0.012 s, 28% closer. The Kalman filter calls the two forms the prediction \hat x_{k|k-1} and the update \hat x_{k|k} (Part 6).

8. In what sense is the steady-state Kalman filter a first-order filter?

Its update \hat x_k = (1-K_\infty)\hat x_{k-1} + K_\infty z_k is the same recursion with z_0 = 1 - K_\infty, fed the current sample; for a random walk its one-step prediction is the program's form exactly, delayed input included. The Kalman filter supplies the coefficient from q and r instead of a guess, and, before convergence, a time-varying one.

Part 8

Exercises

  1. Make it real-time. Rewrite the filter as a function that takes one input sample and returns one output sample, keeping its state between calls, as a sensor loop on a microcontroller would call it.
    Hint

    The state is the previous output and the previous input. Keep them in a struct that the caller owns, or in static variables if there is only ever one filter.

    Solution 
    typedef struct { double z0, b, y_prev, u_prev; } Filtre;

void filtre_init(Filtre *f, double K, double tau, double Te) {
    f->z0 = exp(-Te / tau); f->b = K * (1 - f->z0); f->y_prev = 0; f->u_prev = 0;
}
double filtre_step(Filtre *f, double u) {
    double y = f->z0 * f->y_prev + f->b * f->u_prev;   /* one multiply-add, one multiply */
    f->y_prev = y; f->u_prev = u;
    return y;
}

    Calling filtre_step on each sample of the recording reproduces filtrage() exactly; the whole state is four doubles, and nothing is allocated.

  2. Test it properly. Replace the impulse self-test by a unit step and check, in code, that the output reaches 63.2% of K after \tau/T_e samples and 99.3% after five time constants.
    Hint

    Use \tau = 0.05 s so that the test fits in half a second; compare with a tolerance rather than for equality, since the values are floating-point.

    Solution

    With \tau = 0.05 s the step response first exceeds 0.632 at the fifth sample after the step and 0.993 at the 25th, exactly \tau/T_e and 5\tau/T_e: n samples after the step the output is K(1 - z_0^n) = K(1 - e^{-nT_e/\tau}), the continuous response at t = nT_e, so there is no extra sample to count. The page's "unit step" input shows the curve. A test that prints PASS or FAIL and returns a non-zero exit code on failure is worth more than the printed table, because a build script can run it.

  3. Choose \tau for the recording. Fit the clean sine, as the page does, then sweep \tau and report the RMSE between the filter output and the clean sine. Where is the minimum, and what does that say about using a first-order filter here?
    Hint

    In Python: a least-squares fit of a\sin\omega t + b\cos\omega t + c over a grid of frequencies, then np.exp(-Te/tau) and the recursion in a loop.

    Solution

    The fit gives 1.002 Hz, amplitude 0.997, noise sd 0.096. The RMSE to the clean sine is 0.697 at \tau = 2, 0.539 at 0.2, 0.228 at 0.05 and 0.120 at 0.02, and its minimum, 0.095, is at \tau \approx 0.008 s, below one sample: 1.5% better than the recording. The filter does act there, removing about a quarter of the noise, but forecasting one sample ahead costs nearly as much in error on the sine. Fed the current sample, the same recursion gives 0.693, 0.512, 0.188 and 0.082 at the same four values, and a minimum of 0.069 at \tau \approx 0.012 s, 28% better. A first-order filter can denoise this recording a little, provided it uses the sample it is scored against; a signal only 100 samples per period long leaves it little room either way.

  4. Chapter 01 in C. Translate the two-state Kalman filter of chapter 01 to C: a struct with x and the four entries of P, a predict and an update function with the scalar innovation, and no matrix library. Run it on the vehicle CSV and compare with the Python estimates.
    Hint

    With H = (1, 0) the innovation covariance is the scalar P_{00} + R, so no inverse is needed; write the 2×2 products out by hand, as the page's JavaScript does.

    Solution

    About forty lines. The estimates agree with the NumPy class to rounding (chapter 01's JavaScript version, written the same way, matches the repository's estimates to 7 \times 10^{-5} m, the four-decimal rounding of the page's copy of the data). The cost per sample is a dozen multiply-adds and six doubles of state, x and the four entries of P (five using its symmetry): a Kalman filter fits on any microcontroller that has a floating-point unit, and on most that do not.

Part 9

The chapter on one page

  1. The filter: \tau\dot y + y = Ku; discretised exactly as y_k = z_0 y_{k-1} + K(1-z_0)u_{k-1}, z_0 = e^{-T_e/\tau}; cutoff 1/(2\pi\tau), 20 dB per decade, 45° lag at the cutoff.
  2. The C: typed cells, arrays without lengths, pointers as array and output parameters, return codes instead of exceptions, fopen/fscanf/fprintf/fclose, and undefined behaviour when an index is out of range.
  3. The bugs: the wrong array passed to the filter (output all zeros, 198 cells read past the end), a histogram over 500 entries of arrays in which only 250 had been written, and a time constant of 2 s for a 1 Hz signal with a self-test that prints 0.00 either way.
  4. The signal: 1.00 Hz, amplitude 1.00, noise sd 0.096; gain 0.08 at \tau = 2, 0.62 at 0.2, 0.99 at 0.02; the program's form beats the raw recording by 1.5% at best (\tau \approx 0.008 s), the same recursion fed u_k by 28% (\tau \approx 0.012 s): the one sample of delay, not causality, is what costs.
  5. The link: the steady-state scalar Kalman filter is this recursion with z_0 = 1 - K_\infty: the program's u_{k-1} form is its one-step prediction, the u_k form its update, and the time constant comes from q/r rather than a guess.

Part 10

Scope and further reading

Scope. This chapter covers the first-order filter, its exact discretisation, the subset of C needed to implement it with file I/O, and the reading of a small program for bugs. It does not cover higher-order or FIR filter design, fixed-point arithmetic, which a microcontroller without a floating-point unit would need, or the toolchains of specific devices.
