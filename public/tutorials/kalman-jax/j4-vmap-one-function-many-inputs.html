Kalman Filters with JAX · Part I, JAX · Chapter J4 of J6

vmap: one function, many inputs

The repository's filter steps are written for one state, one covariance, one measurement. The unscented filter needs the motion model applied to five sigma points; a test of the filter needs a thousand simulated runs. You could loop, or rewrite every function with an extra axis. jax.vmap does the rewrite for you: it traces the function once, as jit does, and turns every operation on one input into the same operation on a batch, with no loop in the program it produces. This chapter shows how, then runs a thousand Kalman filters in one call, 85 times faster than a loop, to check that the filter is honest about its own uncertainty and to settle a question J3 left open: was chapter 02's low noise estimate bad luck?

Part 1

The batching problem

A function is usually easiest to write, read and test for one input. Here is a one-layer network applied to one vector:

def predict_one(x, W):        # x: (2,), W: (3, 2)
    return jnp.tanh(W @ x)      # (3,)

Now there are 4 inputs, stacked as xs of shape (4, 2). Three ways to apply the function to all of them:

1. Loop. jnp.stack([predict_one(x, W) for x in xs]). Correct, and simple, but each call is a separate dispatch (J2), and inside jit the loop is unrolled into one copy of the function per input.

2. Rewrite by hand. jnp.tanh(xs @ W.T). Fast, but now the code is about batches, and every line must be rethought with an extra axis: which side of @, which axis to transpose, which to sum over, what broadcasts (J1). That is where shape bugs live, and the per-example version is no longer the one you read and tested.

3. Let JAX do the rewrite.

jax.vmap(predict_one, in_axes=(0, None))(xs, W)     # (4, 3), equal to the loop's result

in_axes=(0, None) says: map over axis 0 of the first argument, and give every call the same second argument. The result is exactly the loop's. The program is the hand-written one. Compare the two jaxprs:

{ lambda ; a:f32[2] b:f32[3,2]. let                 # predict_one
    c:f32[3] = dot_general[dimension_numbers=(([1], [0]), ([], []))] b a
    d:f32[3] = tanh c
  in (d,) }

{ lambda ; a:f32[4,2] b:f32[3,2]. let               # vmap(predict_one, in_axes=(0, None))
    c:f32[3,4] = dot_general[dimension_numbers=(([1], [1]), ([], []))] b a
    d:f32[3,4] = tanh c
    e:f32[4,3] = transpose[permutation=(1, 0)] d
  in (e,) }

(The preferred_element_type parameters are removed; the rest is JAX's output.) The matrix-vector product became one matrix-matrix product, contracting W's axis 1 with the batch's axis 1: W X^\top, all four inputs at once. tanh was applied to the whole (3, 4) result, and a transpose put the batch axis first. There is no loop: four inputs or a million, one program of three operations.

vmap

In plain words: write the function for one input; vmap gives you the version for many, as if you had rewritten it with an extra axis.

More precisely: jax.vmap(f, in_axes, out_axes) returns a function that maps f over an axis of some of its arguments. It traces f once with tracers that carry a batch axis, and each primitive's batching rule produces an equivalent operation on the batched arrays. The result is a program with no loop over the batch, and the same values as a loop [1].

Vectorisation
Expressing a computation as operations on whole arrays instead of loops over elements, so that the hardware can process many elements at once.
Batch axis
The axis vmap maps over; its length is the batch size.
Part 2

How vmap works

vmap is another interpretation of the same trace as J2's jit and J3's grad. Its tracer carries the value's per-example type and where the batch axis is. Inside a vmapped function an argument prints as

VmapTracer(aval=float32[2], batched=float32[4,2])

The function sees a vector of length 2, as it was written for; underneath is a (4, 2) array. Every primitive has a batching rule that says how to apply it when some inputs carry a batch axis [2]:

PrimitiveBatching rule
sin, tanh, add, mul, … (elementwise)Apply to the batched array as it is; an unbatched operand is broadcast.
dot_general (matrix products)If both operands are batched, the batch axes become a batch dimension of the product: a batched matrix multiply. If one is, its batch axis is carried through as a free axis.
reduce_sum, transpose, indexingShift the axis numbers by one to step around the batch axis.
cond, whileWith a condition that depends on the batch: turned into selections and masked loops (Part 4). With an unbatched condition: kept as they are, on batched operands.
cholesky, solve, …Call the batched version of the linear-algebra routine.

The demo at the top shows this for the repository's linear_kf_predict. Batch only x: F @ x becomes a matrix product with the 1000 states as columns, and P_pred, which does not depend on x, is computed once and then broadcast to 1000 identical copies, because every output of a vmapped function gets a batch axis by default. Batch everything: each @ becomes a dot_general with batch dimensions ([0], [0]), 1000 independent 2 × 2 products in one operation. In every case the batched program is a straight list of array operations, the same length or a few operations longer, and never a loop.

Because the result is an ordinary jaxpr, it can be compiled by jit, differentiated by grad and batched again by another vmap. The transformations compose, which is the design idea of JAX [3].

Part 3

in_axes and out_axes

in_axes has one entry per positional argument: an integer, the axis of that argument to map over, or None, meaning the argument is shared by every element. A single integer applies to all arguments; the default is 0. For containers such as tuples or dicts of arrays, the entry can be a matching container (J6 calls these pytrees). out_axes, default 0, says where the batch axis goes in each output:

jax.vmap(predict_one, in_axes=(0, None))(xs, W).shape                  # (4, 3)
jax.vmap(predict_one, in_axes=(0, None), out_axes=1)(xs, W).shape      # (3, 4)
jax.vmap(predict_one, in_axes=(1, None))(xs.T, W).shape                # (4, 3): batch along axis 1 of the input

Every mapped axis must have the same length, the batch size. Four mistakes produce four messages, worth recognising:

MistakeJAX 0.12 says
Batches of different sizes: vmap(add)(jnp.ones(3), jnp.ones(4))ValueError: vmap got inconsistent sizes for array axes to be mapped: followed by each argument's size
Nothing to map: in_axes=(None, None)ValueError: vmap must have at least one non-None value in in_axes or axis_size must be specified
Wrong number of entries: in_axes=(0,) for two argumentsValueError: vmap in_axes must be an int, None, or a tuple of entries corresponding to the positional arguments passed to the function, but got len(in_axes)=1, len(args)=2.
An axis the array does not have: in_axes=(1, 0) on a vectorValueError: vmap was requested to map its argument along axis 1, which implies that its rank should be at least 2, but is only 1 (its shape is (3,))

Choosing None where it is true matters for speed as well as correctness. Sharing F and Q lets XLA use a plain matrix product; batching them, even with 1000 identical copies, forces 1000 small ones and 1000 times the memory. Toggle F in the demo and watch the dot_general change.

Part 4

Branches and loops in a batch

Python control flow on values fails under vmap for the same reason as under jit (J2, Part 5): the tracer has no single value to branch on. And a batch adds a new difficulty to JAX's own control flow: different elements may want different branches, or different numbers of iterations. A program without a loop over the batch cannot give each element its own path, so vmap changes what the control flow means.

lax.cond becomes a select when its condition depends on the batched input. (When it does not, every element takes the same branch and vmap keeps the cond.) A function that takes the square root of positive inputs and negates the others:

def branchy(x):
    return lax.cond(x > 0, lambda v: jnp.sqrt(v), lambda v: -v, x)

jax.make_jaxpr(jax.vmap(branchy))(jnp.ones(4))
{ lambda ; a:f32[4]. let
    b:bool[4] = gt a 0.0:f32[]
    c:i32[4] = convert_element_type[new_dtype=int32 weak_type=False] b
    d:bool[4] = eq c 0:i32[]
    e:f32[4] = stop_gradient a
    f:f32[4] = select_n d e a
    g:f32[4] = neg f
    h:bool[4] = eq c 1:i32[]
    i:f32[4] = stop_gradient a
    j:f32[4] = select_n h i a
    k:f32[4] = sqrt j
    l:f32[4] = select_n c g k
  in (l,) }

The cond is gone. Both branches, neg and sqrt, run on all four elements, and select_n keeps the right one per element: J2's jnp.where. The stop_gradient lines feed each branch the inputs that belong to the other branch without letting them carry a gradient, which defuses J3's where trap. The cost is that an expensive branch is now paid by every element. If you batch a cond to skip work, the work is no longer skipped.

lax.while_loop waits for the slowest element. A loop that counts the steps of the Collatz sequence until it reaches 1 needs 0 steps for 1, 7 for 3 and 111 for 27. Vmapped over [1, 2, 3, 6, 7, 27], it returns the right counts, [0, 1, 7, 8, 16, 111]. It gets them by running the body on the whole batch until every element is done, freezing finished elements with a select. Every element pays for 111 iterations.

Part 5

Composing transformations

Per-example gradients. jax.grad(loss) differentiates a loss for one example; vmapping it gives one gradient per example, something a framework built around a batch-mean loss makes awkward:

def loss(w, x, y):
    return (jnp.dot(w, x) - y) ** 2

jax.vmap(jax.grad(loss), in_axes=(None, 0, 0))(w, Xs, Ys)   # one row per example

For w = [1, -1] and three examples this gives [[-2, -4], [6, 2], [0, -6]], whose mean, [1.333, -2.667], is the gradient of the mean loss, as linearity requires. Per-example gradients are used for differentially private training, for spotting examples that pull a model the wrong way, and for the variance of a stochastic gradient.

jacfwd is vmap of jvp. J3's forward mode computes one Jacobian column per sweep. Feed it all the unit vectors at once and the columns come out together:

jax.vmap(lambda t: jax.jvp(g, (x,), (t,))[1], out_axes=1)(jnp.eye(2))   # equal to jax.jacfwd(g)(x)

That is how JAX implements jacfwd; jacrev is vmap of vjp over the rows. The two match bit for bit on the example in j4_numbers.py.

Nesting and jit. vmap(vmap(f, in_axes=(None, 0)), in_axes=(0, None)) maps over two axes: all pairs (exercise 1). And jax.jit(jax.vmap(f)) compiles the batched program once per batch size; every timing below is of such a function.

Part 6

What a batch buys

The test: run B Kalman filters, each over its own 1000 measurements, with the repository's run_linear_kf. Either a Python loop of B calls to jax.jit(run_linear_kf), or one call to jax.jit(jax.vmap(run_linear_kf, in_axes=(0, None, None, None, None, None, None))), which maps over the measurements and shares the model. The results are identical: filter 37 of a batch equals its own single run exactly. Timed on the laptop CPU used for this course:

Filters BLoop of jitted callsOne vmapped callSpeed-upLog scale: loop, vmap

For one filter the two are the same, as they should be. The loop's time grows in proportion to B: 0.7 ms a filter, nearly all of it dispatch and the overhead of a sequential scan over 2 × 2 matrices. The batched call grows far more slowly, because each of the 1000 scan steps now does 1000 filters' arithmetic in one operation, and the per-step overhead is shared: 1000 filters cost 8.2 ms instead of 692, 85 times less. Ten thousand cost 107 ms. On a GPU, where a single 2 × 2 filter would leave almost all of the hardware idle, the gap would be wider still.

Part 7

Back to Kalman

The unscented filter's two vmaps. unscented_kf_predict pushes its five sigma points through the motion model with jax.vmap(f)(sigma_points): f is written for one state, which is how a user would write a motion model. Then it forms the five outer products for the covariance with jax.vmap(lambda diff: jnp.outer(diff, diff))(diffs). The jaxpr of the second is

{ lambda ; a:f32[5,2]. let
    b:f32[5,2,1] = broadcast_in_dim[broadcast_dimensions=(0, np.int64(1))] a
    c:f32[5,1,2] = broadcast_in_dim[broadcast_dimensions=(0, np.int64(2))] a
    d:f32[5,2,2] = mul b c
  in (d,) }

which is exactly the hand-written diffs[:, :, None] * diffs[:, None, :], or jnp.einsum("ni,nj->nij", diffs, diffs): all three give the same array. vmap wrote J1's broadcasting for you.

Is the filter honest about its uncertainty? A Kalman filter reports an estimate \hat x_k and a covariance P_k that claims how wrong the estimate is. If the claim is right, the normalised estimation error squared

\epsilon_k = (x_k - \hat x_k)^\top P_k^{-1} (x_k - \hat x_k)

follows a chi-square distribution with 2 degrees of freedom, so its average over many independent runs should be 2 at every step [5]. That needs the true state, which only a simulation has, and many runs, which is where vmap comes in: 1000 simulated runs of chapter 02's model, 200 steps each, filtered in one call. The test can also be run on the innovations, which real data does have: the normalised innovation squared v_k^2 / S_k should average 1. Below, the filter assumes noise levels that are a multiple of the true ones. Choose the multiples and see whether the tests notice.

Average NEES (expect 2) and average NIS (expect 1) over 1000 runs, step by step, with the 95% band for a correct filter

average NEES over all steps– average NIS over all steps– steps with NEES inside its band– steps with NIS inside its band–

With the true noise levels the average NEES over all steps is 2.002 and the average NIS 1.002, and 195 of the 200 steps fall inside the 95% band, as about 190 should: the filter is consistent. Underestimate the process noise and the NEES climbs (4.44 at half, 13.2 at a quarter): the filter is overconfident. Overestimate it and the NEES falls below 2: it is too cautious. The NIS, the test available on real data, catches errors in the measurement noise at once, but it barely notices the process noise: with \sigma_a four times too large it reads 0.954, inside its band at 168 of 200 steps, while the NEES reads 1.14. Averaged over all 200 000 innovations the shortfall does show, since a consistent filter's average would lie between 0.994 and 1.006; so the NIS can detect it, but only with a great deal of data, where the NEES sees it at every step. Innovations are dominated by the measurement noise, so they say little about a process noise this small. That is a property of this model, worth knowing before trusting an NIS test on chapter 04's real data.

J3's question, answered. J3 estimated the two noise levels from chapter 02's 1000 measurements by maximum likelihood and found \sigma_z = 0.513, close to the true 0.5, but \sigma_a = 0.061, far from the true 0.1. Bad luck, or a biased method? One record cannot say; a thousand can. The repository's generator is a Python loop that vmap cannot batch efficiently, so j4_numbers.py rewrites it as a lax.scan with the same keys and draws; for key 42 it reproduces chapter 02's data exactly. Then jax.vmap(fit) runs J3's estimate, 12 Newton steps each with a gradient and a Hessian through 1000 filter steps, on the datasets for keys 0 to 999. All 1000 converge, in 12 seconds for the lot.

The estimate is centred on the truth: the median \hat\sigma_a is 0.099 and the median \hat\sigma_z 0.4996. It is also spread out, as J3's Hessian predicted: 90% of the \hat\sigma_a lie between 0.073 and 0.125, while the \hat\sigma_z lie between 0.481 and 0.518. Chapter 02's 0.061 is the 7th lowest of the 1000. The method is fine; key 42 is a dataset that comes up less than once in a hundred. Without vmap this would have taken a thousand-iteration Python loop, or a rewrite of the fitting code with a batch axis through the filter, its gradient and its Hessian.

Part 8

Check your understanding

1. What does vmap produce, and how does it differ from a loop?

A function whose program applies each operation to the whole batch, produced by tracing the per-example function once and applying each primitive's batching rule. The values equal the loop's; the program has no loop over the batch, so its length does not grow with the batch size and each operation processes all elements at once.

2. What does in_axes=(0, None) mean?

Map over axis 0 of the first argument; pass the second argument unchanged to every element. None marks shared arguments such as model matrices.

3. Batching only x in linear_kf_predict, why does P_pred come out as 1000 identical matrices?

P_pred does not depend on x, so it is computed once, but out_axes=0 gives every output a batch axis, so vmap broadcasts it. Setting out_axes=(0, None) would return it once.

4. Why does a vmapped lax.cond whose condition depends on the batched input run both branches?

Different elements may need different branches, and a program without a loop over the batch cannot take one path for some elements and another for the rest. So both branches are computed for all elements and a select keeps the right result for each. If the condition does not depend on a batched value, vmap keeps the cond and only one branch runs, on the whole batch.

5. How is jax.jacfwd built from other transformations?

As vmap of jvp over the unit vectors: each JVP gives one Jacobian column, and vmapping computes them all in one batched sweep.

6. One vmapped call runs 1000 filters 85 times faster than a loop of 1000 jitted calls. Where does the saving come from?

The loop pays the per-call dispatch and the per-step overhead of a sequential scan 1000 times, each time for one 2 × 2 filter. The batched call pays them once, and each of its scan steps does 1000 filters' arithmetic as one array operation.

7. What does the average NEES test, and why can it only be run in simulation?

Whether the filter's covariance matches its actual errors: for a consistent filter the NEES averages the state dimension, here 2. It needs the true state, which only simulated data provides; on real data the NIS, built from innovations, is the substitute.

8. Was chapter 02's estimate \hat\sigma_a = 0.061 evidence that maximum likelihood is biased here?

No. Over 1000 datasets from the same generator the estimates centre on 0.099, with 90% between 0.073 and 0.125. Chapter 02's dataset is the 7th lowest: an unlucky record, not a biased method.

    Hint

    How large is R here? How large is the predicted position variance once the filter has settled?

    Solution

    Average NEES 1.14 against 2.00, average NIS 0.954 against 1.002. Once the filter has settled, the innovation variance is R = 0.25 plus a predicted position variance of 0.030.   5. Make the generator batchable. Rewrite generate_linear_synthetic_data with lax.scan so that it can be vmapped over keys, and check that it reproduces the original for key 42.
    Hint

    Carry the key and the state. Split the key exactly as the original does, in the same order, so that every draw is the same.

    Solution

    The maximum difference from the original's measurements is 0.0. Then jax.vmap(generate_scan)(keys) makes a thousand datasets in one call.

    def generate_scan(key, n_steps=1000):
    def step(carry, _):
        key, x = carry
        key, process_key = jax.random.split(key)
        x = F @ x + jax.random.multivariate_normal(process_key, jnp.zeros(2), Q)
        key, measurement_key = jax.random.split(key)
        z = H @ x + jax.random.normal(measurement_key, (1,)) * 0.5
        return (key, x), (x, z)
    _, (xs, zs) = jax.lax.scan(step, (key, jnp.array([0.0, 1.0])), None, length=n_steps)
    return xs, zs
Part 10

The chapter on one page

  1. vmap turns a function written for one input into one for a batch, with the loop's values and without a loop in the program.
  2. It works by tracing with tracers that carry a batch axis; each primitive's batching rule rewrites it: elementwise operations stay, matrix products gain batch dimensions or free axes, axes are renumbered.
  3. in_axes names the mapped axis of each argument, None for shared ones; out_axes places the batch axis in each output. Mapped axes must share one length.
  4. Control flow: a cond whose condition depends on the batch runs both branches and selects; a while_loop whose condition does runs until the slowest element finishes.
  5. Composition: vmap(grad(f)) gives per-example gradients, jacfwd is vmap(jvp), nested vmap gives all pairs, and jit(vmap(f)) compiles the batch.
  6. In the Kalman code: 1000 filters run in 8.2 ms batched against 692 ms in a loop; over 1000 runs the filter is consistent (average NEES 2.002), and the NIS barely notices an overstated process noise; J3's estimator centres on the true \sigma_a, and chapter 02's 0.061 is the 7th lowest of 1000.

Part 11

Scope and further reading

Scope. This chapter covers vmap, its arguments and errors, how it treats control flow, its composition with grad, jvp and jit, its speed on batched filters, and two Monte Carlo uses in Kalman filtering. Not covered: axis_name and collective operations inside vmap, jax.lax.map for batches too large for memory, sharding a batch across devices, and custom batching rules.
