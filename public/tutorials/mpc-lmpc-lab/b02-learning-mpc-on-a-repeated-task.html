Advanced MPC and Learning MPC · Part B, Labs · Chapter B2 of 6

Learning MPC on a repeated task

Chapter A11 designed the terminal set and terminal cost by hand, from a Riccati equation and an invariant polytope. Chapters A12 and A13 showed how successful runs supply them instead. This lab runs the loop. A two-step MPC with no terminal ingredients produces a feasible but poor first run of the course's cart: it coasts, overshoots and costs 69 percent more than the optimum. Learning MPC stores it, learns from it, and with a four-step horizon reaches the long-horizon optimum to nine decimals in three iterations; with a two-step horizon it stops short, and the lab shows why. Below, the whole experiment runs live.

Part 1

The task, the reference and the seed

The task. The canonical cart of chapter A1, repeated from x_S = (-3.5, 2.5): moving right at 2.5 near the left wall, to be brought to rest at the origin. Every run stops once \|x\| \le 10^{-3} and is completed by the two deadbeat inputs of chapter A12, so that it ends exactly on the target. The stage cost is the course's, q(x, u) = x^\top Q x + R u^2; there is no \ell_1 term, so the online problems are plain quadratic programs.

Long-horizon reference. A common benchmark is one open-loop solve with a very long horizon as a proxy for the infinite-horizon optimum. Here the computation is kept light by checking convergence in the horizon instead:

N_{\mathrm{ref}} open-loop cost terminal norm
10 16.636214648 7 \times 10^{-4}
20 16.636214709 7 \times 10^{-9}
30 16.636214709 6 \times 10^{-12}
40 16.636214709 1 \times 10^{-11}

The value has converged to nine decimals, so N_{\mathrm{ref}} = 30 is the reference for the rest of the lab: J^\star = 16.636215. It is a numerical reference, not a proof that a finite horizon equals the exact infinite-horizon optimum; with N = 10 the plan cannot quite reach the origin, which is why its cost is a hair lower.

A feasible but suboptimal seed. LMPC needs one successful trajectory. Plain receding-horizon MPC with horizon 2 and no terminal cost or constraint provides it: 20 inputs, cost 28.087, 68.8 percent above the reference. Its first input is 0. With two steps and no terminal cost the objective contains q(x_0, u_0) + q(x_1, u_1), and x_1's position does not depend on u_0 at all for this discretisation's first step beyond the u_0 / 2 term, so braking buys almost nothing the horizon can see: the cart coasts to (-1, 2.5), overshoots to p = 2, and spirals back. That is the horizon-one pathology of chapter A6 in a milder form. With horizon 3 the seed would cost 17.028, only 2.4 percent above; with horizon 5, 16.636235, within 2 \times 10^{-5}. The lab keeps the two-step seed because it leaves something to learn, and chapter A6's point stands: the horizon is a lever, and this seed has it set short on purpose.

Complete task cost against open-loop objective. One N = 2 solve prices two stages. The seed's closed-loop cost accumulates the whole repeated execution until the target. Learning curves compare complete iteration costs, never open-loop objectives.

The database. The controller stores, for every successful run, the states, the applied inputs and the backward costs-to-go, with the target stored once with value zero. After the seed: 1 trajectory, 21 safe samples (the target plus 20 states), stored cost 28.087, costs-to-go along it 28.087, 14.587, 12.137, 10.487, 6.237, 1.987, 0.393, … The database is chapter A12's add_trajectory and safe_data.

Part 2

The first LMPC solve

The explicit horizon is now 4, but the terminal set and value carry information beyond those four steps. From x_S the first LMPC input is u_0 = -0.794, where the seed chose 0. The predicted terminal state, (0.061, -0.023), is exactly stored state 11 of the seed, weight 1 and stored value 0.006: the four-step plan brakes hard and reaches a point eleven steps down the slow run from which the stored continuation costs almost nothing. The objective, four stage costs plus \lambda^\top V, is 16.644, against the stored 28.087.

Why braking is suddenly worth it. The seed judged u_0 = 0 best because its two-step objective charged the input and credited nothing for arriving earlier. LMPC charges the same stage costs and adds \lambda^\top V, the stored cost of finishing the task from x_N: landing far along the seed path buys a much cheaper continuation, and the price of the braking is nothing compared to it. The information came entirely from one slow run.

Part 3

The learning iterations

Each iteration resets to x_S, solves the LMPC problem at every step with the shifted warm start of chapter A13, reaches the target, closes with the exact bridge, appends the new successful trajectory and updates the costs-to-go. The online QP uses the target plus the most recent four trajectories; the full history is kept for analysis. Nine iterations, three horizons:

The gap is relative, (J^j - J^\star) / J^\star. The seed is iteration 0; every later row is the complete cost of one new LMPC execution. For every horizon the first iteration removes almost all of the excess, 99.7 percent of it for N = 2 and 99.9996 percent for N = 4, because the stored seed already contains a whole safe path and its costs-to-go. Then the horizons part ways. With N = 4 the gap keeps falling, by a factor of about a hundred per iteration, to the solver's floor of 5 \times 10^{-10} by iteration 4, and the first input settles from -0.794 to -0.783; the trajectory joins the reference. With N = 3 and N = 2 the cost stops after the first iteration, 0.13 and 0.30 percent above the optimum, and the first input never moves again. Part 6 shows that the plateau is real.

Never an increase. Over all 27 iterations the largest iteration-to-iteration change in the wrong direction is +8 \times 10^{-8} for N = 2 and +6 \times 10^{-10} for N = 4, the solver's tolerance on a cost of 16.6 and not a counter-example to the non-increase result of Part 7. Every iteration takes 9 inputs for N = 2 and 11 for the other two, the last two being the bridge.

Part 4

Anatomy of the learning

Phase plane and inputs. The seed curls slowly across the plane, saturates on 4 of its 20 inputs and spends most of its cost after the overshoot. The first LMPC iteration already lies close to the reference: it brakes at once, -0.794, and from then on the learned trajectories are visually indistinguishable from the reference and from each other, consistent with costs differing in the sixth decimal. The last iteration saturates on 1 of its 11 inputs, like the reference.

Safe-set growth, or rather the lack of it. Every successful run adds its states to the database and can enlarge or reshape the convex hull. Here it never does: the hull has area 10.25 after the seed and 10.25 after nine iterations, because the slow seed's overshoot to p = 2 already encloses every faster run (chapter A12 made the same observation). Yet the cost falls from 28.09 to 16.636215. The hull is only half of the learning, and on this task none of it: LMPC also learns better costs-to-go, and even when the geometry is fixed from the start, improved terminal values alter the short-horizon decision.

Stored costs-to-go. The cost-to-go along each stored trajectory is computed backwards, J_T = 0, J_t = q(x_t, u_t) + J_{t+1}. The recursion residual on the last iteration is 3 \times 10^{-17}, round-off. The curve t \mapsto J_t is the learned value function sampled along one run; J_0 is the iteration cost that the learning curve plots. The seed keeps half of its cost for after the overshoot; the learned run pays almost all of it in the first braking steps.

Part 5

Data growth and the window

If every state of every run is kept, the number of barycentric variables grows with the total sample count: each active safe-state sample is one \lambda_r in the QP. One remedy is a time-varying subset,

TS_t^{l,j} = \Big( \bigcup_{i=l}^{j} \bigcup_{s=t}^{T_i} \{x^i[s]\} \Big) \cup \mathcal O,

which keeps only iterations l, \ldots, j and, from each, only the states visited at time t or later. The lab's controller uses the iteration window alone, the most recent four trajectories, and keeps all time indices. The previous iteration is always retained, which the cost-improvement argument of Part 7 needs.

Same costs, smaller problem. With every stored trajectory active, the five first iteration costs for N = 4 agree with the window's to the last printed decimal (the first four are identical by construction, since until then the window holds every trajectory). The number of barycentric variables grows from 32 to 76 by iteration 5 instead of staying at 45, and the mean solve time per QP in Python grows from 1.9 to 5.6 ms instead of staying near 3. Nothing is lost by the window here, and the online problem is bounded. The lab keeps the full history for analysis; the controller never sees it.

Part 6

The plateau, checked by brute force

For N = 2 and N = 3 the cost stops after one iteration. The guarantees of Part 7 say nothing about the limit; chapter A13 already warned that the learned value is pessimistic between data, an upper bound of the true cost-to-go built from runs that were not optimal. The question is whether the plateau is a property of the controller or an artefact of the solver.

A search that uses no solver. Take the data after the last N = 2 iteration, grid the two inputs (u_0, u_1) over [-1, 1]^2 at 41 by 41 points, evaluate the two stage costs plus the learned terminal value V_c(x_2) at every admissible grid point by its linear program, and refine the grid three times around the best point. The best plan the grid finds costs 16.685571 at (u_0, u_1) = (-0.8686, -1), against the stored run's 16.685473 with its first two inputs -0.8686 and -1: the same plan to the grid's resolution, one part in 10^5 above it. So with the data it has, the two-step controller cannot do better than what the solver returns: the plateau 0.30 percent above J^\star is a property of the pessimistic learned value, not of the optimiser. A longer horizon escapes it because it can reach stored states that are further along, and cheaper, than any two steps can; N = 4 reaches the optimum, and a different seed does too (exercise 7).

Reading it as a theorem and an observation. The theory promises that the cost never increases and that every iteration is feasible; it does not promise convergence to J^\star, and this lab shows both halves at once: non-increase for every horizon, convergence for one of them. Even so, the N = 2 limit is only 0.30 percent above the optimum, against 69 percent for the trajectory that produced the first data.

Part 7

What is guaranteed, what is observed

Guaranteed (under the deterministic repeated-task assumptions of chapters A12 and A13): every iteration is recursively feasible and reaches the target; the previous successful trajectory remains a feasible candidate for the next iteration, since its terminal state is in the hull and its continuation is stored, so the LMPC objective at x_S is at most the stored cost and J^{j+1}(x_S) \le J^j(x_S); and since each iteration is admissible, J^j(x_S) \ge J^\star(x_S). The costs therefore converge.

Observed, not promised: that the N = 4 trajectories approach the long-horizon reference to 5 \times 10^{-10}; that the first iteration removes almost all of the gap; that the hull never changes; that the N = 2 limit is within 0.30 percent. A different task, cost or seed could change every one of these numbers without touching the guarantees.

Do different seeds converge to the same solution? LMPC only needs an initial feasible successful trajectory, from plain MPC, a saturated LQR, a demonstration or anything else. From the three-step seed, 2.4 percent above the optimum, N = 4 reaches 16.636227 after one iteration and 16.636215 from the second on: the same limit to nine decimals as from the two-step seed (exercise 7). That is evidence of initialisation independence for this convex task and this horizon, not a theorem: nothing in the theory says that different seeds must meet, and the N = 2 controller shows that the same data can lead to different limits for different horizons.

Part 8

What is learned, and what is not

The plant model is not learned. A and B are known and used explicitly in every online QP. What is learned: safe terminal geometry, successful continuation inputs, and terminal cost-to-go information. Data-driven, not model-free; chapter B4 adds model learning on top, for a car whose model is not known.

LMPC is not DQN. A deep Q-network learns an action-value approximation with a neural network and temporal-difference updates (chapter B5). This LMPC keeps an explicit model and explicit constraints, solves an optimisation online, and uses data only to build terminal ingredients. The two are related through value information, not through the algorithm.

LMPC against iterative learning control. Both exploit repetition. Classical ILC updates a trial-indexed input signal from one execution to the next; LMPC inserts learned trajectory information into a constrained receding-horizon problem. Its distinctive object is the learned terminal set and value pair.

What the experiment establishes. The short-horizon seed is feasible but expensive; successful data provide terminal geometry and cost-to-go; the LMPC terminal state satisfies a barycentric safe-set constraint; repeated executions reduce the complete task cost; the learned trajectories approach the long-horizon reference for a long enough horizon; the modelled constraints are satisfied throughout. What it does not establish: robustness to disturbances or model mismatch, safety of arbitrary nonlinear convexification, global-optimality convergence for every LMPC problem, model-free learning, or transfer to other initial conditions without further analysis.

Part 9

The code behind it

Every step of every iteration starts the solver from the shifted sequence of chapter A13, which the package builds from the previous solution.

advanced_mpc_lmpc/lmpc.py · LMPCController.shifted_warm_start

    def shifted_warm_start(self, x_next, solution):
        lam = solution.lambdas
        Usafe = solution.safe_inputs
        nxt = solution.next_index
        S = solution.safe_states

        u_terminal = lam @ Usafe

        U_shift = np.vstack([
            solution.U[1:],
            u_terminal.reshape(1, -1),
        ])

        lam_shift = np.zeros(len(S))
        np.add.at(lam_shift, nxt, lam)

        return self._pack_warm(
            np.asarray(x_next, float),
            U_shift,
            lam_shift,
            S,
        )

The appended input is lam @ Usafe, the mixture of the stored continuation inputs with the terminal weights of the last solve, and the new input sequence is the old one shifted by one with that input at the end. The new weights are built by np.add.at(lam_shift, nxt, lam): each old weight moves from its stored state to that state's stored successor, so the new terminal guess is exactly the mixture of stored successors that the recursive-feasibility proof names. The interior-point solver of chapter A4 does not need a warm start to converge, but the shifted point is also the proof's feasible candidate, which is why the loop keeps it: if the solver ever failed, this sequence could be applied as it is.

Part 10

Common pitfalls

  1. "Every stored state is optimal." No: stored states are safe because they belong to successful runs, and the seed is very suboptimal.
  2. "The convex hull is always safe." No: the proof relies on linear dynamics and convex constraints (chapter A12).
  3. "The terminal value is a neural network." Not here: barycentric interpolation of stored roll-out costs.
  4. "Hull growth explains the learning." On this task the hull never grows and the cost falls by 41 percent: the learned values do the work.
  5. "The long-horizon reference proves the exact infinite-horizon optimum." It is a finite-horizon proxy whose convergence was checked to nine decimals.
  6. "A two-step horizon only sees two steps ahead." Only the explicit prediction is two steps long; the terminal constraint links it to stored continuations that reach the target and the terminal cost prices the remainder, which is why LMPC with N = 2 beats the seed with the same horizon by 41 percent.
  7. "Non-increasing cost means convergence to the optimum." No: N = 2 and N = 3 never increase and never reach it.
Part 11

Check your understanding

Try to answer each question before opening it.

1. Why does the two-step seed apply u_0 = 0 first?

Its objective prices only two stages and has no terminal cost, so braking is charged now and credited nothing later; the cheapest two-step plan coasts.

2. Why can a horizon-four LMPC outperform the horizon-two seed from the same start?

The learned terminal set and value communicate information about safe and costly behaviour beyond the explicit window. From x_S the seed applies 0 and LMPC applies -0.794 for exactly that reason.

3. What is compared on the learning curve?

Complete closed-loop task costs of whole iterations, never the open-loop objective of one solve.

4. Why does the first iteration remove almost all of the gap?

Because the stored seed already contains an entire safe path to the target with its costs-to-go; the horizon only has to reach it.

5. Why is the previous iteration a feasible candidate for the next?

Its terminal state is in the hull, its continuation inputs are stored, and the shifted sequence of chapter A13 reaches a mixture of stored successors.

6. Does monotone iteration cost imply global optimality?

No. Performance improvement and convergence to a global optimum are different statements; N = 2 shows the first without the second.

7. Why does the QP grow with experience, and what bounds it?

Each active safe-state sample contributes one barycentric variable; a window of recent trajectories bounds the count while keeping the previous iteration, which the improvement argument needs.

8. Why did the hull never change here?

The slow seed overshoots to p = 2 and returns at v = -1.5, exploring more of the plane than any faster run; the good runs lie inside its hull.

9. What did the brute-force search establish?

That with the learned value after the last N = 2 iteration, no admissible two-step plan from x_S costs less than the stored run: the plateau is in the data and the horizon, not in the solver.

10. Is the model learned?

No. A and B enter every online QP; only the terminal ingredients are learned.

Part 12

Exercises

Each exercise has a hint and a solution; the code runs with the course package installed. Try first, then peek.

  1. The seed by hand. Show that from x_S = (-3.5, 2.5) the two-step MPC with no terminal cost applies u_0 = 0.

    Hint

    Write the two-step objective q(x_0, u_0) + q(x_1, u_1) with x_1 = (-3.5 + 2.5 + u_0/2,\ 2.5 + u_0) and minimise over u_1 first.

    Solution

    x_0 is a constant, so the objective is 0.2u_0^2 + (-1 + u_0/2)^2 + 0.2(2.5 + u_0)^2 + 0.2u_1^2, minimised over u_1 at u_1 = 0. In u_0 the derivative is 0.4u_0 + (-1 + u_0/2) + 0.4(2.5 + u_0) = 1.05u_0, zero at u_0 = 0, and the constraints |x_1| \le (4, 3) hold there. The horizon sees the position improve by moving right (it is at -3.5) and the velocity cost barely weighted, so the cheapest move is to do nothing. The lab's first stored states, (-1, 2.5) then (1, 1.5), follow.

  2. Horizon of the seed. Repeat the seed experiment with plain MPC horizons 2, 3 and 5 and compare complete closed-loop task costs.

    Hint

    Set the seed horizon in the demo; the numbers script prints the three.

    Solution

    N = 2: cost 28.087, gap 68.8 percent. N = 3: 17.028, 2.4 percent. N = 5: 16.636235, within 2 \times 10^{-5} of the reference: plain MPC with five steps is essentially optimal on this task, which is why the lab seeds with two. The horizon is a lever on the seed as on everything else.

  3. The first learned move. With the two-step seed stored, solve the LMPC problem once from x_S for N = 2, 3, 4 and report the first input, the terminal state and the active weights.

    Hint

    LMPCController.solve(x_S) returns U, terminal_state and lambdas.

    Solution

    N = 2: u_0 = -0.869, terminal state (-0.303, 0.631), two weights, 0.166 on (-1, 2.5) and 0.834 on (-0.164, 0.26). N = 3: u_0 = -0.839, terminal state (0.061, -0.023), stored state 11 with weight 1. N = 4: u_0 = -0.794, the same terminal state and weight. The longer the horizon, the further down the seed its plan can reach, and the more gently it needs to brake.

  4. Database size. Compare all-data against windowed safe sets for N = 4: iteration costs, barycentric variables and solve time.

    Hint

    last_n_trajectories=None against 4; time each solve.

    Solution

    Five iterations: the costs agree to the sixth decimal (16.636970, 16.636224, 16.636215, …), the number of barycentric variables grows 32, 43, 54, 65, 76 against 32, 43, 54, 45, 45, and the mean solve time per QP in Python grows from 1.9 to 5.6 ms against about 3 ms with the window. The window costs nothing here and bounds the online problem.

  5. Hull growth. Compute the hull area of the stored states after the seed, after one, three and nine iterations.

    Hint

    scipy.spatial.ConvexHull(points).volume is the area in the plane; stack the stored states of the first k trajectories with the origin.

    Solution

    10.25, 10.25, 10.25 and 10.25. The seed's overshoot encloses every later run, so the terminal set is complete after one trajectory and the learning is entirely in the stored values, which fall from 28.09 to 16.636215 at x_S and correspondingly along the path.

  6. The plateau. Reproduce the brute-force check for N = 2 and explain what it does and does not show.

    Hint

    Grid (u_0, u_1), evaluate the two stage costs plus convex_safe_value at x_2, refine around the best.

    Solution

    The search finds no admissible two-step plan from x_S cheaper than the stored run with the learned value after iteration 9, to the grid's resolution of 10^{-3} in each input. It shows that the solver returned the true minimiser of the problem it was given; it does not show that the plateau is a feature of Learning MPC in general. With N = 4 the same data support a plan that reaches the optimum, because a four-step plan can land on stored states that two steps cannot.

  7. A different seed. Seed with the three-step plain MPC run instead and rerun N = 4 for five iterations. Does the experiment prove initialisation independence?

    Hint

    seed_run(3) in the numbers script.

    Solution

    Costs 17.027694 (seed), 16.636227, 16.636215, 16.636215, 16.636215, 16.636215: the same limit to nine decimals as from the two-step seed, reached one iteration sooner. That is evidence of initialisation independence for this convex task and this horizon, not a proof: the theory guarantees non-increase from each seed and nothing about where the sequences end, and the N = 2 controller lands elsewhere from the same data.

  8. Model mismatch. If the real system is x^+ = (A + \Delta A)x + Bu, which line of the convex-invariance proof fails?

    Hint

    The stored successors were produced by the real plant, but the proof multiplies by the nominal A.

    Solution

    The line x^+ = \sum_r \lambda_r (A s_r + B u_r) = \sum_r \lambda_r s_r^+. Replaying the mixture of stored inputs on the true plant gives \sum_r \lambda_r ((A + \Delta A) s_r + B u_r); if the stored successors came from the true plant this still equals \sum_r \lambda_r s_r^+, but the online QP predicts x_N with the nominal A, so the state that actually arrives at time N is not the S^\top \lambda the optimiser planned, and the continuation argument breaks. Either way the certificate rests on the identity between model and plant, which chapter B6 takes up.

Part 13

The chapter on one page

  1. Task: the canonical cart from (-3.5, 2.5) to the origin; reference J^\star = 16.636215, converged to nine decimals at N_{\mathrm{ref}} = 30.
  2. Seed: two-step plain MPC, first input 0, 20 inputs, cost 28.087, 68.8 percent above; 21 stored samples.
  3. First learned move: N = 4 applies -0.794, ends on stored state 11 of the seed, objective 16.644 against the stored 28.087.
  4. Iterations: N = 4 reaches 16.636970, 16.636224, 16.636215, never increasing; N = 3 and N = 2 stall at 0.13 and 0.30 percent above.
  5. Anatomy: the hull never changes (area 10.25 throughout); the stored values fall; the learned run brakes at once and saturates once, like the reference.
  6. Window: four trajectories keep the QP at 45 barycentric variables at equal cost; all data reach 76 by iteration 5.
  7. Plateau: a brute-force search over (u_0, u_1) with the learned value finds nothing cheaper than the stored run; the limit is in the data and the horizon.
  8. Meaning: non-increase and feasibility are theorems; the limit, the first-iteration jump and the fixed hull are observations.

The vocabulary, in one table

Term Meaning here
Seed The first successful trajectory, here from two-step plain MPC.
Long-horizon reference A converged finite-horizon open-loop solve standing in for the infinite-horizon optimum.
Iteration cost The complete closed-loop cost of one run from x_S to the target.
Trajectory window Only the most recent runs enter the online QP.
Plateau An iteration cost that stops improving because V_c over-estimates the tail between data.
