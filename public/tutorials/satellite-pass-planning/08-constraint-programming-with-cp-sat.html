Constraint programming with CP-SAT

Chapter 07's greedy collects 193 on the small instance, and its local search reaches 211, but neither can say how far it is from the best plan. This chapter writes the problem as a constraint program and hands it to Google's CP-SAT solver, which returns 219 in under a second together with a proof that nothing better exists. The concept is exact search: exploring all plans implicitly, discarding whole families of them with bounds, until the best plan found and the best bound proved meet. The page reads the repository's model line by line, builds a branch and bound from scratch that you can step through node by node, and explains, without magic, what the solver adds to it.

Part 1

From a rule to a proof

What a heuristic cannot say. Chapter 07 ended with a plan worth 211 and no way to tell whether 211 is the best possible. To know that, you need a statement about every plan, including the 2^{168} subsets nobody will ever list. Such a statement is an upper bound: a number U with a proof that no feasible plan collects more than U.

The crudest bound. Every plan collects at most the total priority of the targets some satellite can see: 316 on the small instance (chapter 05). It is a valid bound, and useless: no plan comes close, because reconfiguration times and budgets forbid most combinations. A better bound must use the constraints.

The certificate. Suppose a solver holds a plan worth 219, checked by the independent checker, and a proof that no plan exceeds 219. Then 219 is optimal, and nothing else needs to be examined. This pair, a lower bound given by a plan and an upper bound given by a proof, is what every exact solver works towards. Their difference is the gap; "OPTIMAL" is the status a solver reports when the gap is zero.

What is exact search?

In plain words: a search that considers every possible plan, most of them without ever writing them down, because it can show that whole families of plans cannot beat the best one already found. When it finishes, its answer comes with a proof.

More precisely: the set of plans is split recursively by decisions ("task o in or out"), forming a tree. At each node, a bound U(\text{node}) on the value of every plan below it is computed. If U(\text{node}) \le the value of the best plan found so far (the incumbent), the node is pruned. The search is complete when no node is left open; at any moment, the largest bound over the open nodes is a global upper bound, and the incumbent a lower bound [3].

Incumbent
The best feasible plan found so far; its value is a lower bound on the optimum.
Best bound
The smallest proven upper bound so far; no plan collects more.
Gap
(\text{bound} - \text{incumbent})/\text{bound}. Zero means proven optimal.
Anytime
A solver that can be stopped at any moment and still return its incumbent and its bound. CP-SAT is one.

The hero demo is such a search on a toy cut from the course's instance: satellite 0 during its first pass, the 21 opportunities whose windows fall in the first 900 s (targets in the Gulf of Guinea and the Bay of Biscay approaches), 1350 s of listening on offer against a power budget of 300 s. With the simplest bound it explores 1311 nodes and proves that 28 is optimal, the same value CP-SAT finds; a complete enumeration would visit 2^{21} = 2{,}097{,}152 subsets. Part 4 explains every control.

Part 2

The model, line by line

A constraint program is a list of variables, each with a finite set of allowed values (its domain), a list of constraints relating them, and an objective. You state the problem; the solver searches. satplan/cpsat.py builds the model in thirty lines. Each construct is new; take them one at a time.

Two variables per opportunity

m = cp_model.CpModel()
opps = inst.opportunities
x = [m.new_bool_var(f"x{o.idx}") for o in opps]
s = [m.new_int_var(o.earliest_start, o.latest_start, f"s{o.idx}") for o in opps]

x_o \in \{0, 1\} says whether opportunity o is used. s_o is its start time in whole seconds, with domain [e_o, \ell_o], from the window start to the latest start that still fits the task: on the small instance a domain holds 118 values on average. Integer seconds are exact here because every window edge is on the 10 s grid and every duration and reconfiguration time is a whole number of seconds (chapters 04 and 06). The domain already encodes the window constraint; nothing else is needed for it.

Optional intervals and NoOverlap

if use_no_overlap:  # redundant with the pairwise precedences, but propagates globally
    for ids in inst.by_satellite().values():
        m.add_no_overlap(
            m.new_optional_fixed_size_interval_var(s[i], opps[i].duration, x[i], f"iv{i}") for i in ids
        )

An interval variable bundles a start, a size and an end = s_o + d_o. "Fixed size" means the size is the constant d_o. "Optional" means the interval has a presence literal, here x_o: if x_o = 0 the interval is absent and every constraint on it is ignored. add_no_overlap over a satellite's intervals says that the present ones do not overlap in time. It knows nothing of reconfiguration times, which the pair constraints below add, so it is redundant: the precedences already forbid every overlap it forbids. It is kept because it is a global constraint. A pairwise precedence looks at two tasks; NoOverlap looks at all tasks of a satellite at once and can deduce, for example, that three tasks whose windows fall in a 100 s stretch cannot all fit there, which no single pair reveals. On the small instance with one worker (deterministic), removing it raises the search from 141,598 to 237,535 branches and from 25,150 to 82,199 conflicts; the repository's README reports that on the medium instance its effect on the value is within run-to-run noise.

One collection per target: AtMostOne

for ids in inst.by_target().values():
    if len(ids) > 1:
        m.add_at_most_one(x[i] for i in ids)
\sum_{o \in \text{opp}(j)} x_o \le 1 \quad \text{for each target } j.

47 targets have two or three opportunities and get a constraint; the 67 with a single one need none. AtMostOne is a specialised form the solver handles as a clique of pairwise exclusions: setting one literal to true sets all the others to false at once.

The three kinds of conflict pairs

Chapter 06's sweep lists every pair of opportunities on the same satellite whose placements can interfere (876 on the small instance), and classifies them by which orders can fit at all. Write g_{ab} = d_a + s(a,b) for the minimum time between the start of a and the start of b if a goes first.

for p in inst.pairs:
    a, b = p.a, p.b
    gab = opps[a].duration + p.s_ab
    gba = opps[b].duration + p.s_ba
    if not p.a_first_ok and not p.b_first_ok:
        m.add_bool_or([x[a].Not(), x[b].Not()])
    elif p.a_first_ok and not p.b_first_ok:
        m.add(s[b] >= s[a] + gab).only_enforce_if([x[a], x[b]])
    elif p.b_first_ok and not p.a_first_ok:
        m.add(s[a] >= s[b] + gba).only_enforce_if([x[a], x[b]])
    else:
        before = m.new_bool_var(f"o{a}_{b}")
        m.add(s[b] >= s[a] + gab).only_enforce_if([x[a], x[b], before])
        m.add(s[a] >= s[b] + gba).only_enforce_if([x[a], x[b], before.Not()])

Neither order fits (106 pairs): the two cannot both be selected, the clause \lnot x_a \lor \lnot x_b. A clause is an "or" of literals, the basic constraint of SAT solvers.

Only one order fits (414 pairs): if both are selected, that order holds, s_b \ge s_a + g_{ab} (or the mirror).

Both orders fit (356 pairs): a new Boolean o_{ab}, the order literal, says which comes first, and each order is enforced under its own condition. That is 356 order literals and 712 precedences.

Half-reification. The method only_enforce_if(lits) attaches enforcement literals to a constraint: the constraint must hold when all the literals are true, and is switched off otherwise. In logic,

(x_a \land x_b \land o_{ab}) \;\Rightarrow\; s_b \ge s_a + g_{ab}.

This is an implication, not an equivalence: it is called half-reification because the reverse direction is not imposed (two tasks may happen to be well separated without being selected). The solver propagates it both ways: when the three literals are true, it tightens the start-time domains; when the inequality cannot hold within the current domains, it deduces that the three literals cannot all be true. The widget in Part 3 does exactly that on a real pair. A MILP has to write the same implication with a big-M, which chapter 09 shows is much weaker.

Budgets as knapsacks

for _, limit, ids in inst.budget_groups():
    m.add(sum(opps[i].duration * x[i] for i in ids) <= limit)
\sum_{o \in G} d_o\, x_o \le B_G \quad \text{for each power or memory group } G.

One linear constraint per group whose opportunities could overrun the limit if all were chosen (chapter 06): 19 on the small instance, 10 for power (300 s per revolution) and 9 for memory (600 s between contacts). Each is a knapsack constraint.

The objective and the hint

m.maximize(sum(o.weight * x[o.idx] for o in opps))

if hint is not None:

The objective is the total priority \sum_o w_o x_o. A hint is a suggested value for some variables: here the greedy plan of chapter 07, every x_o and the chosen start times. It is not a constraint. The solver tries it first; when it is complete and feasible, it becomes the first incumbent, so the solver never reports a plan worse than the greedy's. The rest of solve_cpsat sets a time limit, 8 parallel workers and a random seed, and records every improving plan with a callback.

Part 3

What the solver does

CP-SAT combines several techniques from different communities: constraint programming, Boolean satisfiability (SAT) and integer programming. The OR-Tools documentation and the authors' talks describe them [1]; this section explains each idea at the level needed to read the solver's behaviour, not its full implementation.

Presolve. Before searching, the solver simplifies the model: it fixes variables whose value is forced, removes constraints implied by others, merges and strengthens what it can. The model it searches is not exactly the one written above.

Propagation: domains shrink. Each constraint has a propagator, a small procedure that removes from the variables' domains the values that the constraint, given the current domains, makes impossible. Take a precedence s_b \ge s_a + g_{ab} that is enforced. Since s_a \ge \min s_a, every value of s_b below \min s_a + g_{ab} is impossible; since s_b \le \max s_b, every value of s_a above \max s_b - g_{ab} is impossible. Propagators run in turn until nothing changes. If a domain becomes empty, the current set of decisions is contradictory: a conflict. Try it on a real pair.

domain of s_a– domain of s_b– g_{ab} / g_{ba} [s]–

Set x_a = x_b = 1 on a "both orders" pair, leave the order undecided, and push the earliest start of a to the right with its slider: at some point "a then b" stops fitting, and propagation sets the order literal by itself, with no search. Push both sliders and neither order fits: a conflict, from which the solver learns a clause. The widget isolates one pair; inside the solver, the earliest starts come from other propagators and decisions, and one deduction triggers others along chains of pairs.

Search: branching. When propagation stops and some variables are still undecided, the solver makes a decision, for example x_o = 1 or s_o \le 2350, propagates its consequences, and continues. If a conflict appears, it undoes decisions (backtracks) and tries otherwise. That is the tree of the hero demo, with far stronger reasoning at each node. With one worker, the small instance is solved in 141,598 branches.

Clause learning: the SAT part. When a conflict occurs, a modern SAT solver does not just backtrack. It analyses which decisions and deductions caused the conflict and records a new clause that rules out that cause everywhere in the search, then jumps back to the decision that made it possible. This is conflict-driven clause learning [5]. CP-SAT extends it to integer variables by expressing bounds such as [s_a \ge 2350] as Boolean literals, so the reasons produced by propagators become clauses too, an approach called lazy clause generation [6]. The widget's learned clause is of that form. While a learned clause is kept, the failure it records is never repeated; the small instance's one-worker run learns from 25,150 of them.

Linear relaxation: the upper bound. Part of the model is linear (the knapsacks, the objective, and linear versions of other constraints). Dropping the requirement that x_o be 0 or 1 gives a linear program whose optimum is an upper bound on every plan, computable by the simplex method. CP-SAT solves such relaxations and adds cuts (inequalities valid for every integer plan that the LP solution violates) to tighten them. The hero demo's third bound is the simplest example: the power budget's linear relaxation, the fractional knapsack of chapter 07, solved exactly by the density rule. Chapter 09 studies relaxations in detail.

Large neighbourhood search: better plans fast. Some workers do not try to prove anything. They take the incumbent, fix most of its variables, free a neighbourhood (for example all tasks of one satellite in a stretch of time), and solve that small problem exactly with a short limit. It is chapter 07's ruin and recreate with an exact solver in place of the greedy refill [7], and it is why incumbents improve quickly even on instances too large to prove.

A portfolio of workers. With num_workers = 8, CP-SAT runs 8 differently configured searches in parallel: some branch on Booleans, some on start times, some work mostly on the LP bound, some run LNS. They share incumbents and bounds, and some of what they learn. On the small instance this is worth a factor of six or seven in wall time: the 1-worker run takes about 3 s on the author's machine when it is otherwise idle, the 8-worker runs about half a second. The price is non-determinism: the threads' interleaving depends on the machine's timing, so two runs with the same seed can return different plans, and, when stopped at a time limit, different values. Part 5 shows two such runs; chapter 10 measures the noise.

Status. When the search ends, solver.status_name(status) is OPTIMAL if the incumbent's value equals the best bound (the search is complete), FEASIBLE if a plan is known but the time limit came first, and INFEASIBLE or UNKNOWN otherwise. The repository returns solver.best_objective_bound along with every plan, so a FEASIBLE result still says how far it can be from the optimum.

Part 4

A branch and bound from scratch

The hero demo is the oldest exact method for integer problems, branch and bound [4], in about sixty lines of JavaScript, with nothing borrowed from CP-SAT. It runs on one satellite, so that "can this set of tasks be scheduled?" stays easy to decide.

Branching. The 21 opportunities are sorted by window start. A node at depth k has decided the first k: for each, taken or left. Its two children decide opportunity k+1. "Take" is possible only if the target is not already served, the power and memory budgets have room, and the task fits after the last task taken: at t = \max(e_o,\ t_{\text{last}} + d_{\text{last}} + s(\text{last}, o)), provided t \le \ell_o. The search is depth first: the most recent node is expanded first, so it reaches complete plans quickly and keeps in memory only the current path and the siblings still to visit.

A restriction, and its check. Taking tasks in order of window start fixes the order of tasks on the satellite. A real plan might put a task with a later window before one with a long, earlier window, so this search could, in principle, miss the optimum. On this toy it does not: ch08_numbers.py solves the same 21 opportunities with CP-SAT and finds 28, the value every setting of the demo reaches, and the page compares its node counts with the Python ones. The restriction is not harmless in general: on satellite 0's stretch from 17,200 to 17,600 s, the same search finds 16 where CP-SAT finds 20, because the best plan there needs an order that window starts do not give. A real solver keeps the order free, which is why the model has order literals.

Three bounds. At each node, an optimistic estimate of the best value reachable below it:

  • All remaining: the value so far plus the priority of every target among the undecided opportunities. It ignores every constraint.
  • What still fits: the same, counting only the opportunities that could still be taken on their own (budget, window and reconfiguration time after the last task taken).
  • Budget relaxation: over those opportunities, the best value the remaining power budget could buy if tasks could be cut into fractions: the fractional knapsack, solved by the density rule. This is a linear relaxation of the knapsack constraint, the same kind of bound CP-SAT and the MILP of chapter 09 compute.

Reading the table. Every setting proves the same optimum, 28; they differ only in work. The bound matters most: at the root, the first two bounds say 49 (the total priority of the 21 targets) and the budget relaxation says 28.0, already the optimum. That is partly luck: without the power budget CP-SAT still finds 28 on this pass, so the reconfiguration times alone cap it at the same value, and the relaxation of the budget happens to land exactly on it. With this bound, the search only has to find a plan worth 28 and check a few dozen nodes. The starting plan matters when the search would otherwise take long to find a good one: with "leave first", the first plans found are poor, and starting from the greedy's 25 cuts the work from 431 to 82 nodes with the third bound; with "take first", good plans come early anyway and the greedy start saves little (70 to 50). This is the role of CP-SAT's hint, and it is as modest on the small instance (Part 5).

An exact solver is a search made affordable by bounds. Every node pruned removes all the plans below it at once, and the quality of the bound, not the speed of the computer, decides how many nodes are left. Proving optimality means closing the gap from both sides: plans from below, bounds from above.

With the weak bound, the tree goes from 19 nodes to 8665 and 172,313 as n goes from 10 to 20 and 30, and past the 500,000-node limit from 40 on: a factor of 20 or more for every 10 opportunities, exponential growth that no computer outruns. Extrapolated at that rate from 30 to 168 opportunities, it would need about 172{,}313 \times 20^{13.8} \approx 10^{23} nodes. The budget relaxation keeps one satellite tractable, erratically (5985 nodes at 40, 275 at 50), because on a single satellite's passes the relaxation of the power budget turns out to be a tight bound. The whole instance is harder in ways this toy hides: the four satellites are coupled by AtMostOne (a target can be served by any of them), reconfiguration times bind as much as budgets, and the order of tasks must stay free. What CP-SAT adds to the toy is, in order of the paragraphs above: presolve; propagation of every constraint at every node, so that a decision's consequences on all neighbouring tasks are known at once; learned clauses, so that a failure is not repeated; LP bounds with cuts over all the constraints, not one knapsack; LNS workers that supply good incumbents early; and parallel workers sharing all of it. With all that, the 168 opportunities take under a second.

Part 5

Plans and bounds over time

The hero's chart has a twin inside every CP-SAT run: the incumbent rises, the best bound falls, and the solver stops when they meet or when time runs out. ch08_numbers.py records both with two callbacks (on_solution_callback for plans, best_bound_callback for bounds) on the repository's model and parameters.

Small instance. In the run recorded on this page, the bound starts at 446, the sum of the priorities of all 168 opportunities (every x_o = 1, the bound that ignores every constraint), drops to 261, 225 and 223 within a tenth of a second, and then creeps down by one or two points at a time while the plans climb to 219 (the first plan reported is worth 137; the hint's 193 follows four milliseconds later). They meet at 0.45 s. The run exported with the shared instance (SAT_SMALL.python.cpsat.trace) has the same shape: ten improving plans from 193 to 219 in 0.28 s, status OPTIMAL. The benchmark proves the three small seeds optimal in 0.6 to 1.8 s (results/results.md).

The hint, measured. On the small instance it hardly matters. Without it, the 8-worker run finds a first plan worth 134 at once and the optimum just as fast; with one worker, the search takes 141,598 branches with the hint and 128,211 without, about the same time. The hint guarantees that the first incumbent is at least the greedy's; it does not make the proof shorter, because the proof is about the bound. On the medium instance, where the proof is out of reach, a good early incumbent is worth more.

Medium instance. 1373 opportunities and 16,335 pairs. The bound falls to 575 within a second, and in 60 s it never moves again; the incumbent climbs through dozens of improvements, quickly at first and then by single points. The benchmark's run stops at 557 (gap 3.1 %); the run of ch08_numbers.py recorded on this page, with the same model, parameters and seed, stopped at 559 (gap 2.8 %), and three other runs of the script made while writing this chapter stopped at 549, 556 and 549, all with the bound at 575. Neither is proven optimal. Two lessons. First, the gap is an upper estimate of the distance to the optimum: the true optimum lies somewhere between 559 and 575, and a weak bound makes a good plan look worse than it is. Second, a multi-threaded search stopped at a time limit is a random experiment: comparing two methods by one run each is comparing two samples, which chapter 10 takes seriously.

The project's numbers. Small instance: 219, proven OPTIMAL in under a second on all three seeds (the MILP of chapter 09 proves the same optima in 9 to 17 s). Medium: 557, 590 and 534 against bounds of 575, 604 and 551 (gaps 2.3–3.1 %) in 60 s. Large (4,900 opportunities, 140,000 pairs): 1072 and 1066 against bounds of 1138 and 1126 in 120 s, barely above the greedy's 1060 and 1047. Chapter 10 cuts the horizon into blocks to do better there.

Part 6

Check your understanding

1. What two things must a solver hold to declare a plan optimal?

A feasible plan of value v (a lower bound) and a proof that no plan exceeds v (an upper bound equal to v). The search tree's pruned nodes and the bounds at the open nodes are that proof.

2. Why is NoOverlap redundant in this model, and why keep it?

Every pair of tasks that could overlap is a conflict pair, and its precedence constraints (or its clause) already forbid overlap, with the reconfiguration time on top. It is kept because, as a global constraint over all the intervals of a satellite, it propagates deductions no pair can make alone. On the small instance with one worker, removing it costs 237,535 branches instead of 141,598.

3. What does only_enforce_if([x[a], x[b], before]) mean, and why not an equivalence?

The precedence must hold when all three literals are true; otherwise it is ignored. An equivalence would also force the literals to be true whenever the inequality happens to hold, which is wrong: two tasks may be far apart in time and still not be selected. Implication in one direction is all the model needs; hence "half" reification.

4. Why does a "both orders" pair need an extra Boolean, and a "one order" pair not?

With both orders possible, the plan has to choose one, and the choice is a decision the model must represent: the order literal. With one order possible, there is nothing to choose: if both tasks are selected, that order holds. With none, the tasks are simply exclusive: a clause.

5. In the hero demo, why does the budget relaxation prune so much more than the other bounds?

On satellite 0's first pass, 1350 s of listening compete for 300 s of power budget. The fractional knapsack uses that limit and gives 28.0 at the root, which here equals the optimum (the reconfiguration times happen to cap the pass at the same value), while the other bounds ignore the budget and start at 49. A bound that starts at the optimum leaves the search only the task of finding a plan that reaches it.

6. The hero search fixes the order of tasks by window start. Why is its answer trustworthy on the toy, and why would it not be in general?

On the toy, CP-SAT, which keeps the order free, finds the same optimum, 28. In general the best plan may need a task with a later window start to go first; on satellite 0's stretch from 17,200 to 17,600 s the fixed-order search finds 16 against CP-SAT's 20.

7. What does a learned clause such as \lnot x_a \lor \lnot x_b \lor [s_a < 2350] say?

That in every feasible plan, at least one of the following holds: a is not selected, b is not selected, or a starts before 2350. It is a consequence of the model, so adding it removes no plan, but it lets propagation cut off, anywhere in the search, every branch that repeats this combination.

8. Two medium runs with the same seed end at 557 and 559. Which is right?

Both are feasible plans, checked by the independent checker; neither is proven optimal. The difference is the non-determinism of 8 threads stopped at a time limit. The defensible statement is "557 to 559 in 60 s, with a bound of 575"; a single run is one sample.

  2. A better bound for the toy. Add the memory budget to the hero's third bound: take the minimum of the power and the memory fractional knapsacks. Is it still a valid bound? Does it prune more?
    Hint

    Any plan below the node satisfies both budgets, so each knapsack alone bounds it; the minimum of two valid upper bounds is a valid upper bound. On the toy the 21 opportunities fall in two memory segments, so the memory knapsack is a sum over two groups.

    Solution

    Valid, yes. On this toy it can hardly help: the power bound is already 28.0 at the root, the optimum, so only the nodes where the memory budget binds more tightly than the power budget gain anything. On a pass with short gaps between contacts the memory knapsack would matter more. The general point: bounds can be combined, and a solver's LP does it automatically by including all the constraints at once.

    With the budget, the optimum is 28.   4. Noise. Solve the medium instance five times with 8 workers, a 30 s limit and the same seed, and report the values and bounds. Then five times with one worker.

The 1-worker runs repeat themselves exactly if the time limit is not what stops them, and with a time limit they can still differ slightly, because how far a search gets in 30 s depends on the machine's speed at that moment. Report a spread, not a single number; chapter 10 does this for the benchmark.

Part 8

The chapter on one page

  1. Proof: a plan of value v plus a bound of v; the gap is (bound − plan) / bound, and OPTIMAL means zero.
  2. Variables: x_o Boolean, s_o \in [e_o, \ell_o] integer, tied into an optional fixed-size interval with presence x_o.
  3. Constraints: AtMostOne per target (47), NoOverlap per satellite (4, redundant but globally propagating), 106 clauses, 414 enforced precedences, 356 order literals with two precedences each, 19 budget knapsacks; maximise \sum w_o x_o; the greedy plan as a hint.
  4. Half-reification: only_enforce_if makes a constraint hold when its literals are true, and lets the solver deduce that they cannot all be true when it cannot hold.
  5. The solver: presolve, propagation, branching, clause learning with bound literals, LP relaxations with cuts, LNS, 8 workers sharing what they find.
  6. Branch and bound from scratch: on 21 opportunities, 1311 nodes with the weakest bound, 70 with the budget's relaxation, 50 with the greedy start too; optimum 28, equal to CP-SAT's.
  7. The traces: small, optimal in under a second; medium, bound 575 within a second, plans 557 and 559 in two runs of 60 s, gaps near 3 %; runs differ.

The vocabulary, in one table

WordMeaning
Constraint programVariables with finite domains, constraints on them, an objective; the solver searches.
DomainThe set of values a variable may still take; propagation shrinks it.
Optional intervalStart, fixed size and end, with a presence literal; absent intervals are ignored.
Global constraintOne constraint over many variables with its own strong propagator, such as NoOverlap.
ClauseAn "or" of literals: \lnot x_a \lor \lnot x_b.
Enforcement literal, half-reificationA literal under which a constraint must hold: literals true implies constraint.
PropagationRemoving values that a constraint makes impossible, repeated until nothing changes.
Conflict, learned clauseA contradiction found by propagation; the clause recording its cause so it is never repeated.
Branch and boundSplit the plans by decisions; prune a branch whose bound cannot beat the incumbent.
RelaxationThe problem with some constraints dropped (here integrality); its optimum bounds the original's.
Incumbent, best bound, gapBest plan found; smallest proven upper bound; their relative difference.
HintA suggested solution the solver tries first; not a constraint.
Portfolio, non-determinismSeveral differently configured searches in parallel; their timing makes runs differ.
Part 9

Scope and further reading

Scope. This chapter explains what CP-SAT's components do and shows their effect on this problem; it does not document the solver's internals, which change between versions (the repository uses OR-Tools 9.15). It leaves out search strategies and solver parameters beyond those the repository sets, the detail of cutting planes (chapter 09 covers LP relaxations), and symmetry. The traces of the small and medium runs and the toy are recorded in interactive/ch08-data.js by code/ch08_numbers.py --write; a rerun with 8 workers will give slightly different traces, as Part 5 explains. The scenario is synthetic and makes no claim about any real satellite system.
