A solver does two jobs: it finds good plans, an upper bound on the best cost, and it proves that nothing is better, which needs a lower bound. Part 1

Finding a plan and proving it

Take the paint machine of chapter A1: order A (blue, 20 minutes, due at 30), B (red, 10, due 25), C (blue, 15, due 70) and D (red, 25, due 60), a machine set up for blue, 10 minutes per colour change. Chapter A2 found 55 minutes of total tardiness for first come, first served (FIFO), 50 for shortest setup first (SST), and the best of all 4! = 24 sequences, ABDC, at 40. Checking that ABDC costs 40 is one line of arithmetic. Checking that nothing costs less is a different job: the other 23 sequences must be accounted for.

A solver like CP-SAT reports on both jobs: the best plan found so far, whose cost is an upper bound on the optimum, and a lower bound, a number no plan can beat, obtained by reasoning. When they meet, the plan is proven optimal; until then their distance, the optimality gap, says how much better a plan could still be. The real problems are snapshots: the frozen state of the running shop at one event, with the jobs still to plan (chapter C3). With 12 jobs, the orders on a single machine already number 12! = 479{,}001{,}600. This chapter is about not listing them: bounds that discard many sequences at once, propagation that removes impossible values, learning that turns each failure into a rule, and heuristics that find good plans early.

What are the upper bound, the lower bound and the gap?

In plain words: the upper bound is the cost of the best plan you hold; the lower bound is a cost you have proved nobody can beat; the gap is how much you might still be leaving on the table.

More precisely: for a minimisation with optimum z^\star, a feasible plan x gives \mathrm{UB} = f(x) \ge z^\star and a valid bound gives \mathrm{LB} \le z^\star. The absolute gap is \mathrm{UB} - \mathrm{LB} \ge 0, the relative gap (\mathrm{UB} - \mathrm{LB}) / |\mathrm{UB}|. A zero gap proves the plan optimal.

Part 2

Branch and bound on the paint machine

The search tree. Build a sequence one order at a time. The empty sequence is the root; choosing the first order gives four nodes, the second twelve, and so on. A node is a prefix, the orders placed first; a complete sequence is a leaf. Level k holds 4!/(4-k)! prefixes, so the hero's tree has

1 + 4 + 12 + 24 + 24 = 65 \ \text{nodes}, \qquad \sum_{k=0}^{n} \frac{n!}{(n-k)!} = \lfloor e \, n! \rfloor \ \text{for } n \text{ jobs}

(exercise 1); for 10 jobs, 9,864,101 nodes.

The bound of a node is a number every sequence below it is guaranteed to reach. The tardiness of the orders already placed, g(\text{prefix}), is one: those completions are fixed and the rest can only add, since tardiness is never negative. A better one adds the remaining orders. At the end of the prefix the machine is free at t and set up for colour c; a remaining order o cannot finish before t + p_o, nor before t + 10 + p_o if its colour differs from c, because the machine must change colour at some point before painting it. Tardiness grows with completion time, so

\boxed{\mathrm{LB}(\text{prefix}) = g(\text{prefix}) + \sum_{o \notin \text{prefix}} \max\bigl(0,\ t + s(c, o) + p_o - d_o\bigr)},

with s(c, o) = 0 if o has colour c and 10 otherwise. Each remaining order is treated as if it had the machine to itself, hence a lower bound. At the root every order alone is on time, so \mathrm{LB} = 0. One level down it bites: after A the machine is free at 20 and blue, B alone ends at 40, 15 minutes late, C and D are on time, so \mathrm{LB}(A) = 15. The first-level bounds are A 15, B 20, C 15, D 55.

Pruning. Keep the best complete sequence found so far, of value \mathrm{UB}. A node with \mathrm{LB} \ge \mathrm{UB} cannot lead to anything better: its subtree is discarded unseen.

What is branch and bound?

In plain words: explore the tree of choices, but before going down a branch, compute an optimistic estimate of the best it could contain; if even that is no better than a plan you hold, skip the branch.

More precisely: a tree search with a bound satisfying \mathrm{LB}(u) \le f(\sigma) for every leaf \sigma below node u, and an incumbent value \mathrm{UB}; node u is pruned when \mathrm{LB}(u) \ge \mathrm{UB}. The exploration order changes the work, never the answer.

The bound does most of the work (55 nodes against 17); the order matters less. Holding the optimum does not make the proof free: handed ABDC, the search still touches 16 nodes. On large problems that is the usual picture: a good plan comes early, and most of the work goes into raising the lower bound. Step through the hero's default (the incumbent appears at the fifth step), then change the settings and compare with the table.

Why it is correct. Every leaf is evaluated (value at least \mathrm{UB}), or below a pruned node u (value at least \mathrm{LB}(u) \ge \mathrm{UB}), or below an open node u (value at least \mathrm{LB}(u)). So z^\star \ge \min(\mathrm{UB}, \min_{\text{open}} \mathrm{LB}) at all times; when the stack empties, z^\star \ge \mathrm{UB} and the incumbent is optimal. A solver then reports OPTIMAL; with a plan and an open gap, FEASIBLE; with no plan yet, UNKNOWN. Total tardiness on one machine is NP-hard (Du and Leung [5], chapter A2), so unless P = NP no polynomial-time bound keeps every tree small; CP-SAT's strength is bounds from propagation and a search that learns. Pinedo [3] treats this branch and bound in depth.

Part 3

Propagation: shrinking what is still possible

If P must finish before U can start, and P cannot finish before minute 4, then U cannot start before minute 4 plus the transport.

What is propagation?

In plain words: each constraint crosses out the values it can prove impossible; the constraints take turns until none can cross out more.

More precisely: the domain D(x) is the set of values variable x may still take. A propagator of a constraint maps domains to smaller ones, f(D) \subseteq D, removing only values that belong to no solution of that constraint. Propagation applies the propagators until none changes anything: a fixed point. In scheduling the domains are time windows, an earliest start \mathrm{est} and a latest completion \mathrm{lct}, hence a latest start \mathrm{lst} = \mathrm{lct} - p and an earliest completion \mathrm{ect} = \mathrm{est} + p.

A hand example. On machine 1, P (4 minutes), Q (3) and R (3); on machine 2, U (3) and V (5); U starts at least 2 minutes after P ends, a transport lag as in chapter C1. (These letters are not the paint orders.) The windows are P\ [0, 20], Q\ [1, 8], R\ [2, 9], U\ [0, 20], V\ [3, 10]; in CP-SAT latest completions come from the horizon and, once a plan is known, from the objective bound.

Precedence. From S_U \ge E_P + 2 and E_P \ge \mathrm{est}_P + p_P, and symmetrically,

\mathrm{est}_U \leftarrow \max\bigl(\mathrm{est}_U,\ \mathrm{est}_P + p_P + 2\bigr), \qquad \mathrm{lct}_P \leftarrow \min\bigl(\mathrm{lct}_P,\ \mathrm{lct}_U - p_U - 2\bigr),

so \mathrm{est}_U = 6 and \mathrm{lct}_P = 15.

Timetabling. If \mathrm{lst}_i < \mathrm{ect}_i, operation i runs during [\mathrm{lst}_i, \mathrm{ect}_i) in every solution, its compulsory part: for V, [5, 8). Another operation j on the machine with \mathrm{est}_j + p_j > 5 overlaps it from any start before 8, so \mathrm{est}_j \leftarrow 8; for U, \mathrm{est}_U = 8.

Edge-finding. On machine 1 nobody has a compulsory part, yet P cannot go first: P, Q, R need 10 minutes together, Q and R must end by 9, and nothing starts before 0. For an operation i and a set \Omega of others on the machine, with \mathrm{est}(\Omega) the smallest earliest start, \mathrm{lct}(\Omega) the largest latest completion and p(\Omega) the total duration,

\boxed{\mathrm{est}(\Omega \cup \{i\}) + p(\Omega) + p_i > \mathrm{lct}(\Omega) \ \Longrightarrow\ \mathrm{est}_i \leftarrow \max_{\emptyset \ne \Omega' \subseteq \Omega} \bigl(\mathrm{est}(\Omega') + p(\Omega')\bigr)}.

Proof. If i did not end last among \Omega \cup \{i\}, the last one to end would be in \Omega, so all of them would run inside [\mathrm{est}(\Omega \cup \{i\}), \mathrm{lct}(\Omega)], shorter than their total duration: impossible on one machine. So i ends last and, nothing overlapping, starts after all of \Omega, which cannot be done before \mathrm{est}(\Omega') + p(\Omega') for any non-empty subset \Omega'. \square

In the example, with \Omega = \{Q, R\}: 0 + 6 + 4 = 10 > 9, and \mathrm{est}_P = \max(4, 5, 7) = 7, over the subsets \{Q\}, \{R\}, \{Q, R\}. A mirror rule moves latest completions left. Precedence then fires again: \mathrm{est}_U = 7 + 4 + 2 = 13.

    With edge-finding, five deductions reach the fixed point P\ [7, 15], U\ [13, 20]; without it, three stop at P\ [0, 15], U\ [8, 20]. The product of the numbers of possible start values falls from 17 \times 5 \times 5 \times 18 \times 3 = 22{,}950 to 5 \times 5 \times 5 \times 5 \times 3 = 1{,}875 (9,000 without edge-finding). Enumeration agrees: of the six orderings of P, Q, R, only QRP and RQP fit, with P starting at 7 at the earliest.

    The order of the rules does not matter. Each rule only removes values and is monotone (D \subseteq D' implies f(D) \subseteq f(D')). Then the largest domains G that every rule leaves unchanged exist, every intermediate domain contains G (D \supseteq G gives f(D) \supseteq f(G) = G), and so every run stops exactly at G.

    Propagation is incomplete. At the fixed point Q and R are still unordered; search decides the rest. Real solvers use faster versions of these rules (Laborie, Rogerie, Shaw and Vilím [2]); CP-SAT's NoOverlap propagates in this spirit, and we cite, not reproduce, its exact algorithms.

    Part 4

    Learning from failure: clauses and lazy clause generation

    SAT in brief. A literal is a Boolean variable or its negation; a clause is an OR of literals. Take (x \vee y), (\neg y \vee z), (\neg z \vee x) and decide x = \text{false}. The first clause forces y (unit propagation: when all literals of a clause but one are false, the last must be true), the second forces z, and the third is false: a conflict. Its reasons chain back to x = \text{false}, so the solver learns the clause (x), undoes decisions back to the cause (backjumping) and continues with x true. This is conflict-driven clause learning.

    Lazy clause generation (Stuckey [1]) brings this to integers. A bound becomes a literal: [S_A \ge 45] is true when A starts at minute 45 or later. A propagator that moves a bound explains it as a clause over such literals, so conflict analysis runs through NoOverlap or a linear sum as through clauses. Literals are created only when needed, hence "lazy": the paint machine's four starts in [0, 110] would need 4 \times 110 = 440 literals in advance; the conflict below uses 2.

    A learned clause on the paint machine. Having found ABDC (40), the solver asks for total tardiness at most 39. Decide D first: D is painted from 10 to 35, so S_B \ge 35 and, after a change back to blue, S_A \ge 45; then T_A \ge 35 and T_B \ge 20, so \sum T \ge 55 > 39, a conflict. Its explanation does not mention D:

    [S_A \ge 45] \wedge [S_B \ge 35] \ \Rightarrow\ \textstyle\sum_j T_j \ge 55, \qquad \text{learned clause: } [S_A \le 44] \vee [S_B \le 34].

    "Not D first" would rule out 6 sequences; this clause rules out 8 of the 24, including CDAB and CDBA: after C then D, B and A cannot start before 50 and 60, and the clause fails at once. Because it speaks about integers, not about the decision, it travels to branches never visited.

    What is lazy clause generation?

    In plain words: a solver that records why it deduced each bound, so that at a dead end it writes a general rule ("A or B must start earlier") instead of just backing up.

    More precisely: propagation combined with conflict-driven SAT solving, where integer domains are bound literals [x \ge v] created on demand, every propagator explains its inferences as clauses, and conflicts are analysed over these explanations (Stuckey [1]). CP-SAT is built on this design.

    Proving that 40 is optimal is proving that "total tardiness \le 39" has no solution; learning shortens that proof by sharing reasoning across branches.

    Part 5

    Inside CP-SAT: a portfolio of searches

    CP-SAT runs many searches at once and lets them share what they find. Its log, captured by code/c02_numbers.py, lists for the course's model with 8 workers 9 full-problem subsolvers, 13 interleaved subsolvers, all large neighbourhood searches, and 3 helpers.

    Full-problem searches (default_lp, no_lp, quick_restart and others) each run a branch and bound with propagation and learning on the whole model. They differ in what they branch on, how often they restart (drop the tree, keep the learned clauses, begin again), and how much linear relaxation they add (no_lp none, max_lp the most).

    The core worker raises the lower bound as maximum-satisfiability solvers do. It asks whether every term of the objective can sit at its smallest value; when that is impossible, it extracts a core, a set of terms that cannot all be there at once. Can A and B both be on time? If A goes first, B needs a colour change and ends at 40, 15 late; if B goes first, A ends at 50, 20 late. So \{T_A = 0, T_B = 0\} is a core, and T_A + T_B \ge 15: the bound rises to 15 (exercise 3 looks for more).

    The linear relaxation. Chapter C1 showed that the big-M relaxation bounds the paint machine's tardiness by 0, against the optimum 40. CP-SAT's LP workers relax the linear constraints and add cuts of their own; we do not measure what they contribute.

    What is large neighbourhood search?

    In plain words: keep most of the best plan, free one part of it (a time window, some machines, some jobs), re-solve only that part quickly, keep the result if better, repeat.

    More precisely: given an incumbent \bar x, choose a set N of variables, fix the others to \bar x, solve the sub-model with a small budget, accept an improvement. The families differ in how N is chosen: at random, from the constraint graph, along the circuit, or from scheduling structure. LNS cannot prove anything about plans it did not look at.

    On the paint machine, freeing two of the four positions of SST's plan ACBD (50) finds nothing better, while freeing three consecutive positions reaches ABDC (40) in one step (exercise 4): the shape of the neighbourhood decides what LNS can reach.

    On the 8-job snapshot of Part 6, the log credits both improvements over the hint to LNS workers (routing_random_lns, then scheduling_intervals_lns, which reaches the optimum 7940) and most bound improvements to core. LNS finds; the full-problem searches and core prove.

    Part 6

    Bounds, gap and status on real snapshots

    Two terms of Part 7 first: the budget is deterministic time, a machine-independent count of the solver's work, in units meant to be close to seconds (0.2 per replan in the benchmark; Part 7 shows what it counts); the hint is the warm start, the cheapest of a few quick greedy plans, handed to the solver as its first solution.

    The statuses. OPTIMAL: the plan's cost equals the lower bound, so the plan is best for the model. FEASIBLE: a plan whose proof the budget did not finish. UNKNOWN: no plan within the budget. INFEASIBLE: a proof that no plan exists.

    The snapshots. A Snapshot holds the minute now, each machine's free time and set-up, and for each job to plan its due date, its first undecided operation and, per eligible machine, the earliest minute it can be there. The numbers script runs one simulated day (seed 0, frequent breakdowns, 60 jobs) under quick re-planning (chapter C3) and records its 158 snapshots: 151 with jobs to plan, at most 12, and 7 empty. It solves every third non-empty one with the benchmark's settings (budget 0.2, 8 workers, hint): 27 of these 51 (53 %) end OPTIMAL, and size decides: all 11 of 1 to 4 jobs, 14 of the 18 of 5 or 6, 2 of the 8 of 7 or 8, none of the 14 of 9 to 12.

    One snapshot, budget by budget. Snapshot 101, an arrival at minute 891, has 8 jobs and 19 operations to place; it is the real snapshot whose model chapter C1 sizes, and the one this chapter keeps returning to. Its warm start costs 7962 in the model's objective 10 \sum_j T_j + \sum_j C_j (notation), completion times counted from the start of the day. Each point of the widget is a separate solve.

    With the hint, the solver reaches the optimal 7940 within the smallest budget, and the rest goes into the proof: the gap closes from 400 (5.0 % of the objective) to 200 at 0.2, 81 at 0.4, 0 at 0.8. Finding is cheap, proving is expensive: at 0.2 the plan is optimal and the status still says FEASIBLE, because a better plan cannot yet be excluded. Without the hint there is no plan at 0.025 and 0.05, then 8202, worse than the warm start, and 7961 at 0.2. The proof is not faster with the hint: at 0.1 and 0.2 its bound is even lower (7540 and 7740 against 7702 and 7847), because the search takes a different path. One snapshot is not a general rule.

    The largest snapshot. Snapshot 132 (minute 1111, 12 jobs, 33 operations) ends at budget 0.2 with plan 15311 and bound 13876: a gap of 1435, 9.4 % of the objective. That percentage flatters the plan: completion times count from the start of the day, so any plan carries at least 12 \times 1111 = 13{,}332 unavoidable units, and 1435 units are about 143.5 minutes of total tardiness if total completion stays the same. Read gaps in absolute terms when the objective has a large constant part. Part of the gap is the bound's fault: exercise 6 finds a simple valid bound of 14266. Without the hint the plan costs 40183, 2.62 times as much.

    In the benchmark, results/runs.csv counts every replanning event, including empty ones that call no solver (status EMPTY). Without breakdowns 668 of 1,200 (56 %) ended OPTIMAL, with frequent breakdowns 1,345 of 3,178 (42 %), probably because breakdowns keep more jobs in the shop. The rest ended FEASIBLE, EMPTY or, 5 times, GREEDY (Part 7). Computing took 1.61 s per event on average.

    Part 7

    Warm starts, budgets and reproducible runs

    A hint is a suggestion. model.add_hint(x, v) says "try x = v first" and constrains nothing. When every variable is hinted and the values satisfy every constraint, the hint is complete and feasible, and CP-SAT keeps it as its first solution; on snapshot 101 the log reports it so, with objective 7962.

    What is a warm start?

    In plain words: starting the solver with a good plan in hand, so it can only improve and has something to return even with a tiny budget.

    More precisely: an initial feasible solution, here given as a complete hint. It sets the first upper bound, steers the first decisions and feeds the LNS workers. It changes neither the model nor the optimum and adds no bound of its own; it changes the search path, and with it how fast the bound rises.

    The fallback. solve_snapshot builds the warm start first: the cheapest of three greedy list schedules and, when there is one, the previous plan re-timed on the new snapshot (chapter C3). If the solver returns no plan, or a more expensive one, the warm start is used, with status GREEDY: 5 of the 4,378 benchmark replans, all under breakdowns. One cause can be shown: when the budget runs out in presolve, before the search has loaded the hint, the solver returns UNKNOWN although the hint is complete and feasible, as on snapshot 101 at a budget of 0.01 and on the larger snapshot 132 at 0.025 (it gets past presolve at 0.025 and 0.05 respectively); whether the 5 benchmark cases arose this way or from the 20 s wall-clock safety net, runs.csv does not record.

    What are deterministic time and interleaved search?

    In plain words: with a limit in seconds, the amount of search depends on the computer and its load, so two runs can return different plans, and in a simulation that re-plans thousands of times one different plan changes everything after it. So say "stop after this much work", and make the parallel workers take turns.

    More precisely: max_deterministic_time stops on a count of the search's elementary operations. interleave_search = True runs the portfolio in batches of tasks (24 per batch for this model, says the log) and exchanges solutions and bounds only between batches, which the parameter documentation [4] describes as deterministic.

    What the budget counts. On snapshot 101 the response's deterministic_time is 1.122 for a limit of 0.2 and 6.356 for 0.8. The log explains the figure: its task-timing table gives each subsolver's deterministic time, and these add up to 1.111 and 6.344; the small rest is work outside the search tasks, such as presolve. So the response reports the work of all subsolvers added up. The limit is not a cap on that sum: with num_workers = 1 the reported figure equals the limit (0.200 and 0.800), with or without interleaving, because the tasks run one after another; with 8 workers they run side by side and their work adds up to 5.6 times the limit at 0.2 and 7.9 times at 0.8 (more than the limit without interleaving too). The parameter's docstring in the installed package says only that the unit should be "as close as possible to a second" [4]; it does not say how the limit is shared among workers, and we do not guess. Two things are safe: with 8 workers a budget of 0.2 buys several times 0.2 units of work, and the stopping point is the same on every run.

    Reproducibility, checked. Two solves of snapshot 101 at 0.2 with random_seed = 0 return the same plan operation by operation, the same bound 7740 and the same counters (7,743 branches, 867 conflicts); only wall-clock times differ. With random_seed = 1 the search differs (7,827 branches), the plan happens not to. With interleave_search = False the plan and the bound can change from one execution to the next (the numbers script prints three runs; their values change each time it runs): without the batches, what the workers share depends on thread timing. test_controller_is_deterministic checks the property on a whole run.

    def warm_start(ws: Workshop, snap: Snapshot, allowance: int, previous_plan=None) -> Plan:
    candidates = [greedy_plan(ws, snap, allowance, rule) for rule in ("finish", "start", "edd")]
    if previous_plan:

    Part 9

    Common pitfalls

    1. "FEASIBLE means a poor plan." It means an unfinished proof; the plan may already be optimal (Part 6).
    2. "A small relative gap means near-optimal." Not when the objective has a large constant part: 9.4 % on the 12-job snapshot is about 143.5 minutes of tardiness.
    3. "OPTIMAL means the best control of the shop." It means optimal for the snapshot's model: fixed transport lags, no future arrivals or breakdowns. Chapter C3 shows why optimal snapshot plans do not make an optimal policy.
    4. "Seconds are the natural budget." They tie every run to the computer's speed and load. For repeatable experiments stop on deterministic time and interleave the workers.
    Part 10

    Check your understanding

    Try to answer each question before opening it.

    1. What certifies the upper bound, and what certifies the lower bound?

    The upper bound, a plan the solver holds. The lower bound, the reasoning that produced it: node bounds, propagation, learned clauses, relaxations, cores.

    2. Why is "so far plus each remaining order alone" a valid bound?

    No remaining order can finish before the machine is free plus its painting time, plus a colour change if its colour differs, and tardiness does not decrease with completion time; add the fixed tardiness of the prefix.

    3. With the optimum given in advance, branch and bound still touches 16 nodes. Why?

    The optimum only sets the upper bound; every other subtree must still be ruled out by a bound of at least 40.

    4. Timetabling deduced nothing on machine 1, edge-finding did. What is the difference?

    Timetabling reasons about one operation at a time, through compulsory parts, and none exists on machine 1. Edge-finding reasons about a set: P, Q and R together do not fit before Q and R must be done, so P goes after both.

    5. Why is a learned clause more useful than backtracking?

    Backtracking forgets why a branch failed. The clause keeps the reason in terms, such as [S_A \ge 45], that appear in other branches too.

    6. Why is the linear relaxation weak on disjunctive scheduling?

    Fractional ordering variables relax both big-M inequalities at once, removing the machine's capacity from the LP: the bound 0 against 40.

    7. Which parameters make the benchmark reproducible, and how?

    max_deterministic_time stops after a fixed amount of work, interleave_search synchronises the workers in batches so sharing does not depend on thread timing, and random_seed fixes the remaining random choices.

    Part 11

    Exercises

    The code runs in the repository's environment, from its root folder.

    1. Count the search tree. Show that the tree of all prefixes of n jobs has \sum_{k=0}^{n} n!/(n-k)! nodes and that this equals \lfloor e \, n! \rfloor for n \ge 1. Check n = 4 and n = 10.

      Hint

      With j = n - k the sum is n! \sum_{j=0}^{n} 1/j!; compare with e = \sum_{j \ge 0} 1/j! and bound the tail.

      Solution

      Level k holds the ordered choices of k jobs out of n, n!/(n-k)!. The total N = n! \sum_{j=0}^{n} 1/j! is an integer, and e \, n! - N = \frac{1}{n+1} + \frac{1}{(n+1)(n+2)} + \dots < \frac{1}{n+1} + \frac{1}{(n+1)^2} + \dots = \frac1n \le 1. So N = \lfloor e \, n! \rfloor: 65 for n = 4, and 9,864,101 nodes for 3,628,800 leaves when n = 10.

    2. Edge-finding on a looser machine. Widen the windows of Part 3 to Q\ [1, 9] and R\ [2, 10]. Does edge-finding still put P last? Is P first now possible?

      Hint

      Recompute \mathrm{est}(\{P, Q, R\}) + p(\{Q, R\}) + p_P against \mathrm{lct}(\{Q, R\}), then try P, Q, R at their earliest starts.

      Solution

      0 + 6 + 4 = 10 is not greater than \mathrm{lct}(\{Q, R\}) = 10, so edge-finding deduces nothing about P. Rightly so: P from 0 to 4, Q from 4 to 7, R from 7 to 10 meets every window. The numbers script checks it (section PROPAGATION, "exercise 2").

    3. Cores of the paint machine. A core is a set of orders that cannot all be on time. Find every minimal core of the paint machine (no proper subset is a core) and the smallest total tardiness of its orders. Disjoint cores add up to a lower bound. Which bound do the cores give?

      Hint

      For a set, try the sequences of its own orders from minute 0 on a blue machine: other orders placed among them can only delay them. Two orders of the same colour are both on time if the earlier-due one goes first.

      Solution

      \{A, B\} is a core (Part 5), with smallest tardiness 15. No other pair is: in AC, AD, BC, BD and CD the second order ends at 35, 55, 45, 45 and 50, on time. Of the triples without both A and B, \{B, C, D\} fits (B, D, C end at 20, 45, 70), but \{A, C, D\} does not: A must come first to end by 30, and then whichever of C and D goes last is 10 late. The minimal cores are \{A, B\} (15) and \{A, C, D\} (10). They share A, so they cannot be added: the cores give 15, against the optimum 40. The numbers script enumerates every subset (section CORES).

    4. Large neighbourhood search by hand. Start from SST's plan ACBD (50). Neighbourhood 1 frees two of the four positions, keeps the other two orders where they are, and re-solves the freed pair exactly (both orderings). Neighbourhood 2 frees three consecutive positions and re-solves them exactly (all six orderings). Run LNS with each, moving to the best neighbour (ties broken alphabetically) while it improves. Where does each stop? Does stopping at 40 prove that 40 is optimal?

      Hint

      Neighbourhood 1 is "swap two orders": list the six swaps of ACBD and cost them as in chapter A2. For neighbourhood 2, positions 2 to 4 hold C, B and D after A.

      Solution

      The six swaps of ACBD give CABD 55, BCAD 75, DCBA 135, ABCD 55, ADBC 60 and ACDB 65: none beats 50, so neighbourhood 1 stops at once, at a local optimum 10 minutes above the optimum. Neighbourhood 2 with positions 2 to 4 free contains ABDC: A, then B (red, change) 30 to 40, 15 late, D 40 to 65, 5 late, C (change) 75 to 90, 20 late, total 40, reached in one step. No proof follows: being best among one's neighbours is a local property, and BDCA (60) is a local optimum of neighbourhood 2 as well. Over the 24 starting sequences, with ties between equally good neighbours broken alphabetically (as the numbers script does), 9 end above 40 with neighbourhood 1 and 3 with neighbourhood 2; other tie choices give between 9 and 14, and 3 or 4, but the sets of local optima ({ABDC, ACBD, BDCA} and {ABDC, BDCA}) do not depend on them. Only a lower bound of 40 (Part 2) proves ABDC optimal. The numbers script runs both searches from every start (section LNS).

    6. A bound the solver does not see. Bound the objective of snapshot 132 by scheduling each job alone: from j.first_op on, each operation on its best eligible machine m (k in the code), no earlier than j.ready[k] (the first) or the previous end plus the transport lag (the others), nor than snap.machine_free[k], with no changeover. Compare with CP-SAT's 13876 at budget 0.2. Why can the solver miss a valid bound?

      Hint

      Carry the earliest end on each eligible machine; arrival on k is the minimum over previous machines k' of their end plus transport_lag(ws, k', k, 2). For the last question, look at which constraint of chapter C1's model uses machine_free.

      Solution 
      from jobshop.cpsat import transport_lag
def each_job_alone(ws, snap, allowance=2):
    total = 0
    for j in snap.jobs:
        E = {}
        for op in range(j.first_op, ws.n_ops(j.family)):
            new = {}
            for k, p in ws.alternatives(j.family, op).items():
                if op == j.first_op:
                    if k not in j.ready:
                        continue
                    arrive = j.ready[k]
                else:
                    arrive = min(E[k2] + transport_lag(ws, k2, k, allowance) for k2 in E)
                new[k] = max(arrive, snap.machine_free[k]) + p
            E = new
        end = min(E.values())
        total += 10 * max(0, end - j.due) + end
    return total
print(each_job_alone(ws, snaps[132][0]))   # 14266

      Every step only relaxes the model, so 14266 is a valid bound, above 13876. The solver probably misses it because the model states "start \ge machine_free[k]" only for the operation first on the machine, through a circuit arc. Adding it for every operation, enforced by the presence literal, is a standard strengthening; the repository does not, and we have not measured it.

    Part 12

    The chapter on one page

    1. Two jobs: finding plans gives the upper bound, proving gives the lower bound; a zero gap is a proof.
    2. Branch and bound: a bound valid below each node, pruning when \mathrm{LB} \ge \mathrm{UB}; 17 of 65 nodes prove ABDC (40) optimal.
    3. Propagation: precedence, timetabling and edge-finding shrink windows to a fixed point.
    4. Learning: conflicts explained over bound literals give clauses that rule out unvisited branches.
    5. CP-SAT: full-problem searches and core prove, neighbourhood searches find.
    6. Real snapshots: finding is cheap, proving is expensive; FEASIBLE is an unfinished proof.
    7. Reproducibility: deterministic time and interleaved workers give the same plan on every run.
