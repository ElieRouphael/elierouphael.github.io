A fair benchmark

CP-SAT re-planning is less late than the best rule on the 20 test days: a real difference, or the luck of 20 random days? This chapter teaches how to decide. Run every method on the same days so that the day-to-day variation cancels, put a bootstrap interval on the mean difference, keep the days you tune on apart from the days you report, and check every schedule independently so that a bug cannot pass for a better method. Below, pick any two methods on the 20 test days and see what the pairing buys.

Part 1

The same days for every method

The question. Under frequent breakdowns, CP-SAT re-planning (C3) has a mean tardiness of 19.3 minutes over the 20 test days and the best dispatching rule, shortest setup first (SST, B2), 34.1. A day in this course is random: 60 orders arrive at random times, machines break at random times. Run the same method on another 20 days and the average moves. How do we know the 14.8-minute gap is not just the luck of these days?

Look at one day first. Seed 7 is a bad day for everybody: in the calm shop first come, first served (FIFO) averages 97.4 minutes of lateness per order and CP-SAT 12.4; under breakdowns FIFO reaches 169.9 and CP-SAT 63.6. It is the worst of the 20 days for all seven methods in the calm shop, and for six of them under breakdowns. That shared variation says nothing about which method is better. Had CP-SAT been tested on days 0 to 19 and SST on days 20 to 39, a few heavy days on one side would decide the comparison.

The remedy is to give every method the same days. In the repository a test day is a seed: make_scenario(ws, seed) draws the 60 arrivals, families and due dates and, for each machine, the whole calendar of breakdowns, before any method runs. Every method then faces the same orders and the same failures, and the comparison on day i is a comparison of decisions alone.

What are common random numbers?

In plain words: test every method on the same random days, so that a difference in results can only come from a difference in decisions.

More precisely: a simulation experiment uses common random numbers (CRN) when the random inputs of replication i, here the arrivals, due dates and breakdown calendars of seed i, are identical for every method compared. The results X_i and Y_i of two methods on replication i are then dependent, usually positively, and the analysis works with the paired differences \Delta_i = X_i - Y_i.

Replication
one independent run of the simulated system; here one test day, one seed.
Paired difference
\Delta_i = \bar T^{X}_i - \bar T^{Y}_i, the difference of the two methods' mean tardiness on day i; negative means X was less late.
Synchronisation
each random number is used for the same purpose in every run, whatever the controller decides. Without it, the "same seed" does not give the same day.

Synchronisation is the hard part. One generator shared by everything would break CRN silently: if failures were drawn only while a machine works, a method that leaves a machine idle would use fewer random numbers, and every later arrival would differ. The repository avoids this by construction:

jobshop/scenario.py · make_scenario

def make_scenario(
    ws: Workshop,
    seed: int,
    n_jobs: int = 60,
    load: float = 0.60,
    mtbf: float | None = None,
    mttr: float = 20.0,
    tightness: tuple[float, float] = (2.0, 4.0),
) -> Scenario:
    """Poisson arrivals, uniform job mix, due date = arrival + k x shortest work (k uniform).

    Breakdowns: per machine, exponential time between a repair and the next failure (mean
    `mtbf`, calendar time), repair time uniform in [0.5, 1.5] x `mttr`. The arrival stream does
    not depend on `mtbf`: the same seed gives the same jobs at every disturbance level.
    """
    rng = np.random.default_rng([seed, 1])
    gaps = rng.exponential(mean_interarrival(ws, load), size=n_jobs)
    arrivals = np.floor(np.cumsum(gaps)).astype(int)
    families = rng.integers(0, ws.n_families, size=n_jobs)
    factors = rng.uniform(tightness[0], tightness[1], size=n_jobs)
    jobs = tuple(
        Job(i, int(f), int(a), int(a + round(k * ws.min_remaining_work(int(f), 0))))
        for i, (a, f, k) in enumerate(zip(arrivals, families, factors))
    )

    downtime: list[tuple[tuple[int, int], ...]] = []
    horizon = 4 * int(arrivals[-1]) + 5000  # far beyond any run
    for m in range(ws.n_machines):
        spans: list[tuple[int, int]] = []
        if mtbf is not None:
            brng = np.random.default_rng([seed, 2, m])
            t = 0
            while t < horizon:
                down = t + max(1, int(round(brng.exponential(mtbf))))
                up = down + max(1, int(round(brng.uniform(0.5, 1.5) * mttr)))
                spans.append((down, up))
                t = up
        downtime.append(tuple(spans))
    return Scenario(seed, jobs, tuple(downtime), mttr)

The arrival stream has its own generator, np.random.default_rng([seed, 1]), and draws all 60 gaps, families and due-date factors at once. Each machine has its own breakdown generator, default_rng([seed, 2, m]), so the failures of machine 3 do not depend on how many numbers machine 1 used. And the breakdowns are in calendar time, drawn far beyond any run and stored in scenario.downtime: a machine fails at the same minute whether or not it is working, so no decision can shift a later failure. Law [2] treats this synchronisation as what makes CRN work.

The hero shows what this buys: pick FIFO and CP-SAT, and the two series of dots rise and fall together while the differences below are far more regular than either method.

The hero's readouts quote 95 % intervals and whether they "exclude zero"; both words are used from now on.

What does a 95 % interval say?

In plain words: a range computed from the 20 days that very likely contains the true mean difference, the average over all the days the shop could have.

More precisely: a 95 % interval is a procedure: applied to many independent sets of 20 days, it would contain the true mean difference \mu_\Delta in about 95 % of them. If it excludes zero, the data are hard to explain by the luck of the days alone. For a roughly normal mean it is close to the mean \pm 1.96 standard errors, 1.96 being the 97.5 % quantile of the standard normal, so that \pm 1.96 standard deviations hold 95 % of a normal distribution. Part 3 shows how the bootstrap computes such an interval without assuming normality.

Standard error
the standard deviation of a mean: \sigma/\sqrt n for n independent days of spread \sigma, how much the mean itself would move from one set of n days to another.
Excludes zero
the whole interval lies on one side of 0, so the sign of the difference is settled at that confidence.
Part 2

The variance of a paired difference

In plain words. When both methods do badly on the same days, subtracting their results cancels the shared part. Three days with X = (10, 20, 60) and Y = (14, 26, 68) minutes: each method spreads from tens to sixty, but the differences X - Y = (-4, -6, -8) barely move. Covariance measures how much two results go up and down together, positive when they are high on the same days; correlation is covariance rescaled to lie between -1 and 1. (Here \rho is a correlation, not the load \rho = 0.60 of B1.)

By hand. The means are 30 and 36, so the deviations are (-20, -10, 30) and (-22, -10, 32). The sample variances are s_X^2 = (400 + 100 + 900)/2 = 700 and s_Y^2 = (484 + 100 + 1024)/2 = 804, the sample covariance \big((-20)(-22) + (-10)(-10) + (30)(32)\big)/2 = 750, and the correlation 750/\sqrt{700 \times 804} = 0.9997. Then s_X^2 + s_Y^2 - 2\,\widehat{\mathrm{Cov}} = 700 + 804 - 1500 = 4, exactly the variance of (-4, -6, -8): (4 + 0 + 4)/2 = 4. The identity below says why.

The identity. Let X and Y be the two methods' results on one random day, with variances \sigma_X^2, \sigma_Y^2 and covariance \mathrm{Cov}(X, Y) = \mathbb E[(X - \mu_X)(Y - \mu_Y)]. Expanding the square,

\mathrm{Var}(X - Y) = \mathbb E\big[\big((X - \mu_X) - (Y - \mu_Y)\big)^2\big] = \sigma_X^2 + \sigma_Y^2 - 2\,\mathrm{Cov}(X, Y).

With the correlation \rho = \mathrm{Cov}(X, Y) / (\sigma_X \sigma_Y), \mathrm{Var}(X - Y) = \sigma_X^2 + \sigma_Y^2 - 2 \rho \sigma_X \sigma_Y.

Averaged over n days. The test days are independent (each has its own seed and starts from an empty shop), so the n differences \Delta_i are independent copies of X - Y and their mean \bar\Delta has variance \mathrm{Var}(X - Y)/n. Compare two designs with n days per method:

\begin{aligned} \text{common days:} \quad \mathrm{Var}(\bar\Delta) &= \frac{\sigma_X^2 + \sigma_Y^2 - 2\rho\sigma_X\sigma_Y}{n}, \\ \text{independent days:} \quad \mathrm{Var}(\bar X - \bar Y') &= \frac{\sigma_X^2 + \sigma_Y^2}{n}, \end{aligned}

where \bar Y' is the mean of Y over other days, independent of \bar X. Their ratio is

\frac{\mathrm{Var}(\bar\Delta)}{\mathrm{Var}(\bar X - \bar Y')} = 1 - \rho\, c, \qquad c = \frac{2\sigma_X\sigma_Y}{\sigma_X^2 + \sigma_Y^2} \in (0, 1],

with c = 1 when the two spreads are equal (c \le 1 because (\sigma_X - \sigma_Y)^2 \ge 0). Two consequences. Pairing helps exactly when \rho > 0. And for \rho \ge 0 the ratio is at least 1 - \rho: the variance can shrink at most to the share 1 - \rho, reached when the methods spread equally.

The numbers, for CP-SAT minus SST under breakdowns. From the 20 test days of results/runs.csv: s_X = 17.55 minutes for CP-SAT, s_Y = 24.02 for SST, covariance 411.8, correlation r = 0.977. Then

s_X^2 + s_Y^2 - 2\,\widehat{\mathrm{Cov}} = 308.0 + 576.9 - 823.6 = 61.3,

a standard deviation of 7.83 minutes for the daily difference, against \sqrt{884.9} for unrelated days. Here c = 0.953 and 1 - rc = 0.069: pairing divides the variance by about 14. The standard error of the mean difference over the 20 days is 7.83/\sqrt{20} = 1.75 minutes paired, 6.65 unpaired.

Correlations are high everywhere. The 21 correlations between pairs of the seven methods run from 0.82 to 0.99 in the calm shop (median 0.96) and from 0.88 to 0.98 under breakdowns (median 0.95); the lowest involve quick re-planning (Greedy replan). A burst of arrivals or a long repair is hard for every controller.

Part 3

The bootstrap

The problem. We have 20 numbers \Delta_1, \dots, \Delta_{20} with mean \bar\Delta = -14.8 and want an interval for the true mean difference \mu_\Delta. The textbook interval \bar\Delta \pm t_{19}\, s/\sqrt n uses t_{19} = 2.093, the 97.5 % quantile of Student's t distribution with 19 degrees of freedom, which replaces 1.96 when the spread s is estimated; it assumes \bar\Delta roughly normal, while tardiness is skewed, with a long tail of very bad days such as day 7. The bootstrap [1] reads the distribution of \bar\Delta from the data instead. At n = 20 it is not more accurate than the t-interval in general, and here the two nearly agree, [-18.4, -11.7] and [-18.5, -11.2]; its value is that it needs no formula and works the same for any statistic.

In plain words. We cannot draw new days from the shop, but we have 20 days that came from it. So we pretend these 20 days are the distribution, draw new sets of 20 from them with replacement, and watch how much the mean moves from set to set: that movement stands in for the movement between real sets of 20 days.

What is the percentile bootstrap?

In plain words: resample your own data, many times, to see how much a statistic would change from one sample to another, and read an interval from the spread.

More precisely: let \hat F_n be the empirical distribution of the sample, mass 1/n on each \Delta_i. Draw B bootstrap samples \Delta^{*b}_1, \dots, \Delta^{*b}_n independently from \hat F_n, that is, n days chosen uniformly with replacement, and compute each mean \bar\Delta^{*b}. The 95 % percentile interval is [\hat q_{0.025}, \hat q_{0.975}], the 2.5 % and 97.5 % quantiles of the B resample means. The course uses B = 10{,}000.

Plug-in principle
estimate a property t(F) of the unknown distribution by the same property of the empirical one, t(\hat F_n).
Bootstrap distribution
the distribution of \bar\Delta^* when the sample is held fixed and only the resampling is random.
Paired resampling
resample whole days, so that day i's two results stay together; resampling \Delta_i does exactly that.
Unpaired resampling
resample X's n days and Y's n days independently and subtract the two resample means; it ignores that day i is the same day for both.

Why it works: the plug-in principle. We need the distribution of \bar\Delta - \mu_\Delta, which depends on the unknown distribution F of a day. The plug-in principle replaces F by \hat F_n: under \hat F_n the "true mean" is \bar\Delta itself and a sample of n days is a resample, so \bar\Delta^* - \bar\Delta stands for \bar\Delta - \mu_\Delta. Taken literally, with \hat q the quantiles of \bar\Delta^*,

\begin{aligned} &P\big(\hat q_{0.025} - \bar\Delta \le \bar\Delta - \mu_\Delta \le \hat q_{0.975} - \bar\Delta\big) \approx 0.95 \\ \iff\ &\mu_\Delta \in \big[2\bar\Delta - \hat q_{0.975},\ 2\bar\Delta - \hat q_{0.025}\big], \end{aligned}

the basic bootstrap interval, [-17.9, -11.3] for CP-SAT − SST. The approximation is good when \hat F_n is close to F, that is, when n is not too small.

The percentile interval rests on a different argument (Efron and Tibshirani [1], chapter 13). Suppose some increasing function g makes g(\bar\Delta) - g(\mu_\Delta) normal with mean 0 and some variance c^2, in the real and the bootstrap world alike. The exact 95 % interval for g(\mu_\Delta) is then g(\bar\Delta) \pm 1.96c. In the bootstrap world g(\bar\Delta^*) has quantiles g(\bar\Delta) \pm 1.96c too, and since g is increasing, the quantiles of \bar\Delta^* are \hat q = g^{-1}\big(g(\bar\Delta) \pm 1.96c\big): exactly the ends of that interval mapped back. So the percentile interval is right without our knowing g. The two intervals agree when the bootstrap distribution is symmetric about \bar\Delta; here the percentile ends lie 3.57 below and 3.09 above the mean, so they differ by about half a minute.

One thing can be computed exactly. For a single draw \Delta^* from \hat F_n, \mathbb E^*[\Delta^*] = \frac1n \sum_i \Delta_i = \bar\Delta and \mathrm{Var}^*(\Delta^*) = \frac1n \sum_i (\Delta_i - \bar\Delta)^2 = \hat\sigma^2, the plug-in variance. The n draws of a resample are independent, so

\mathrm{Var}^*(\bar\Delta^*) = \frac{\hat\sigma^2}{n} = \frac{n - 1}{n} \cdot \frac{s^2}{n},

the familiar squared standard error, slightly shrunk because \hat\sigma^2 divides by n where s^2 divides by n - 1. For CP-SAT − SST, \hat\sigma = 7.63 and the bootstrap standard error is 7.63/\sqrt{20} = 1.71, against s/\sqrt n = 1.75.

A hand-sized example. Take three days with differences -3, -6 and -15; their mean is -8. There are 3^3 = 27 ordered resamples, all equally likely, and their means are

Resample mean −15 −12 −11 −9 −8 −7 −6 −5 −4 −3
Resamples 1 3 3 3 6 3 1 3 3 1

(three times -15 gives -15; two -15 and one -6 gives -12, in 3 orders; one of each gives -8, in 6 orders; and so on). The plug-in variance is \hat\sigma^2 = (25 + 4 + 49)/3 = 26, and the variance of the 27 means is exactly 26/3 = 8.6667, a standard error of 2.94 where s/\sqrt n gives 3.61. But the percentile interval is useless here: the smallest mean has probability 1/27 = 0.037, more than 2.5 %, so the 95 % interval is the whole range [-15, -3], and bootstrap_ci returns exactly that. With 20 days there are 20^{20} \approx 1.05 \times 10^{26} ordered resamples; B = 10{,}000 random ones approximate their distribution.

The 20 daily differences of CP-SAT − SST under breakdowns; highlighted: the days in the last resample (orange: drawn twice or more)

What B buys. Drawing B random resamples instead of all of them adds Monte Carlo error: over 100 resampling seeds with B = 10{,}000, the ends of the paired CP-SAT − SST interval have a standard deviation of 0.049 and 0.032 minutes, those of the wider unpaired one 0.175 and 0.166. Hence the hero, which resamples in the browser with another generator, shows the unpaired interval as [-27.7, -2.4] against NumPy's [-27.9, -2.7], and the paired one, [-18.4, -11.7], to the digit.

What it assumes. Three things, and the first matters most.

  1. Independent days, true here by construction. In a real plant consecutive days share leftover work and resampling single days would understate the uncertainty; a block bootstrap, which resamples runs of consecutive days, is the usual remedy [1].
  2. Enough days for \hat F_n to resemble F, as the three-day example shows.
  3. A statistic that some increasing transformation makes roughly normal, the condition of the percentile argument above. With skewed data at small n it holds only roughly; the bias-corrected and accelerated (BCa) interval [1] corrects for this, and the course only cites it.

Does it deliver 95 %? On 1,000 samples of 20 days from the 500-day pool, the percentile interval for SST's mean covers the pool average 90.8 % of the time in the calm shop and 91.2 % under breakdowns; for the paired difference SST − EDD, 92.7 % and 93.3 %. Even with normal data it would cover only 92.9 % at n = 20, the probability that |t_{19}| < 1.96\sqrt{19/20}, because it behaves like \bar\Delta \pm 1.96\,\hat\sigma/\sqrt n instead of using t_{19} and s; the rest of the single mean's shortfall comes from its skewness (2.23 and 1.61).

How the interval shrinks with the number of days. Because \mathrm{Var}(\bar\Delta) = \sigma_\Delta^2/n, the half-width is about 1.96\, \sigma_\Delta/\sqrt n: four times as many days for half the width, on average. Move the hero's Test days used slider: with the first 5, 10, 15 and 20 days, the paired interval of CP-SAT − SST is 10.4, 12.0, 8.4 and 6.7 minutes wide, the unpaired one 25.1, 40.8, 30.1 and 25.3. Not monotone, because the sample standard deviation rises from 6.27 minutes over the first 6 days to 10.53 over the first 8, as the heavy days 6 and 7 (differences -29.6 and -35.4) enter.

How many days would settle the DQN question? DQN is +1.3 minutes behind SST under breakdowns, with an interval [-2.1, +5.1] that includes zero, and the daily difference has a standard deviation of 8.50 minutes. A half-width of 1.3 minutes needs n \approx (1.96 \times 8.50/1.3)^2 = 164 days. Twenty days cannot resolve a difference that small; the honest summary is "no difference detected", not "equal".

Part 4

Training, validation and test days

In plain words. A method adjusted while looking at the test days has, in part, learned those days. Its test score measures how well it fits them, not how it will do tomorrow. The cure: separate the days.

What are training, validation and test sets?

In plain words: three disjoint sets of days, one to learn on, one to choose with, and one to report, used once.

More precisely: the training days are those a method may learn from (the DQN agent's episodes); the validation days serve every choice made while developing (hyper-parameters, checkpoints, the CP-SAT settings, the shop's load); the test days are run once, after every choice is frozen, and only their results are reported. A choice made on the test turns its score into an optimistic one.

In the repository the three sets are seed ranges.

The agents may differ a little (2 of the 20 paired comparisons among them exclude zero), but the next part shows how large a gap selection alone produces.

Part 5

The winner's curse

In plain words. Run several equally good methods on the same 20 days and report the best. Its result is low partly because the days happened to suit it; on fresh days that luck does not repeat. The name comes from auction theory, where the winning bid tends to be the one that overestimated the most.

The mathematics. Take K methods with the same true mean \mu and the same daily spread \sigma, any two correlated \rho on a common day. A convenient model writes a day's result for method k as \mu + \sigma(\sqrt\rho\, Z_i + \sqrt{1 - \rho}\, \varepsilon_{ki}): a shared day effect Z_i and a method-specific part \varepsilon_{ki}, all independent standard normals. Averaged over n days,

\bar X_k = \mu + \frac{\sigma}{\sqrt n}\left(\sqrt\rho\, G_0 + \sqrt{1 - \rho}\, G_k\right), \qquad G_0 = \sqrt n\, \bar Z,\ \ G_k = \sqrt n\, \bar\varepsilon_k,

where \bar Z and \bar\varepsilon_k are the day averages of Z_i and \varepsilon_{ki}, so that G_0, G_1, \dots, G_K are independent standard normals. The shared term is the same for every k, so it does not affect which method wins:

\min_k \bar X_k = \mu + \frac{\sigma}{\sqrt n}\left(\sqrt\rho\, G_0 + \sqrt{1 - \rho}\, \min_k G_k\right).

Take expectations, with \mathbb E[G_0] = 0 and \mathbb E[\min_k G_k] = -e_K:

\begin{aligned} \mathbb E\Big[\min_k \bar X_k\Big] - \mu &= -\,\sigma\sqrt{1 - \rho}\;\frac{e_K}{\sqrt n}, \\ e_K = \mathbb E\Big[\max_{k \le K} W_k\Big] &= \int_{-\infty}^{\infty} w\, K \varphi(w)\, \Phi(w)^{K-1}\, dw, \end{aligned}

where W_k = -G_k are independent standard normals (\min_k G_k = -\max_k W_k), and K\varphi(w)\Phi(w)^{K-1} is the density of their maximum, the derivative of P(\max W_k \le w) = \Phi(w)^K. Numerically, e_2 = 0.564 (exactly 1/\sqrt\pi, exercise 3), e_3 = 0.846, e_4 = 1.029, e_5 = 1.163, e_{10} = 1.539 and e_{20} = 1.867: the curse grows with the number of candidates, slowly, asymptotically like \sqrt{2 \ln K} (a standard result on the maximum of normal variables, cited, not proved here; at K = 20 it still gives 2.45).

Read the formula. The optimism shrinks like 1/\sqrt n, grows with K, and common random numbers reduce it by \sqrt{1 - \rho}, because only method-specific luck can make one method win. With \sigma = 24.0 minutes (SST's spread over the test days under breakdowns), n = 20 and K = 4: independent days give an expected optimism of 5.53 minutes, common days with \rho = 0.90 only 1.75. With K = 10 the figures are 8.26 and 2.61; with K = 4, \rho = 0.90 and only 5 days, 3.50.

In the widget the orange and blue histograms differ only by that shift; the dashed markers show their means. Set \rho to 0 and the winner looks 5.5 minutes better than it is; raise \rho and the curse shrinks.

In the real shop the four rules are not equal. The 500-day pool gives each rule's true mean with a standard error of 0.39 to 2.26 minutes. On 2,000 random sets of 20 pool days, the truly best rule (EDD calm, SST under breakdowns) has the lowest mean 97.3 % and 97.7 % of the time, and the winner's score is optimistic by only 0.04 and 0.13 minutes on average: the rules differ by more than the paired noise. If instead the rule is chosen on 10 other days and its score read on the 20 test days, the report is off the rule's true mean by +0.03 and -0.01 minutes on average: no optimism. The five DQN agents are the opposite case, nearly equal candidates, where the curse can account for most of the gap.

Part 6

What a fair report contains

A comparison is fair when a reader can see the size of the difference, its uncertainty and how it was produced. For CP-SAT against SST under breakdowns:

  1. The protocol. 20 test days (seeds 0 to 19), the same for every method, run once after all choices were made on other seeds; all 480 runs of the evaluation passed the independent checker.
  2. Each method, with its interval. CP-SAT 19.3 [12.3, 27.1], SST 34.1 [24.8, 44.9] minutes of mean tardiness.
  3. The paired difference, with its interval. -14.8 [-18.4, -11.7] minutes, CP-SAT minus SST. The two methods' own intervals overlap; the paired one is far from zero.
  4. Days better, equal and worse. 20, 0 and 0. The smallest gain on a day is 4.3 minutes, the largest 35.4; the median difference is -11.9.
  5. Effect sizes. Absolute: 14.8 minutes per order. Relative: 1 - 19.3/34.1 = 43\ \% less tardiness. Standardised: d_z = \bar\Delta / s_\Delta = -1.89, the mean difference in units of its daily spread.

Counts of days are a test of their own. If neither method were better and days were independent, each day would favour CP-SAT with probability \tfrac12, and all 20 days falling on one side would have probability 2 \times 0.5^{20} = 1.9 \times 10^{-6}. This is the sign test: crude, since it ignores the sizes, but free of any assumption on the distribution of tardiness. For DQN − SST the same report gives +1.3 [-2.1, +5.1], d_z = 0.15, better on 11 days of 20: no detectable difference either way.

Relative sizes can mislead. In the calm shop CP-SAT cuts EDD's tardiness by 81 %, but the gain is 5.7 minutes and d_z = -0.71: there is little tardiness to remove. Report the absolute difference first.

Many comparisons, a few false alarms. Seven methods make 21 pairs per level; if no pair differed, about 0.05 \times 21 = 1.05 intervals per level would still exclude zero by chance. scripts/evaluate.py fixes its comparisons in code, each non-rule method against the best rule at that level, and the README reports all of them, plus CP-SAT against Greedy replan, including the DQN ones that found nothing.

Part 7

The checker as executable invariants

Statistics cannot rescue a wrong simulator. If the simulation of B1 let a method break a rule of the shop, it would look better on every day, with a tight paired interval: the bug has to be caught in the schedules.

A small instance first. On the paint machine of A1, set up for blue, a log that paints A (blue, minutes 0 to 20) and then B (red) from 20 to 30, with no 10-minute colour change, finishes B at 30 instead of 40. One line of code, "before each job, the changeover from the previous colour", reads the log and catches it.

What is an executable invariant?

In plain words: a rule of the shop written as code that inspects a finished schedule and complains if the rule was broken, run on every schedule, not trusted.

More precisely: an invariant is a property every valid executed schedule must satisfy. jobshop/checker.py:check_schedule(ws, scenario, log) takes only the workshop data, the scenario and the executed log (machine work segments and the legs of the automated carts, AGVs) and returns the list of violated invariants; an empty list means the schedule is valid. It reads nothing from the simulator's internal state and nothing from a solver model, so a simulator or solver bug that makes a schedule break a rule of the shop cannot hide from it. Bugs that keep every invariant, such as a controller peeking at future breakdowns, a wrong due date in the scenario or a slip in run_metrics, need other tests.

What it checks. Four groups of invariants, re-derived from the log alone:

  1. Every operation, once, correctly: on a single eligible machine m \in \mathcal M_{jk}, for exactly its time p_{jkm}, with no changeover work after processing began and no work logged for an operation that does not exist.
  2. Machines: no two segments overlap; no work during a breakdown [t_{\text{down}}, t_{\text{up}}); no operation interleaved with another; before each operation, exactly the changeover s_m(f, g) from the previous family.
  3. Carts: every leg takes the layout's travel time \tau(a, b), starts where the previous one ended, and never overlaps another leg of the same cart.
  4. Jobs move physically: operation k+1 starts after operation k ends, and the job is carried by cart legs to the right machine's station before processing starts.

A bug the checker catches. The numbers script builds a simulator with a plausible bug: it reads every changeover as zero. Under breakdowns, the four rules then report a mean tardiness of 6.2 (FIFO), 4.1 (shortest job first, SPT), 3.3 (EDD) and 3.3 (SST) minutes, against 60.8, 45.4, 37.6 and 34.1 with the real simulator. SST and EDD become identical, because without changeovers SST falls back on its tie-break, the due date. The checker, given the true workshop, rejects 20 of 20 runs of every rule, with 2,998, 2,907, 2,934 and 2,934 violations such as "job 7 op 0 got 0 min of setup, needs 6". A subtler bug would favour one method: one in the plan-following code that let a planned job start before its cart delivered it would help CP-SAT only, and invariant group 4 exists for that case.

Testing the tester. A checker that accepts everything passes every run, so tests/test_checker.py takes a valid EDD log (seed 42, 40 jobs, frequent breakdowns: 277 work segments, 248 cart legs, 0 violations) and breaks it in one way per test:

def bootstrap_ci(
    values: Sequence[float],
    *,
    confidence: float = 0.95,
    resamples: int = 10_000,
    seed: int = 0,
) -> tuple[float, float]:
    """Percentile bootstrap confidence interval for the mean."""
    values = np.asarray(values, dtype=float)
    if len(values) < 2:
        return float("nan"), float("nan")
    rng = np.random.default_rng(seed)
    samples = rng.choice(values, size=(resamples, len(values)), replace=True)
    alpha = (1.0 - confidence) / 2.0
    low, high = np.quantile(samples.mean(axis=1), [alpha, 1.0 - alpha])
    return float(low), float(high)

rng.choice(values, size=(resamples, len(values)), replace=True) draws every resample at once: row b is n days drawn with replacement from \hat F_n. samples.mean(axis=1) gives the B means \bar\Delta^{*b}, and np.quantile at alpha = 0.025 and 1 - alpha reads the percentile interval; NumPy interpolates between neighbouring order statistics where the browser demo takes the lower one, another source of last-digit differences. The fixed seed=0 makes every table reproducible.

The paired comparison is built in level_tables, which writes the result tables. Its first statement sorts each method's runs by seed:

def check_schedule(ws: Workshop, scenario: Scenario, log: RunLog) -> list[str]:
    """Return the list of violations (empty list = the executed schedule is valid)."""
    errors: list[str] = []
    jobs = {j.idx: j for j in scenario.jobs}

    by_op: dict[tuple[int, int], list] = defaultdict(list)
    by_machine: dict[int, list] = defaultdict(list)
    for s in log.segments:
        if s.end <= s.start:
            errors.append(f"segment with non-positive length: {s}")
        if s.kind not in ("setup", "proc"):
            errors.append(f"unknown segment kind: {s}")
        by_op[(s.job, s.op)].append(s)
        by_machine[s.machine].append(s)

    # 1. every operation of every job is done once, on one eligible machine, for its full duration
    op_machine: dict[tuple[int, int], int] = {}
    op_first: dict[tuple[int, int], int] = {}
    op_last: dict[tuple[int, int], int] = {}
    for job in jobs.values():
        for op in range(ws.n_ops(job.family)):
            segs = sorted(by_op.get((job.idx, op), []), key=lambda s: s.start)
            if not segs:
                errors.append(f"job {job.idx} op {op}: never processed")
                continue
            machines = {s.machine for s in segs}
            machine = segs[0].machine
            op_machine[(job.idx, op)] = machine
            op_first[(job.idx, op)] = segs[0].start
            op_last[(job.idx, op)] = segs[-1].end
            if len(machines) > 1:
                errors.append(f"job {job.idx} op {op}: split over machines {sorted(machines)}")
                continue
            alternatives = ws.alternatives(job.family, op)
            if machine not in alternatives:
                errors.append(f"job {job.idx} op {op}: machine {machine} is not eligible")
                continue
            done = sum(s.end - s.start for s in segs if s.kind == "proc")
            if done != alternatives[machine]:
                errors.append(f"job {job.idx} op {op}: processed {done} min, needs {alternatives[machine]}")
            kinds = [s.kind for s in segs]
            if "proc" in kinds and "setup" in kinds[kinds.index("proc"):]:
                errors.append(f"job {job.idx} op {op}: setup work after processing started")
    for job_idx, op in by_op:
        if job_idx not in jobs or op >= ws.n_ops(jobs[job_idx].family):
            errors.append(f"work logged for unknown operation ({job_idx}, {op})")

    # 2. one thing at a time on a machine, no work while down, setup times respected
    for machine, segs in by_machine.items():
        segs.sort(key=lambda s: (s.start, s.end))
        for a, b in zip(segs, segs[1:]):
            if b.start < a.end:
                errors.append(f"machine {machine}: overlap between {a} and {b}")
        for s in segs:
            for down, up in scenario.downtime[machine]:
                if s.start < up and down < s.end:
                    errors.append(f"machine {machine}: work during downtime [{down}, {up}): {s}")
        order: list[tuple[int, int]] = []  # operations in the order the machine ran them
        for s in segs:
            if not order or order[-1] != (s.job, s.op):
                order.append((s.job, s.op))
        if len(order) != len(set(order)):
            errors.append(f"machine {machine}: an operation was interleaved with another one")
        previous_family = None
        for job_idx, op in order:
            if job_idx not in jobs:
                continue
            family = jobs[job_idx].family
            needed = ws.setup_time(machine, previous_family, family)
            done = sum(s.end - s.start for s in by_op[(job_idx, op)] if s.kind == "setup" and s.machine == machine)
            if done != needed:
                errors.append(
                    f"machine {machine}: job {job_idx} op {op} got {done} min of setup, needs {needed} "
                    f"(family {previous_family} -> {family})"
                )
            previous_family = family

    # 3. each AGV follows a continuous path in space and time, at the travel times of the layout
    legs_by_job: dict[int, list] = defaultdict(list)
    legs_by_agv: dict[int, list] = defaultdict(list)
    for leg in log.legs:
        legs_by_agv[leg.agv].append(leg)
        if leg.job is not None:
            legs_by_job[leg.job].append(leg)
    for agv, legs in legs_by_agv.items():
        if not 0 <= agv < ws.n_agvs:
            errors.append(f"unknown AGV {agv}")
        legs.sort(key=lambda g: (g.start, g.end))
        position, free_at = LOAD_STATION, 0
        for leg in legs:
            if leg.origin == leg.dest or leg.end - leg.start != ws.travel[leg.origin][leg.dest]:
                errors.append(f"AGV {agv}: leg duration does not match the layout: {leg}")
            if leg.start < free_at:
                errors.append(f"AGV {agv}: in two places at once, leg starts before the previous one ends: {leg}")
            if leg.origin != position:
                errors.append(f"AGV {agv}: leg starts at station {leg.origin} but the AGV is at {position}: {leg}")
            position, free_at = leg.dest, leg.end

    # 4. precedence inside a job, with the job physically carried from station to station
    used_legs = 0
    for job in jobs.values():
        legs = sorted(legs_by_job.get(job.idx, []), key=lambda g: g.start)
        position, available = LOAD_STATION, job.arrival
        for op in range(ws.n_ops(job.family)):
            key = (job.idx, op)
            if key not in op_machine:
                break
            first = op_first[key]
            if first < available:
                errors.append(f"job {job.idx} op {op}: starts at {first}, before the job is available ({available})")
            moves = [g for g in legs if available <= g.start and g.end <= first]
            used_legs += len(moves)
            for leg in moves:
                if leg.origin != position:
                    errors.append(f"job {job.idx}: picked up at station {leg.origin} but it is at {position}: {leg}")
                if leg.start < available:
                    errors.append(f"job {job.idx}: carried before it is available: {leg}")
                position, available = leg.dest, leg.end
            if position != ws.station(op_machine[key]):
                errors.append(
                    f"job {job.idx} op {op}: processed at station {ws.station(op_machine[key])} "
                    f"but the job is at station {position}"
                )
                position = ws.station(op_machine[key])
            available = op_last[key]
    if used_legs != sum(len(v) for v in legs_by_job.values()):
        errors.append("some loaded AGV legs do not fit between two operations of the job they carry")
    return errors

Group 1 gathers each operation's segments (by_op) and checks one machine, eligibility (ws.alternatives) and the processing total against p_{jkm}. Group 2 sorts each machine's segments, compares neighbours for overlap, intersects them with scenario.downtime[machine], recovers the order of operations and checks each changeover against ws.setup_time. Group 3 replays each cart from the load station, leg by leg; group 4 replays each job, its position and availability advanced only by its own legs and operations. Every error is a string saying what broke, which is what the tests assert on.

Part 9

Common pitfalls

  1. "The two intervals overlap, so the methods are not different." CP-SAT's [12.3, 27.1] and SST's [24.8, 44.9] overlap, yet the paired difference is [-18.4, -11.7]. Separate intervals ignore the correlation; judge the interval of the difference.
  2. "Same seed, same day." Only if the random numbers are synchronised. A shared generator whose draws depend on decisions gives each method a different day under the same seed.
  3. Tuning on the test. Every look at the test that changes a choice, a hyper-parameter, a checkpoint, which of several runs to report, makes the reported score optimistic. Choose on validation, report the test once.
  4. "Not significant" read as "equal". DQN − SST is [-2.1, +5.1]: the agent could be 2 minutes better or 5 worse. About 164 days would be needed to pin the 1.3-minute gap to \pm 1.3.
  5. Trusting the percentile interval at its word. With 20 skewed days it covers about 91 to 93 % of the time, and with 3 days it returns the data range. More days help more than more resamples.
  6. Trusting the simulator's own numbers. A bug can make a method look better on every day. Check every schedule with code that shares nothing with the simulator, test that code by breaking schedules on purpose, and remember that bugs keeping every invariant (a controller peeking at the breakdown calendar, a wrong due date) need other tests.
Part 10

Check your understanding

Try to answer each question before opening it.

1. Why does running every method on the same seeds make the comparison more precise?

A day's difficulty affects every method alike, so the results are positively correlated and \mathrm{Var}(X - Y) = \sigma_X^2 + \sigma_Y^2 - 2\rho\sigma_X\sigma_Y is much smaller than \sigma_X^2 + \sigma_Y^2. For CP-SAT − SST under breakdowns, 61.3 instead of 884.9.

2. What does the repository do so that a seed gives the same day to every method?

It draws the arrivals and each machine's breakdowns from separate generators, [seed, 1] and [seed, 2, m], all before the run, and puts the failures in calendar time. No decision can change which random number is used for what.

3. When can pairing hurt?

When the two methods' results are negatively correlated, \rho < 0: then -2\rho\sigma_X\sigma_Y > 0 and the paired difference is noisier than independent days would be. With a shared day effect this is rare; here every correlation is between 0.82 and 0.99.

4. What is the plug-in principle, applied to the mean difference?

Estimate the unknown distribution of a day by the empirical distribution of the 20 observed days, and the sampling distribution of \bar\Delta by that of the mean of 20 days drawn from it with replacement.

5. Why is the bootstrap interval for three days the whole data range?

Each extreme resample, all three draws equal to the most extreme day, has probability 1/27 = 0.037 > 0.025, so the 2.5 % and 97.5 % quantiles are the smallest and largest values. Three days are too few for the empirical distribution to resemble the true one.

6. Why must the bootstrap resample days, not each method's results separately?

Resampling days keeps each day's two results, and so their correlation, together; resampling separately throws the correlation away, which gives the unpaired interval, 3.8 times wider for CP-SAT − SST.

7. Why does picking the best of five agents on the test overstate its performance, and by how much here?

The lowest of five noisy scores is low partly by luck that will not repeat. The agent kept on validation scores 35.4 under breakdowns; the best test score of the five is 33.6. In the equal-means model the expected optimism is \sigma\sqrt{1-\rho}\,e_K/\sqrt n.

8. What does the checker look at, and why must it not look at anything else?

The workshop data, the scenario and the executed log only. If it used the simulator's state or the solver's model, it would share their bugs. It still cannot see a bug that keeps every invariant.

    Only the paired interval excludes zero. The unpaired one is 23.3 minutes wide against 7.6 and says nothing, because it treats two strongly correlated sets of days (r = 0.90) as unrelated.

  5. Break the simulator, let the checker catch it. Build a workshop whose changeovers are all zero, run SST on it for test seed 0 under frequent breakdowns, compute the mean tardiness from the log and check the log against the true workshop.

    Hint

    Workshop is a frozen dataclass: dataclasses.replace(ws, setup=...) returns a modified copy. run_metrics reads the log only. simulate(ws, scenario, controller) is shorthand for Shop(ws, scenario, controller).run().

    Solution 
    from dataclasses import replace
from jobshop.checker import check_schedule
from jobshop.metrics import run_metrics
from jobshop.rules import RuleController
from jobshop.scenario import make_scenario, make_workshop
from jobshop.shop import simulate
ws = make_workshop()
bug = replace(ws, setup=tuple(tuple(tuple(0 for _ in r) for r in mat) for mat in ws.setup))
sc = make_scenario(ws, 0, mtbf=120.0)
log = simulate(bug, sc, RuleController("SST"))
print(run_metrics(ws, sc, log)["mean_tardiness"])            # far below the real simulator's value
errors = check_schedule(ws, sc, log)
print(len(errors), errors[0])                                # "... got 0 min of setup, needs ..."

    Over the 20 test days the bugged simulator reports 3.3 minutes for SST instead of 34.1, and the checker rejects every run.

  6. Write a new invariant. Every job needs at least its fastest-route work: C_j \ge r_j + W_{f(j)}, with W_f the shortest total processing time (ws.min_remaining_work(f, 0)). Write a function that checks it on a log, verify that a valid EDD run passes, then shift every segment of one job 1,000 minutes earlier and verify that your check fails. Is the invariant implied by the checker's existing ones?

    Hint

    A job's completion is the largest end among its segments. The shift puts the job's work before its arrival.

    Solution 
    from dataclasses import replace
from jobshop.rules import RuleController
from jobshop.scenario import make_scenario, make_workshop
from jobshop.shop import simulate
ws = make_workshop(); sc = make_scenario(ws, 3, mtbf=120.0)

def check_min_flow(ws, sc, log):
    end = {}
    for s in log.segments:                                   # a job's completion: its latest segment end
        end[s.job] = max(end.get(s.job, s.end), s.end)
    return [f"job {j.idx} done at {end[j.idx]}, needs at least {j.arrival + ws.min_remaining_work(j.family, 0)}"
            for j in sc.jobs if end[j.idx] < j.arrival + ws.min_remaining_work(j.family, 0)]

log = simulate(ws, sc, RuleController("EDD"))
print(check_min_flow(ws, sc, log))                           # []
log.segments[:] = [replace(s, start=s.start - 1000, end=s.end - 1000) if s.job == 10 else s for s in log.segments]
print(check_min_flow(ws, sc, log)[:1])                       # ['job 10 done at -636, needs at least 250']

    It is implied: groups 1 and 4 already force every operation to start after the job is available and to last p_{jkm} \ge \min_m p_{jkm}, in order. A redundant invariant is still useful as a cheap second line of defence, and it gives a clearer message.

Part 12

The chapter on one page

  1. Common random numbers: the same seeds for every method, with synchronised streams.
  2. The paired variance: \mathrm{Var}(X - Y) = \sigma_X^2 + \sigma_Y^2 - 2\,\mathrm{Cov}(X, Y); for CP-SAT − SST, 61.3 instead of 884.9, an interval 6.7 instead of 25.2 minutes wide.
  3. The bootstrap: the plug-in principle yields the basic interval, a normalising transformation the percentile one; it assumes independent days and covers about 91 to 93 % at n = 20.
  4. Separation: train from seed 100001, choose on 5000 to 5009, report 0 to 19 once; choosing among five agents on the test would have reported 33.6 instead of 35.4.
  5. The winner's curse: the best of K equal candidates is optimistic by \sigma\sqrt{1-\rho}\,e_K/\sqrt n.
  6. The report: means and paired differences with intervals, days better / equal / worse, effect sizes, every comparison the code fixes.
  7. The checker: invariants checked on every schedule from the log alone; a simulator that forgot changeovers is rejected on 20 of 20 runs. Bugs that keep every invariant need other tests.

The vocabulary, in one table

Word Meaning
Replication One independent run of the simulated system; here one test day, one seed.
Common random numbers (CRN) The same random inputs for every method on a replication.
Synchronisation Each random number serves the same purpose in every run, whatever the decisions.
Paired difference \Delta_i The two methods' results on the same day, subtracted.
Standard error The standard deviation of a mean, \sigma/\sqrt n.
Covariance, correlation How two results move together across days; \rho = \mathrm{Cov}/(\sigma_X\sigma_Y).
Empirical distribution \hat F_n Mass 1/n on each observed value.
Plug-in principle Estimate t(F) by t(\hat F_n).
Percentile interval The 2.5 % and 97.5 % quantiles of the B resample statistics.
Coverage How often an interval procedure contains the true value.
Training, validation, test Days to learn on, to choose with, and to report once.
Winner's curse The optimism of the best of several noisy scores.
Effect size The size of a difference: absolute, relative, or standardised (d_z).
Invariant A property every valid schedule satisfies, checked by code on every run.

Scope. The chapter compares methods on a fixed, synthetic workshop whose days are independent by construction. A real plant has dependent days, a changing product mix and no ground truth; the same principles hold there but need a block bootstrap, longer horizons and a checker fed by real event logs.
